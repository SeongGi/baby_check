# 02-설계: 상대 기기 기록 알림

- 기준: `01-요구사항.md` (2026-11-13 1차·2차 결정 반영), master `8b61505` (1.8.2 코드 30)
- 대상 버전: 1.8.3 (코드 31), Android만
- 검토: 1회차 독립 검토 "조건부 승인(수정 후 재검토 불필요)". 지적 사항은 9장 표에 반영 위치를 적었다.
- 선행 작업: `feat/permission-notice`를 먼저 master에 합친다(01 6장). 이 설계의 권한 요청은 그 브랜치의 사전 안내를 거친다.

## 1. 전체 흐름

```
A 기기: 기록 저장 → POST /api/family/sync (pushLogs)
Worker: 쓰기 배치마다 [① 후보 id 존재 확인 SELECT + ② 기록 쓰기 + 토큰 갱신]을 한 트랜잭션으로 실행
        → ③ 기존 분류 읽기로 새 기록 확정 → ④ 응답 반환
        └ ctx.waitUntil: ⑤ 받을 기기 조회 → ⑥ 기기마다 걸러 메시지 만들기 → ⑦ Expo 푸시 API 호출 → ⑧ 죽은 토큰 정리
B 기기: 알림 표시 → 누르면 종류별 화면을 열고 동기화 요청
```

동기화 응답은 푸시 처리와 상관없이 지금과 똑같이 나간다. 알림 판정과 발송에서 생긴 오류는 `console.warn`으로만 남기고 응답 상태와 본문에 영향을 주지 않는다.

## 2. 서버 (`server/`)

### 2.1 D1 테이블 추가 (`schema.sql`)

```sql
CREATE TABLE IF NOT EXISTS push_devices (
  family_id TEXT NOT NULL,
  client_id TEXT NOT NULL,
  token TEXT NOT NULL,                 -- ExponentPushToken[...]
  types_json TEXT NOT NULL,            -- 받을 기록 종류 배열, 예: ["formula","urine"]
  quiet_start INTEGER DEFAULT NULL,    -- 방해 금지 시작(기기 현지 0~1439분), NULL이면 끔
  quiet_end INTEGER DEFAULT NULL,      -- 방해 금지 끝(기기 현지 0~1439분)
  tz_offset_min INTEGER NOT NULL,      -- 기기 현지 시각 - UTC (분). 한국은 540
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (family_id, client_id)
) WITHOUT ROWID;
CREATE INDEX IF NOT EXISTS idx_push_devices_token ON push_devices (token);
```

- 운영 D1에는 `wrangler d1 execute --remote --command`로 이 두 문장만 실행한다. 기존 테이블은 건드리지 않는다. **실행 전 성기님 승인.**
- 토큰 인덱스는 같은 토큰이 다른 가족에 남은 행을 지우는 데 쓴다(2.2).

### 2.2 새 API

인증은 기존과 같다(`getAuthContext`: 가족 키 해시 + clientId).

| 경로 | 본문 | 동작 |
|---|---|---|
| `POST /api/family/push-register` | `{ token, types, quietStart, quietEnd, tzOffsetMinutes }` | 한 배치로 실행한다. ① `members`에 `(family_id, client_id)`가 있을 때만(`AND EXISTS (SELECT 1 FROM members ...)`) 같은 토큰을 가진 다른 `(family_id, client_id)` 행을 지운다. ② 같은 조건으로 upsert한다(`INSERT ... SELECT ... WHERE EXISTS`). ②의 changes가 0이면 가족 유무를 보고 `familyMissingResponse`(404/410)를 그대로 돌려주고, 가족은 있는데 회원이 아니면 403 `not_member`를 돌려준다. 거절 응답(400·403·404·410)은 D1 상태를 바꾸지 않는다. |
| `POST /api/family/push-unregister` | `{}` | `(family_id, client_id)` 행을 지운다. 가족이 없어도 200 `ok`를 돌려준다. |

- `members` 행은 `connect` 때만 생긴다(`index.ts:193, 211`). 그래서 앱은 가족 연결(`connect`)이 성공해 `syncKey`를 저장한 뒤에만 등록한다(3.2).

검증 규칙:
- `token`: 문자열, `ExponentPushToken[` 또는 `ExpoPushToken[`으로 시작, 200자 이하. 아니면 400 `invalid_push_token`.
- `types`: 2.4의 9종 중에서만 받고, 중복은 지운다. 빈 배열이면 등록하지 않고 unregister와 같게 처리한다.
- `quietStart`, `quietEnd`: 둘 다 0~1439 정수이고 서로 다를 때만 저장한다. 하나라도 아니면 둘 다 NULL.
- `tzOffsetMinutes`: -840~840 정수. 아니면 540.

### 2.3 영구 삭제
- `POST /api/family/delete` 배치에 `DELETE FROM push_devices WHERE family_id = ?1 AND ${deleteGuard}`를 추가한다. `legacyDeletion` 경로는 가족이 없을 때만 동작하므로 바꾸지 않는다.
- 연결 해제는 서버 API가 없으므로 앱이 등록 기록을 보고 `push-unregister`를 보낸다(3.2).

### 2.4 새 기록 판정 (`/api/family/sync` 안)

알림 대상 종류(9종): `formula, urine, stool, bath, weight, temperature, sleep, tummyTime, play`. `diary`, `diaryComment`는 대상이 아니다.

1. **후보 고르기(메모리 계산만):** `pushLogs` 중 아래를 모두 만족하는 것만 후보로 둔다.
   - `raw`를 파싱한 `type`이 9종 중 하나
   - `timestamp`가 유한한 숫자이고 `timestamp >= serverNow - 30분`. 위쪽 상한은 두지 않는다(01 6장).
2. 후보가 없으면 판정을 끝낸다. 추가 D1 문장은 0개다. 이전, 전체 대조, 백업 복원은 대부분 이 단계에서 걸러진다.
3. **존재 확인을 쓰기 배치 안에 넣기:** 각 쓰기 배치(`index.ts:482-496`)의 **첫 문장**으로, 그 배치에 들어 있는 후보 id만 대상으로 `SELECT log_id FROM logs WHERE family_id = ?1 AND log_id IN (...)`을 넣는다. D1 batch는 한 트랜잭션이므로, 같은 id를 담은 요청 두 개가 겹쳐도 한쪽만 "없음"을 본다. 여기서 나온 id는 수정이거나 삭제 표식이 있는 기록이므로 뺀다. 단, 같은 요청의 앞 배치가 이미 쓴 후보 id는 뒤 배치 SELECT에 나와도 빼지 않는다(같은 id가 두 배치에 걸친 경우).
   - 한 배치의 문장 수 상한 100을 지키도록 `chunkSize`를 `D1_BATCH_CHUNK_SIZE - 2`(98)로 줄인다. 한 배치의 후보 id는 98개 이하이므로 `IN` 자리표시자도 99개 상한 안에 든다.
   - 후보가 없는 배치에는 SELECT를 넣지 않는다. 그래서 후보 없는 요청의 문장 수와 순서는 지금과 같다.
   - 배치 결과에서 SELECT 결과만 읽고, 나머지 결과는 지금처럼 쓰지 않는다.
4. **쓰기 뒤 확정:** 기존 분류 읽기(`readResults`)에서 후보 id의 행이 `deleted_at IS NULL`이고 `raw_json`이 보낸 값과 같은 것만 새 기록으로 확정한다. 같은 요청 안에서 삭제까지 한 기록은 빠진다.
5. 한 요청에서 확정된 새 기록이 40건을 넘으면 알림을 보내지 않는다. 30분 안의 대량 업로드를 막는 마지막 안전장치다.
6. **오류 격리:** SELECT가 배치 안에 있으므로 배치 실패는 지금도 sync 실패이고, 판정이 새 실패 원인을 더하지 않는다. 3~5단계의 계산(파싱, 결과 해석)은 try/catch로 감싸고, 실패하면 "새 기록 없음"으로 처리한다.

`/api/family/sync`의 응답 본문과 기존 쓰기·읽기 문장은 바꾸지 않는다. 바뀌는 것은 "후보가 있는 배치에 SELECT 1문장 추가"와 `chunkSize` 하나다.

### 2.5 발송 (`server/src/push.ts` 새 파일)

- 진입점을 `fetch(request, env, ctx?)`로 넓힌다. 새 기록이 1건 이상이면 `const p = sendPartnerPush(...).catch(warn)`을 만들고, `ctx?.waitUntil`이 있으면 넘기고 없으면 버린다(하네스와 옛 호출 방어).
- 아기 이름은 sync 읽기 배치에 이미 있는 `profileRow.shared_json`(`index.ts:541`)에서 꺼내 인자로 넘긴다. 추가 읽기는 없다.
- 바꿔 끼울 수 있는 지점: `env.pushFetch`(기본은 전역 `fetch`)와 `env.EXPO_PUSH_URL`(기본 `https://exp.host/--/api/v2/push/send`). 하네스는 이 둘로 127.0.0.1의 가짜 Expo 서버를 쓴다. `env.clock`과 같은 방식이다.

`sendPartnerPush(env, familyId, senderClientId, newLogs, babyName)`:
1. `SELECT client_id, token, types_json, quiet_start, quiet_end, tz_offset_min FROM push_devices WHERE family_id = ?1 AND client_id != ?2`. 받을 기기가 없으면 끝낸다.
2. 기기마다 `types_json`으로 새 기록을 거른다. 남은 기록이 없으면 그 기기는 건너뛴다.
3. 메시지를 만든다(2.6). 방해 금지 시간대 판정은 `m = ((floor(serverNow/60000) + tz_offset_min) % 1440 + 1440) % 1440`으로 한다. 시작 < 끝이면 `start <= m < end`, 시작 > 끝이면(자정을 넘음) `m >= start || m < end`이다.
4. 메시지를 100개씩 묶어 보낸다. 시간 제한은 5초(`AbortSignal.timeout(5000)`)이고 재시도하지 않는다.
5. 응답 ticket 중 `details.error === 'DeviceNotRegistered'`인 행을 지운다. 그 사이 새 토큰으로 다시 등록한 행을 지우지 않도록 가족 id, 기기 id, 토큰이 모두 맞는 행만 지운다. receipt 조회는 하지 않는다. 앱이 실행될 때마다 등록을 맞추므로 바뀐 토큰은 그때 갱신된다.

Expo 접근 토큰(`EXPO_ACCESS_TOKEN`)은 쓰지 않는다. Expo 프로젝트에서 "push 보안"을 켜지 않았으면 필요 없다. 구현 단계에서 켜져 있는지 확인한다.

### 2.6 메시지 형식

- 데이터: `{ kind: 'partnerLog', logId, type, quiet }`. `quiet`는 방해 금지 시간대 판정 결과이고, 앱이 앞 화면에 떠 있을 때 소리를 낼지 정하는 데 쓴다(`content.sound`는 플랫폼마다 평소에도 비어 있을 수 있어 쓰지 않는다).
- 제목: 아기 이름이 있으면 `"{이름} 새 기록"`, 없으면 `"아기 새 기록"`.
- 본문: 기록 시각이 가장 늦은 기록의 요약과 시각. 2건 이상이면 `" 외 N건"`을 붙인다. 예: `🍼 분유 120ml · 오후 3:20 외 2건`.
  - 시각은 받는 기기의 `tz_offset_min`으로 계산해 `오전/오후 h:mm` 형식으로 적는다(`Intl`에 기대지 않고 직접 만든다).
- 요약 규칙(수치가 없거나 유한하지 않거나 0 이하이면 수치를 뺀다). 분유 양·목욕 시간·체온은 소수 첫째 자리, 체중은 둘째 자리까지 반올림하고 끝의 0을 지운다(37.0 → `37℃`). 기간은 `1시간 20분`, `1시간`, `25분`으로 적는다. 수면·터미타임·놀이는 `endedAt`이 없으면 `시작`을 붙이고, `endedAt`이 숫자가 아니거나 시작보다 앞서거나 반올림해 0분이면 이름만 적는다(`😴 수면`):

| 종류 | 필드 | 예 |
|---|---|---|
| formula | `feedingType`(없으면 formula), `amount` | `🍼 분유 120ml`, `🍼 모유 120ml`, `🍼 혼합 120ml` |
| urine | 없음 | `💧 소변` |
| stool | 없음 | `💩 대변` |
| bath | `durationMinutes` | `🛁 목욕 15분` |
| weight | `weightKg` (소수 둘째 자리까지, 끝 0 제거) | `⚖️ 체중 4.25kg` |
| temperature | `temperatureC` (소수 첫째 자리, 끝 0 제거) | `🌡️ 체온 37.2℃` |
| sleep | `endedAt` | 없음 → `😴 수면 시작`, 있음 → `😴 수면 1시간 20분` |
| tummyTime | `endedAt` | `🧸 터미타임 시작` / `🧸 터미타임 10분` |
| play | `endedAt` | `🎈 놀이 시작` / `🎈 놀이 30분` |

- Expo 메시지: `{ to, title, body, data: { kind: 'partnerLog', logId, type }, channelId, priority, sound }`
  - 평소: `channelId: 'partner-records'`, `priority: 'high'`, `sound: 'default'`
  - 방해 금지 시간대: `channelId: 'partner-records-quiet'`, `priority: 'normal'`, `sound: null`
- 진행 중인 기록을 끝내는 것은 "수정"이므로 알림이 가지 않는다. 시작할 때만 알린다.

## 3. 앱

### 3.1 설정 저장 (`src/utils/partnerPush.ts` 새 파일)

AsyncStorage 키 `@partner_push_settings`:
```ts
type PartnerPushSettings = {
  enabled: boolean;
  types: PartnerPushType[];      // 기본 9종 전부
  quiet: { start: number; end: number } | null; // 분 단위, 기본 null
};
```
- **처음 상태(01 6장):** 설정 값이 아직 없으면 그때 알림 권한을 조회(`getPermissionsAsync`, 요청 창 없음)한다. `granted`이면 `enabled: true`, 아니면 `false`로 만들어 저장한다. 한 번 저장한 뒤에는 다시 정하지 않는다.
- 등록 기록 `@partner_push_registered`: `{ fingerprint, syncKey, clientId }`. 지문은 `sha256(syncKey)|clientId|token|types|quietStart|quietEnd|tz`이다. 가족 키 원문은 지문에 넣지 않지만, 해제 요청을 보내려면 키가 필요하므로 `syncKey`는 따로 저장한다(프로필 저장소와 같은 수준의 저장소다).

### 3.2 등록 맞추기 함수 하나
`reconcilePartnerPush({ syncKey, clientId, settings })` 하나가 등록과 해제를 모두 맡는다.
1. 저장된 등록 기록이 있고 그 `syncKey`나 `clientId`가 지금과 다르면, **저장된 값으로** `push-unregister`를 보내고 기록을 지운다. 응답은 2초까지만 기다린다. 등록 기록은 성공 여부와 상관없이 지우지만, 해제가 실패하면(404·410 제외) 저장된 키와 기기 번호를 `@partner_push_unregister_pending`(최대 5개)에 남기고 다음 호출 때마다 다시 보낸다. 서버에는 남은 행을 스스로 정리하는 경로가 없으므로, 이렇게 해야 알림을 끄거나 가족을 떠난 뒤에도 알림이 계속 오는 일을 막는다. 같은 키와 기기 번호로 다시 등록에 성공하면 그 해제 대기는 지운다. 이렇게 하면 해제·410 자동 해제·이전 모듈 해제·다른 가족 합류 같은 모든 경로가 한 곳에서 처리된다.
2. 지금 `syncKey`가 없으면 여기서 끝낸다. 토큰 조회를 포함해 푸시 관련 호출은 0회다(요구사항 3-7).
3. `enabled === false`이거나 `types`가 비었거나 권한이 `granted`가 아니면, 등록 기록이 있을 때만 `push-unregister`를 보내고 기록을 지운다.
4. 그 밖에는 채널을 만든 뒤(3.4) `Notifications.getExpoPushTokenAsync({ projectId })`(app.json `extra.eas.projectId`)로 토큰을 얻는다. 지문이 다르면 `push-register`를 보내고, 200이면 기록을 저장한다. 403·404·410이면 기록을 지우고 다시 시도하지 않는다(가족 상태는 동기화가 처리한다).
5. 네트워크 오류는 삼키고 다음 호출 때 다시 시도한다. 권한 조회는 5초, 토큰 조회는 10초 안에 끝나지 않으면 `token_error`로 끝낸다. 403·404·410으로 거절된 입력은 앱을 다시 켤 때까지 다시 보내지 않는다. 직렬화와 거절 상태는 앱 전체에서 하나만 쓰는 의존성 객체(`getPartnerPushDeps()`)에 둔다. 동기화 큐(`syncRunner`)와 섞지 않는다. 동시에 두 번 불리면 앞의 호출이 끝난 뒤 한 번 더 실행한다(직렬화).

호출 지점은 `App.tsx`의 effect 하나다. 의존성은 `[profile.syncKey, clientId, settingsVersion, appActive]`이다. `syncKey`가 바뀌는 모든 경로(`handleSaveProfile`, `syncRunner`의 `deps.saveProfile`, 이전 모듈)는 결국 `profile` 상태를 바꾸므로 따로 부르지 않는다. 그 밖에 `Notifications.addPushTokenListener`가 불리면 `settingsVersion`을 올려 다시 맞춘다. 리스너가 넘기는 값은 기기(FCM) 토큰이므로 쓰지 않고, 함수 안에서 `getExpoPushTokenAsync`를 다시 부른다.

### 3.3 Android 알림 채널
권한 요청과 토큰 조회 **전에** 채널 두 개를 만든다(Expo SDK 56 문서: 채널 생성이 `getExpoPushTokenAsync`보다 먼저여야 하고, Android 13은 채널이 있어야 권한 창이 뜬다).

## 5. 하네스 변경 (`tools/sync-harness/`)
- `real-server.mjs:305`: `worker.fetch(request, env, execCtx)`로 부른다. `execCtx.waitUntil(p)`는 `p`를 `pending` 배열에 넣는다. 백그라운드 작업은 `finishRecord` 뒤에 따로 기다리고, 그 쿼리 수는 `record.backgroundQueries`에 따로 센다. 그래서 `real-selfcheck.mjs:114` 같은 기존 쿼리 수 검사는 바뀌지 않는다.
- 가짜 Expo 서버: 127.0.0.1에서 뜨는 작은 HTTP 서버다. 받은 메시지를 기록하고, 시나리오가 응답(정상, `DeviceNotRegistered`, 500, 6초 지연)을 고를 수 있다. `env.EXPO_PUSH_URL`로 연결한다.
- `stubs/expo-notifications.mjs`: `getExpoPushTokenAsync`, `getPermissionsAsync`, `setNotificationChannelAsync`, `addPushTokenListener`, `addNotificationReceivedListener`, `getLastNotificationResponseAsync`를 추가하고 호출 수를 센다.
- `regression` 기본 모드의 `stubs/fake-worker.mjs`는 다시 만든 Worker라 푸시 판정이 없다. 푸시 확인은 실제 `index.ts`를 쓰는 real 모드와 단위 테스트에서 한다. fake-worker에는 새 API를 200으로 받는 최소 구현만 넣는다.

## 6. 검증 설계
- **서버 단위 테스트(`push-unit.mjs`, real-server 사용):** 새 기록만 알림, 수정·삭제·같은 요청 안 삭제·30분 넘은 기록 제외, 미래 시각 허용, 40건 상한, 보낸 기기 제외, 종류 거르기, 방해 금지(자정 넘는 구간 포함), 메시지 9종 형식과 결측 수치, `DeviceNotRegistered` 정리, 가족 삭제 시 행 삭제, 토큰 이동 시 옛 행 삭제, 회원이 아닌 기기 403, 같은 id를 담은 동시 요청 두 개에서 알림 1회.
- **동기화 보호:** `push_devices`에 행을 넣은 상태에서 가짜 Expo가 500, 6초 지연, 연결 거부일 때 sync 응답 상태·본문이 푸시 없는 경우와 같은지 비교한다. `verify.sh offline`(real 모드)이 그대로 통과해야 한다.
- **대량 업로드 시나리오(device-real):** 30분 안 기록이 섞인 첫 업로드, `restoreFromLocalBackup` 뒤 sync, 강제 전체 읽기에서 가짜 Expo 호출 수를 센다. 30분 안 기록만 알리고 40건 상한을 넘으면 0회여야 한다.
- **앱 단위 테스트(`reconcilePartnerPush`):** 혼자 쓰는 기기에서 토큰 조회·등록·해제 호출 0회, 다른 가족으로 옮기면 옛 가족 해제 후 새 가족 등록, 410 자동 해제 뒤 해제 요청, 권한 거부 시 등록 없음, 지문이 같으면 재전송 없음, 처음 상태가 권한에 따라 정해짐.
- 기존 `verify.sh unit`, `regression`, `offline`과 `npx tsc --noEmit`(앱, 서버) 통과.
- **원복 가능한 임시 변이(각각 해당 테스트가 실패해야 한다):** 30분 조건 제거, 보낸 기기 제외 제거, 존재 확인 제거, 같은 요청 안 삭제 확정 조건 제거, 지문에서 가족 키 빼기, `waitUntil` 대신 `await`(지연 시나리오에서 응답 지연이 잡혀야 함), 발송 catch 제거(500이 잡혀야 함).
- **실기기(성기님 도움 필요):** Expo Go의 Android는 SDK 53부터 원격 푸시를 쓸 수 없으므로 EAS 빌드나 개발 빌드로 확인한다. 에뮬레이터는 Google Play 이미지여야 한다. 두 기기에서 앱이 꺼진 B에 10초 안에 알림, 끈 종류는 안 옴, 방해 금지 시간대에는 소리 없음, 알림을 누르면 종류별 화면을 연다.

## 8. 알려진 한계와 위험
- 쓰기 배치가 커밋된 뒤 뒤 배치나 읽기 배치가 실패하거나, 응답 직전 예외나 Worker 중단으로 응답을 잃으면, 재시도 때 그 기록은 "이미 있음"으로 잡혀 알림이 빠진다. 중복을 막는 대가로 받아들인다. 보통 기록 하나는 배치 하나에 들어가므로 드물다.
- 앱을 지운 기기의 `DeviceNotRegistered`는 대개 receipt로 늦게 오므로, receipt를 조회하지 않는 지금은 죽은 행이 대부분 남아 발송 대상에 계속 들어간다. 기능에는 해가 없고, 그 기기가 다시 등록하거나 가족이 삭제되면 정리된다.
- `tz_offset_min`은 등록할 때만 갱신되므로, 기기 시간대가 바뀌면 다음 등록 맞추기 전까지 시각 표시와 방해 금지 판정이 어긋난다. 앱은 `-new Date().getTimezoneOffset()`(부호 반전)을 보낸다.
- 30분 조건은 기록 시각(`timestamp`)으로 판정하므로, 40분 전 일을 지금 입력하면 알리지 않는다(01 6장 결정).
- 등록이 403·404·410으로 거절되면 같은 입력은 앱을 다시 켤 때까지 다시 보내지 않는다.
- OS 설정에서 알림 권한을 끄면 다음에 앱을 열 때까지 서버가 계속 보낸다. 기기에 표시되지 않으므로 해는 없다.
- 전환기(`familyMigration.ts:557`)에 다른 기기가 만든 최근 기록을 대신 올리면, 기록을 만든 기기가 자기 기록 알림을 받을 수 있다. 기록에 만든 기기 정보가 없어 막을 수 없고, 30분 조건으로 대부분 걸러진다.
- Expo 푸시 API가 장애이면 알림만 빠지고 동기화는 그대로다. FCM 설정이 빠지면 `getExpoPushTokenAsync`가 실패하므로 앱은 안내를 띄우고 스위치를 끈다.
