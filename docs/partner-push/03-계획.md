# 03-계획: 상대 기기 기록 알림

- 기준 설계: `02-설계.md` (1회차 검토 반영, `5b3fdbb`)
- 선행 조건: `feat/permission-notice`를 master에 합친 뒤, 이 브랜치를 그 master 위로 옮기고 시작한다.
- 구현 담당: 커밋 1~3은 서버와 하네스, 커밋 4~6은 앱이다. 여러 파일에 걸친 구현은 t1-worker(sonnet)에게 맡기고, 주 세션은 설계 대조, diff 검토, 테스트 결과 확인을 맡는다.

## 커밋 단위

| 순서 | 커밋 | 바꾸는 파일 | 완료 확인 |
|---|---|---|---|
| 1 | 하네스가 `ctx`를 넘기고 가짜 Expo 서버를 둔다 | `tools/sync-harness/real-server.mjs`, 새 `fake-expo.mjs`, `stubs/expo-notifications.mjs` | 기존 `verify.sh unit`, `regression`, `offline`이 그대로 통과한다. 쿼리 수 검사도 그대로다. |
| 2 | 서버: `push_devices` 테이블, 등록·해제 API, 영구 삭제 정리 | `server/schema.sql`, `server/src/index.ts`, `tools/sync-harness/stubs/fake-worker.mjs` | 새 `push-unit.mjs`의 등록 검증·403·토큰 이동·삭제 정리 테스트가 통과한다. 서버 `tsc`가 통과한다. |
| 3 | 서버: 새 기록 판정과 발송 | `server/src/index.ts`, 새 `server/src/push.ts` | `push-unit.mjs`의 판정·메시지·방해 금지·동시 요청·동기화 보호 테스트가 통과한다. `verify.sh offline`이 통과한다. |

| 7 | 대량 업로드 시나리오와 검증 기록 | 새 `tools/sync-harness/real-scenarios-push.mjs`, `docs/partner-push/04-검증.md` | 6장 시나리오와 임시 변이 결과를 04에 적는다. |

`google-services.json`과 `app.json`의 `googleServicesFile`, 버전 1.8.3(코드 31)은 성기님의 Firebase 작업이 끝난 뒤 따로 커밋한다.

## 커밋마다 반복하는 절차
1. 구현한다(t1-worker에 설계 해당 절, 바꿀 파일, 완료 확인 명령을 넘긴다).
2. 독립 리뷰 2개를 동시에 돌린다. 하나는 설계와 맞는지, 하나는 정확성 버그만 본다.
3. 지적을 모아 고친다. 이 과정은 최대 3회까지 반복한다.
4. 테스트 출력을 확인하고 커밋한다.
