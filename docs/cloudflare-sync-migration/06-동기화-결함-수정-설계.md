# 06-동기화 결함 수정 설계 (1.8.0 단계 A, 5판)

이 문서는 이미 구현한 1.8.0 Cloudflare 동기화(`02-설계.md`)에서 찾은 결함과 대책을 적는다. 결함은 기존 사용자 이전과 상관없이 새로 만든 가족에도 생긴다. 대책은 `05-기존사용자-이전-설계.md`(4판)에서 옮겨 왔고, 이전 관련 내용(Firestore 읽기, 전환기, 이전 근거 표식, `firestore_origin`)은 넣지 않았다. 이전은 단계 B에서 이 문서의 결과 위에 다시 설계한다.

2판은 1차 독립 검토를, 3판은 2차 독립 검토를 반영했다(두 판정 모두 수정 필요). 4판은 3차 독립 검토(수정 필요)를 반영했다. 가장 큰 변경은 `App.tsx`에 있던 동기화 대기열, 상한 뒤 판정, 회차 이어 가기를 하네스가 직접 실행하는 모듈 `src/database/syncRunner.ts`(2.11)로 옮긴 것이다. 3회 상한을 넘는 4차 검토는 성기님이 승인했다. 5판은 4차 독립 검토(수정 필요)의 지적 14건을 반영했다. 가장 큰 변경은 연결 회차의 결과를 상한뿐 아니라 모든 실패(410, 404 제외)에서 저장된 키로 판정하게 한 것(2.6.3)과, 같은 버전 재전송을 직접 일으켜 쓰기 0행을 판정하는 시나리오 단계(5.1의 5, 8-1, 9)다. 성기님 결정에 따라 5판은 설계 검토를 다시 받지 않고 구현으로 넘어가며, 구현 뒤 독립 리뷰 2개와 변이 검증이 반영 결과를 확인한다. 반영 내역은 7장에 모았다.

1.8.0은 아직 출시 전이고 D1 데이터베이스도 없다. 그래서 서버 API와 장부 형식은 이전 형식과 호환하지 않아도 된다. 다만 1.7.9 기기에 남아 있는 옛 장부 `@baby_sync_ledger_v1`은 단계 B가 쓸 수 있도록 읽지도 지우지도 않는다.

## 0. 불변 조건
모든 단계와 검증 시나리오는 아래 조건을 기준으로 판정한다.

1. **기록 보존:** 동기화는 기기 기록을 합치기만 하고 줄이지 않는다. 사용자가 지운 기록만 삭제 표식으로 사라진다.
2. **수렴:** 두 기기가 오류 없이 동기화를 마치면 두 기기와 서버의 살아 있는 기록, 삭제 표식, 아기 정보가 같아진다. 같은 `updatedAt`에 내용이 다른 기록도 세 곳이 같은 쪽을 고른다.
3. **자동 연결 해제 제한:** 앱이 스스로 가족 연결을 끊는 근거는 서버의 410(`family_deleted`)뿐이다. 404는 "동기화 중지와 오류 표시"로만 처리한다.
4. **부활 금지:** 영구 삭제한 가족은 어떤 요청으로도 D1에 다시 생기지 않는다.
5. **혼자 쓰기 무요청:** `syncKey`가 없으면 네트워크 요청이 0회다.
6. **장부는 힌트:** 장부가 없거나 깨지면 전체 모드로 돌아가고, 장부가 틀려서 기록이 사라지는 일은 없다. 장부에는 서버에 있다고 확인한 내용만 적는다.

## 1. 찾은 결함

### 결함 1: 500건·1MB를 넘으면 동기화가 영구히 멈춘다 (`05` 결함 J)
- 서버는 요청 하나에 기록과 삭제 표식을 합쳐 500건(`server/src/index.ts:34`, `:251-253`), 본문 1MB(`:33`, `:77-80`)까지만 받는다.
- 클라이언트는 전체 모드에서 모든 기록과 삭제 표식을 요청 하나에 담는다(`src/database/sync.ts:200-213`). `postSync`(`src/database/cloudClient.ts:118-127`)는 나눠 보내지 않는다.
- 413이 나면 장부가 갱신되지 않으므로 다음 회차도 전체 모드가 되고, 동기화가 영구히 멈춘다. 가짜 Worker(`tools/sync-harness/stubs/fake-worker.mjs`)에 한도가 없어서 하네스가 잡지 못했다.
- 당겨 받기도 한 응답에 가족의 모든 행을 담는다(`index.ts:366-380`). 기록이 수천 건이면 무료 Workers의 CPU 한도(요청당 10ms)와 응답 크기가 문제가 된다. 지금은 받은 행을 모두 `JSON.parse`한다(`:384-399`).

### 결함 2: 장부가 올리지 않은 기록을 "올림"으로 적는다 (`05` 8.4 중간 2)
- `sync.ts:299-302`는 저장 결과(`saveSyncedDataWithoutLoss`가 합친 기록 전부, `sync.ts:281`)를 모두 `uploaded`에 적는다.
- 요청이 오가는 동안 사용자가 추가하거나 고친 기록도 저장 단계에서 합쳐지므로, 서버에 보내지 않았는데도 장부에는 올린 것으로 남는다. 다음 증분 회차는 그 기록을 보내지 않으므로, 상대 기기는 6시간 전체 대조 때까지 그 기록을 받지 못한다.
- 삭제 표식도 같다. `sync.ts:310-311`은 합친 삭제 id 전부를 `tombstoned`에 적는다. 재전송 호출(`sync.ts:291-295`)이 실패하거나 중단되면 그 표식은 서버에 가지 않은 채 장부에만 남는다.

### 결함 3: D1에 행이 없을 때 올린 삭제 표식이 사라진다 (`05` 결함 E)
- `index.ts:292-300`은 `UPDATE`라서 행이 없으면 아무 일도 하지 않는다. 클라이언트는 그 id를 장부에 적는다(`sync.ts:310-311`).
- 기기 A가 기록을 만들고 올리기 전에 지운 경우, 혹은 A가 지운 기록을 기기 B가 아직 올리지 않은 경우가 해당한다. B가 나중에 그 기록을 올리면 서버에 삭제 표식이 없으므로 기록이 되살아나 A에도 다시 들어온다.

### 결함 4: 같은 버전을 다시 올려도 행을 다시 쓴다 (`05` 2.7-2, 4.1)
- 기록 upsert의 갱신 조건은 `excluded.client_updated_at >= logs.client_updated_at`이다(`index.ts:284-285`). 같은 버전을 다시 보내도 `updated_at`이 새 시각으로 바뀌고, D1 쓰기 행을 쓴다.
- 쓰기가 실제로 없어도 `hasWrites`가 참이면 가족의 `updated_at`과 `last_client_id`를 바꾼다(`index.ts:350-355`). 상대 기기는 변경 토큰이 바뀐 것을 보고 동기화하지만 받을 것이 없다.
- 전체 모드는 모든 기록을 보내므로(`sync.ts:203`) 6시간마다, 그리고 당겨서 새로고침(`App.tsx:562`)마다 가족 기록 전체를 다시 쓴다. 기록 3,000건, 기기 2대, 하루 4회면 가족당 하루 약 4만 8천 행(인덱스 포함)이라서, 두 가족이면 무료 등급 쓰기 한도 10만 행에 이른다.
- 아기 정보도 같다. 서버는 `profile_updated_at === 0`이면 아기 정보를 무조건 다시 쓴다(`index.ts:312-313`). 새 기기의 기본 프로필은 `sharedUpdatedAt: 0`이라서(`storage.ts:33`) 두 기기 모두 아기 정보를 고친 적이 없으면 요청마다 아기 정보를 다시 쓰고 변경 토큰을 바꾼다. 상대 기기가 그 토큰을 보고 동기화하면 또 바뀌는 핑퐁이 생긴다. 서버는 `pushProfile.name ?? family.shared_name`처럼 빠진 항목을 기존 값으로 채우고(`:314-317`), 돌려줄 때는 빈 문자열을 `undefined`로 바꾼다(`:339-342`). 그래서 서버에 저장된 아기 정보와 클라이언트가 비교하는 값이 같은 모양이 아니다.
- 같은 `updatedAt`에 내용이 다르면 서버는 늦게 온 쪽을, 클라이언트는 정렬상 큰 쪽(`sync.ts:89-92`, `storage.ts:335-336`)을 고른다. 두 규칙이 달라서 기기와 서버가 서로 다른 내용으로 굳을 수 있다(불변 조건 2 위반).

### 결함 5: 두 기기가 동시에 가족을 만들면 늦은 쪽이 500을 받는다 (`05` 결함 H)
- 가족 생성(`index.ts:119-130`)의 `INSERT`에 충돌 처리가 없다. 같은 키로 거의 동시에 연결하면 늦은 쪽 요청은 PRIMARY KEY 충돌로 500을 받는다.

### 결함 6: 동시 업로드 때 당겨 받기 커서가 앞서간다 (`05` 결함 K)
- 서버는 요청 시작 때 `serverTime`을 정하고(`index.ts:263`) 쓰기를 100문장씩 나눠 확정한다(`:357-359`). 당겨 받기는 `updated_at > lastSyncedAt`이다(`:373`).
- A의 요청이 확정하기 전에 B의 요청이 당겨 받기를 마치면, B의 커서(B의 `serverTime`)가 A의 행 시각(A의 `serverTime`)보다 뒤로 간다. B는 A의 기록을 다음 전체 대조 때까지 받지 못한다.

### 결함 7: 404 한 번에 가족 연결이 끊기고, 영구 삭제를 구별하지 못한다 (`05` 불변 조건 3, 2.7-1, 2.4.2)
- `sync.ts:170-176`(connect)과 `sync.ts:332-341`(sync)은 404를 곧바로 `familyUnavailable`로 바꾸고, `App.tsx:254-269`는 연결을 끊는다.
- 404는 영구 삭제 외에도 서버 설정 오류(D1 바인딩 잘못, 데이터베이스 교체, 되돌리기)에서 나온다. 설정 오류 한 번에 모든 기기의 연결이 끊기면 사용자가 다시 초대해야 하고, 그 사이 기록은 공유되지 않는다.
- 영구 삭제한 가족을 서버가 기억하지 않으므로, 같은 키로 `allowCreate: true` 연결을 보내면 가족이 다시 생긴다(불변 조건 4 위반 가능).
- 변경 토큰 폴링은 404에도 계속 재연결을 시도한다(`App.tsx:372-399`).

### 결함 8: 평소 동기화 합치기가 꺼져 있다 (1차 검토, 기존 결함)
- `App.tsx:160`의 `isStandardSync`는 `allowFamilyCreation`이 참이어야 한다. 평소 동기화는 `allowFamilyCreation = false`(`App.tsx:150`)라서 이 값은 항상 거짓이고, 연달아 들어온 평소 동기화가 합쳐지지 않고 모두 대기열에 쌓인다.
- 2.6에서 한 회차가 여러 요청으로 길어지면, 저장할 때마다 회차가 하나씩 쌓여 요청 수가 늘어난다.
- 이 판정은 `App.tsx` 안에 있어서 하네스가 실행할 수 없다. 하네스는 `storage.ts`, `sync.ts`, `syncDeadline.ts`만 불러온다(`regression.mjs:1-6`). 상한 뒤 판정(`App.tsx:212-218`)도 같은 처지다. 그래서 2.11에서 두 판정을 공용 모듈로 옮긴다.

## 2. 대책

### 2.1 서버: 삭제된 가족 기록과 410 (결함 7)
`server/schema.sql`에 테이블을 더한다.

```sql
CREATE TABLE IF NOT EXISTS deleted_families (
  id TEXT PRIMARY KEY,       -- familyId (SHA-256 해시)
  deleted_at INTEGER NOT NULL
);
```

- 영구 삭제 배치(`index.ts:229-235`)의 맨 앞에 `INSERT OR IGNORE INTO deleted_families (id, deleted_at) VALUES (?1, ?2)`를 넣는다. 같은 배치라서 함께 확정된다.
- 가족 행이 없을 때 모든 경로(connect, token, deletion-status, delete-schedule, cancel-delete, delete, sync)는 `deleted_families`를 본다. 있으면 410 `family_deleted`, 없으면 404 `family_not_found`다. connect는 `allowCreate`와 상관없이 410을 돌려준다.
- 이 판정은 공통 함수 `familyMissingResponse(env, familyId)` 하나로 만든다. 가족 행을 읽은 쿼리가 없음을 돌려준 경우에만 부르므로, 평소 요청의 쿼리 수는 늘지 않는다.
- 저장 값은 키의 해시뿐이라서 이 테이블에 개인정보는 없다.

### 2.2 서버: 동시 가족 생성 (결함 5, 불변 조건 4)
- 가족 생성을 한 배치로 바꾼다.

  ```sql
  INSERT OR IGNORE INTO families (id, created_at, updated_at, last_client_id)
  SELECT ?1, ?2, ?2, ?3
  WHERE NOT EXISTS (SELECT 1 FROM deleted_families WHERE id = ?1);

  INSERT INTO members (family_id, client_id, created_at, last_active_at)
  SELECT ?1, ?3, ?2, ?2
  WHERE EXISTS (SELECT 1 FROM families WHERE id = ?1)
  ON CONFLICT(family_id, client_id) DO UPDATE SET last_active_at = excluded.last_active_at;
  ```

- 응답의 `isNewFamily`는 첫 문장의 `meta.changes`가 1인지로 정한다.
- 두 번째 문장의 `meta.changes`가 0이면 가족 행이 없는 것이다(삭제 기록 때문에 생성이 막혔거나, 삭제와 겹쳤다). 이때는 `familyMissingResponse`를 불러 410이나 404를 돌려준다. 따로 가족 행을 다시 읽지 않는다.
- 삭제 요청과 생성 요청이 겹쳐도 `WHERE NOT EXISTS`가 같은 문장 안에서 판정하므로 가족이 되살아나지 않는다.
- 이미 있는 가족에 연결하는 경로(`index.ts:103-109`)의 회원 `INSERT`도 위 두 번째 문장으로 바꾼다. 삭제와 겹쳐도 가족 없는 `members` 행이 남지 않고, 변경 행이 0이면 같은 방식으로 410이나 404를 돌려준다.
- **미리 확인하지 않는다:** `allowCreate`가 참이고 가족 읽기가 "없음"을 돌려주면, `deleted_families`를 미리 읽지 않고 곧바로 위 생성 배치로 간다. 삭제 기록 판정은 생성 문장의 `WHERE NOT EXISTS` 한 곳에서만 한다. 미리 확인하는 코드가 있으면 그 확인이 시나리오 10을 먼저 막아서, `WHERE NOT EXISTS`를 뺀 변이가 드러나지 않는다. `allowCreate`가 거짓이면 생성 배치 없이 `familyMissingResponse`로 410이나 404를 돌려준다.

### 2.3 서버: 기록 upsert와 같은 버전 무시 (결함 4, 불변 조건 2)
- 서버는 받은 기록을 **canonical JSON**으로 바꿔 `raw_json`에 저장한다. canonical JSON은 키를 정렬하고 `undefined` 값을 뺀 `JSON.stringify` 결과다. 클라이언트의 `canonical`(`sync.ts:69-80`), `stableValue`(`storage.ts:292-301`)와 같은 알고리즘이다. 이 함수는 서버 파일 안에 그대로 옮겨 둔다(서버는 앱 코드를 import하지 않는다).
- 기록 upsert를 아래처럼 바꾼다.

  ```sql
  INSERT INTO logs (family_id, log_id, client_updated_at, updated_at, deleted_at, raw_json)
  SELECT ?1, ?2, ?3, ?4, NULL, ?5
  WHERE EXISTS (SELECT 1 FROM families WHERE id = ?1)
  ON CONFLICT(family_id, log_id) DO UPDATE SET
    client_updated_at = excluded.client_updated_at,
    updated_at = excluded.updated_at,
    raw_json = excluded.raw_json
  WHERE logs.deleted_at IS NULL
    AND (excluded.client_updated_at > logs.client_updated_at
      OR (excluded.client_updated_at = logs.client_updated_at
          AND excluded.raw_json > logs.raw_json));
  ```

  - 같은 버전을 다시 올리면 조건이 거짓이라서 행을 쓰지 않고, `updated_at`도 바뀌지 않는다.
  - 같은 `updatedAt`에 내용이 다르면 canonical JSON이 큰 쪽이 이긴다. SQLite의 기본 문자열 비교(BINARY)는 UTF-8 바이트 순서이고, 이 순서는 유니코드 코드 포인트 순서와 같다.
  - `WHERE EXISTS`는 영구 삭제 배치와 동시에 도는 요청이 고아 행을 남기지 않게 한다.
- **클라이언트 타이브레이커 일치:** JavaScript의 `>` 비교는 UTF-16 코드 단위 순서라서, 메모에 이모지(보충 평면 문자)와 U+E000~U+FFFF 문자가 함께 있으면 SQLite와 순서가 갈린다. `mergeLogs`(`sync.ts:89-92`)와 `saveSyncedDataWithoutLoss`(`storage.ts:335-336`)의 비교를 코드 포인트 비교 함수 `compareCodePoints(a, b)`로 바꾼다. 함수는 `src/utils/`에 두고 두 곳이 함께 쓴다. 아기 정보 비교(`sync.ts:258-260`, `storage.ts:354-355`)도 같은 함수를 쓴다.
- **배치마다 시각과 토큰:** 서버는 쓰기 배치(100문장 이하)마다 `now(env)`로 새 시각 `t`를 찍고, 그 배치의 모든 행에 `updated_at = t`를 쓴다. 각 배치의 마지막 문장으로 아래 조건부 토큰 갱신을 넣는다.

  ```sql
  UPDATE families SET updated_at = ?t, last_client_id = ?c
  WHERE id = ?f
    AND EXISTS (SELECT 1 FROM logs WHERE family_id = ?f AND updated_at = ?t);
  ```

  - 같은 배치라서 행 확정과 토큰 갱신이 함께 일어나거나 함께 일어나지 않는다. 배치가 확정된 뒤 Worker가 끊겨도 토큰은 이미 바뀌어 있다.
  - 그 배치에서 실제로 쓴 행이 없으면(같은 버전 재전송) `EXISTS`가 거짓이라서 토큰이 바뀌지 않는다. 다른 요청이 같은 밀리초에 쓴 행 때문에 토큰이 한 번 더 바뀔 수는 있지만, 상대 기기가 받을 것이 없는 동기화를 한 번 더 할 뿐이다.
  - 지금처럼 모든 배치 뒤에 따로 실행하는 토큰 갱신(`index.ts:350-355`)은 없앤다.
- **아기 정보:** `families`에 `shared_json TEXT` 열을 더한다. 공유 항목(`name`, `birthDate`, `birthWeight`, `targetFormula`)을 canonical JSON으로 담는 열이고, 이 값이 아기 정보의 기준이다.
  - 서버는 `pushProfile`의 공유 항목을 받은 그대로 canonical JSON으로 만든다. 빠진 항목을 기존 값으로 채우지 않는다(`index.ts:314-317`의 `??` 채우기를 없앤다).
  - **완전한 아기 정보만 쓴다:** 서버는 공유 항목 4개가 모두 있고 형식이 맞을 때만 아기 정보를 쓴다. 형식은 `name`, `birthDate`, `birthWeight`가 문자열(빈 문자열 허용), `targetFormula`가 유한한 숫자다. 하나라도 어긋나면 기록 처리는 그대로 하고 아기 정보만 쓰지 않으며, 응답에 `profileRejected: true`를 싣는다. 클라이언트는 `normalizeProfile`을 거친 프로필을 보내므로 평소에는 일어나지 않는다.
  - 갱신은 아래 문장 하나로 판정한다. `profile_updated_at === 0` 예외(`index.ts:313`)는 없앤다.

    ```sql
    UPDATE families SET shared_json = ?j, profile_updated_at = ?ts,
      updated_at = ?t, last_client_id = ?c
    WHERE id = ?f
      AND (profile_updated_at < ?ts
        OR (profile_updated_at = ?ts AND COALESCE(shared_json, '') < ?j));
    ```

  - 기록과 같은 규칙(시각이 크면 이기고, 같으면 canonical JSON이 큰 쪽)이다. 고친 적 없는 두 기기의 기본 아기 정보는 시각과 내용이 같으므로 처음 한 번만 쓰이고, 그 뒤에는 쓰이지 않는다.
  - 토큰 갱신을 같은 문장에 넣었으므로 아기 정보가 실제로 바뀔 때만 토큰이 바뀐다. 이 문장은 첫 쓰기 배치에 넣고, 올릴 기록이 없으면 이 문장만으로 배치를 만든다.
  - 응답의 `remoteProfile`은 `shared_json`을 그대로 펼친 값과 `sharedUpdatedAt = profile_updated_at`이다. 빈 문자열을 `undefined`로 바꾸지 않는다. 그래서 클라이언트가 비교하는 값과 서버에 저장된 값이 같은 모양이다.
  - **어느 시점의 값인가:** `remoteProfile`은 쓰기 배치를 모두 확정한 **뒤에** 읽은 값이다. 쓰기 전 값을 돌려줘도 다음 회차에 바로잡히지만, 같은 요청 안에서 다른 기기의 아기 정보가 확정된 경우에 한 회차가 늦어진다. 확정 뒤에 읽으면 이 지연이 없고 쿼리 수도 늘지 않으므로 이 시점으로 정한다. 이 차이는 변이 검증으로 잡을 만큼 드러나지 않으므로 5.2 변이 표에는 넣지 않는다. 서버는 2.5의 분류 읽기 배치에 `SELECT shared_json, profile_updated_at FROM families WHERE id = ?1`을 함께 넣는다. 올릴 것이 없는 요청(당겨 받기만 하는 요청)은 당겨 받기 쿼리와 같은 배치에서 읽는다.
  - **값이 없을 때:** `shared_json`이 NULL이면(아직 아무 기기도 완전한 아기 정보를 올리지 않음) 응답에 `remoteProfile`을 넣지 않는다. 빈 객체 `{}`를 돌려주지 않는다.
  - 기존 열(`shared_name` 등)은 스키마에서 뺀다. D1이 아직 없으므로 옮길 데이터가 없다.
  - **`profile_updated_at`은 NOT NULL:** 지금 스키마(`schema.sql:13`)는 `profile_updated_at INTEGER DEFAULT 0`이라서 NULL이 들어갈 수 있다. NULL이면 위 갱신 조건의 비교가 모두 NULL이 되어 아기 정보가 영원히 쓰이지 않는다(4차 검토자가 실행해 확인). 그래서 `profile_updated_at INTEGER NOT NULL DEFAULT 0`으로 바꾼다.

### 2.4 서버: 삭제 표식 upsert (결함 3)
`index.ts:292-300`을 아래처럼 바꾼다. `raw_json`은 NOT NULL이라서 최소 JSON을 넣는다.

```sql
INSERT INTO logs (family_id, log_id, client_updated_at, updated_at, deleted_at, raw_json)
SELECT ?1, ?2, 0, ?3, ?3, ?4
WHERE EXISTS (SELECT 1 FROM families WHERE id = ?1)
ON CONFLICT(family_id, log_id) DO UPDATE SET
  deleted_at = excluded.deleted_at, updated_at = excluded.updated_at
WHERE logs.deleted_at IS NULL;
```

- `?4`는 `{"deleted":true,"id":"<logId>"}`(canonical JSON)다.
- 이미 삭제된 행은 다시 쓰지 않는다. 그래서 삭제 표식을 다시 보내도 상대 기기가 같은 표식을 다시 받지 않는다.
- 당겨 받기는 `deleted_at`이 있는 행을 `log_id`만으로 내보낸다(지금도 `index.ts:385-393`이 그렇게 한다). `raw_json`을 기록으로 쓰는 곳은 당겨 받기 한 곳뿐이므로, 다른 코드는 고치지 않아도 된다.

### 2.5 서버: sync 요청을 올리기와 당겨 받기로 나눈다 (결함 1, 6)
`POST /api/family/sync`의 요청과 응답을 아래처럼 바꾼다. 1.8.0은 출시 전이라서 `lastSyncedAt` 기반 형식은 남기지 않는다.

요청:

| 필드 | 뜻 |
|---|---|
| `pushLogs`, `pushDeletedIds` | 올릴 기록과 삭제 id. 합쳐 500건, 본문 1MB까지(서버 한도는 그대로 둔다). |
| `pushProfile` | 아기 정보. 지금과 같다. |
| `pull` | 없으면 당겨 받기를 하지 않는다(`skipPull`). 있으면 `{ afterUpdatedAt: number, afterLogId: string, limit: number }`에서 시작하는 한 페이지를 받는다. 서버는 `limit`을 25~`MAX_PAGE_ROWS`(기본 500) 범위로 자른다. 그래서 오래된 앱이 더 큰 값을 보내도 서버 설정을 넘지 않는다. |

- **올리기 결과 분류:** 쓰기를 확정한 뒤, 보낸 기록 id의 서버 행을 다시 읽는다(`SELECT log_id, client_updated_at, deleted_at, raw_json FROM logs WHERE family_id = ?1 AND log_id IN (…)`). D1은 쿼리 하나에 바인딩 매개변수를 100개까지 받으므로 id는 99개씩 나눠 한 배치로 읽는다. 행마다 아래처럼 분류한다.
  - 서버 행의 `raw_json`이 보낸 기록의 canonical JSON과 같으면 받아들여진 것이다. `acceptedIds`에 넣는다.
  - 서버 행이 삭제됐으면 `remoteDeletedIds`에 넣는다.
  - 그 밖(서버가 더 새 버전이거나 타이브레이커에서 졌음)이면 서버 행을 `remoteLogs`에 넣는다.
  - 이 분류는 `skipPull` 요청에서도 똑같이 한다. 그래서 `skipPull` 묶음에서도 밀린 기록이 사라지지 않는다(`05` 8.4 경미 11).
- **당겨 받기 페이지:** `pull`이 있으면 아래 쿼리로 한 페이지를 읽는다.

  ```sql
  SELECT log_id, updated_at, deleted_at, raw_json FROM logs
  WHERE family_id = ?1 AND (updated_at, log_id) > (?2, ?3)
  ORDER BY updated_at, log_id
  LIMIT ?4;  -- pull.limit + 1
  ```

  - 페이지 크기는 `pull.limit`(기본 500행)이다. `limit + 1`번째 행이 있으면 `hasMore: true`이고, `nextAfter`는 페이지 마지막 행의 `(updated_at, log_id)`다.
  - 페이지의 `raw_json` UTF-8 바이트 수 합이 800KB(819,200바이트)에 이르면 그 행까지만 담고 `hasMore: true`로 끊는다. 긴 메모가 섞여도 응답이 1MB를 넘지 않아 클라이언트 요청 상한(10초, `cloudClient.ts:43`) 안에 받을 수 있다.
  - 전체 모드는 `(0, '')`에서 시작한다. 그래서 전체 모드의 정렬도 `client_updated_at`(`index.ts:369`)이 아니라 같은 키다.
  - 인덱스를 `idx_logs_family_updated_log ON logs (family_id, updated_at, log_id)`로 바꾼다. 옛 인덱스 `idx_logs_family_updated`는 스키마에서 뺀다(D1이 아직 없으므로 `DROP`은 필요 없다).
  - `logs` 테이블은 `WITHOUT ROWID`로 만든다. 복합 TEXT 기본 키를 쓰는 보통 테이블은 기본 키용 `sqlite_autoindex`를 따로 두므로 새 행 하나가 테이블, 자동 인덱스, 위 인덱스에 3행을 쓴다. `WITHOUT ROWID` 테이블은 기본 키 순서로 저장되어 자동 인덱스가 없으므로 2행을 쓴다. 3판을 쓰면서 `node:sqlite`(SQLite 3.51)로 확인한 결과, 자동 인덱스가 생기지 않고, 2.3·2.4의 upsert 변경 행 수와 위 페이지 쿼리의 인덱스 사용이 바뀌지 않았다. D1에서 받아들이는지는 5.3의 `wrangler dev --local`로 확인한다.
- **CPU 절약:** 당겨 받기 응답은 `raw_json`을 `JSON.parse`하지 않는다. 응답 본문의 `remoteLogs` 배열은 저장된 canonical JSON 문자열을 쉼표로 이어 붙여 만든다. `supersededIds`를 구하려고 받은 행을 모두 파싱하던 코드(`index.ts:401-417`)은 없앤다.
- **커서 후보 (결함 6):** 응답에는 `cursorCandidate = (당겨 받기 쿼리 직전의 now(env)) - 120000`(2분 전)을 넣는다. 다른 요청이 그보다 이른 시각으로 늦게 확정한 행도 다음 당겨 받기에 들어온다. 다시 받는 행은 클라이언트 병합이 중복을 처리한다.
  - **전제:** 배치 하나가 시각을 찍은 뒤 2분 안에 확정된다. 2.3에서 시각을 배치마다 찍으므로, 여유가 덮어야 하는 것은 요청 전체가 아니라 배치 하나의 확정 시간이다. D1 배치 하나는 100문장 이하라서 이 전제는 넉넉하다.
- **응답:**

  | 필드 | 뜻 |
  |---|---|
  | `acceptedIds` | 보낸 기록 가운데 서버 행과 내용이 같은 id |
  | `remoteLogs`, `remoteDeletedIds` | 올리기 분류 결과와 당겨 받은 페이지를 합친 것 |
  | `remoteProfile` | 쓰기 확정 뒤의 아기 정보. `shared_json`이 NULL이면 빠진다(2.3) |
  | `profileRejected` | 보낸 아기 정보가 형식 검사에 실패했을 때만 `true` |
  | `hasMore`, `nextAfter`, `cursorCandidate` | `pull`이 있을 때만 |
  | `maxPushItems`, `maxPageRows` | 서버가 받아들이는 묶음 건수와 페이지 행 수의 상한. 기본값은 400건, 500행이고 `wrangler.toml`의 변수 `MAX_PUSH_ITEMS`, `MAX_PAGE_ROWS`로 바꿀 수 있다. 앱을 새로 출시하지 않고 Worker 설정만 바꿔 줄일 수 있도록 응답에 싣는다(2.6.2). 서버의 요청 한도(500건, 1MB)는 이 값과 별개로 그대로 둔다 |

- **본문 크기:** `content-length` 헤더가 없을 수 있으므로, 서버는 `request.text()`로 읽은 본문의 UTF-8 바이트 수(`new TextEncoder().encode(text).length`)도 1MB와 비교한다. 지금은 헤더만 본다(`index.ts:76-79`).
- **바이트 단위 통일:** 이 문서의 KB와 MB는 모두 UTF-8 바이트 기준이다(1KB = 1,024바이트). 한글 한 글자는 JavaScript 문자열 길이로 1이지만 UTF-8로 3바이트라서, 문자열 길이로 재면 한글 메모가 많은 묶음이 서버 기준 1MB를 넘을 수 있다. 클라이언트는 2.6의 5단계에서 `src/utils/utf8.ts`의 `utf8ByteLength(text)`로 잰다. 이 함수는 코드 포인트를 직접 세므로 `TextEncoder`가 없는 런타임에서도 같은 값을 낸다. 단위 검사로 Node의 `Buffer.byteLength`와 같은 값인지 확인한다(한글, 이모지, 짝 없는 서로게이트 포함. 짝 없는 서로게이트는 `TextEncoder`처럼 U+FFFD의 3바이트로 센다).
- **쿼리 수:** 무료 등급은 Worker 호출 하나에 D1 쿼리 50회까지이고, `db.batch()`는 묶음 전체가 1회로 센다. 올리기 400건 요청은 가족 읽기 1, 쓰기 배치 4~5(토큰 갱신 문장 포함, 2.3), 분류 읽기 배치 1(아기 정보 읽기 포함)로 7회 안쪽이다. 올리기 요청은 `pull`을 싣지 않으므로 당겨 받기 쿼리가 없고, 당겨 받기 요청은 가족 읽기 1, 당겨 받기와 아기 정보 읽기 배치 1로 2회다.

### 2.6 클라이언트: 나눠 보내기와 장부 (결함 1, 2, 3)
`syncWithCloud`(`sync.ts:132-351`)의 한 회차를 아래 순서로 바꾼다.

1. **연결:** 지금처럼 필요할 때만 `connectFamily`를 부른다. 410이면 `familyUnavailable: true`, 404면 `familyNotFound: true`를 돌려준다(2.7).
   - **회차의 기대 키:** 회차를 시작할 때 저장된 `syncKey`(가족 만들기와 합류에서는 `null`)를 `startKey`로 둔다. 첫 저장이 성공하기 전에는 저장된 키가 `startKey`이거나 이 회차의 키일 때만 저장한다. 첫 저장이 성공한 뒤에는 이 회차의 키일 때만 저장한다. 그래서 같은 회차의 두 번째 페이지나 묶음이 "키가 바뀌었다"며 거부되지 않고, 회차 도중 사용자가 연결을 해제하면(저장된 키가 없어짐) 다음 저장이 거부되어 연결이 되살아나지 않는다.
2. **장부 읽기:** 새 키 `@baby_sync_ledger_cf_v1`을 읽는다. 옛 키 `@baby_sync_ledger_v1`은 읽지도 지우지도 않는다(단계 B가 쓴다).
3. **모드 결정:** 장부가 없거나, `forceFullRead`이거나, `lastFullReadAt`이 6시간보다 오래됐거나, `full`(진행 중인 전체 모드)이 있으면 전체 모드다.
   - `full`이 이미 있으면 `forceFullRead`여도 처음부터 다시 시작하지 않고 `full.after`부터 이어 간다. 이어 가도 전체 대조의 결과는 같고, 이미 받은 페이지를 다시 읽지 않는다.
   - 새로 전체 모드를 시작할 때는 `full = { after: (0, ''), uploaded: {}, tombstoned: [] }`를 만들고, 남아 있는 `pullAfter`, `pullCursorAtStart`를 지운다.
4. **전체 모드 당겨 받기:** `full.after`(처음은 `(0, '')`)부터 페이지를 받는다. 페이지마다 2.6.1의 원자적 저장으로 기록을 합치고, `full.uploaded`, `full.tombstoned`, `full.after`를 갱신한다. 첫 페이지의 `cursorCandidate`는 `full.cursorAtStart`에 한 번만 적는다. `hasMore`가 거짓이면 `uploaded`, `tombstoned`를 `full`의 값으로 바꾸고, `cursorMillis = full.cursorAtStart`, `lastFullReadAt = Date.now()`로 정한 뒤 `full`을 지운다.
   - 페이지 크기는 `limits.pull`(2.6.2)이다.
   - **시간 예산:** 회차를 시작하고 6초가 지나면 새 페이지를 요청하지 않고 5단계로 넘어간다. 남은 페이지는 다음 회차가 `full.after`부터 이어 받는다. 20초 상한(`App.tsx:36`) 안에 올리기 시간을 남겨 두려는 것이다. 회차 전체의 시간 예산은 아래 "회차 시간 예산"에 적는다.
   - **페이지 요청 실패:** 2.6.2의 실패 처리 규칙을 따른다. 당겨 받기가 실패해도 네트워크 끊김이 아니면 5단계 올리기는 한다.
   - 회차의 첫 요청에는 모드와 상관없이 `pushProfile`을 싣는다. 전체 모드라면 첫 당겨 받기 요청이 첫 요청이다.
5. **올리기:** 매 묶음마다 저장소에서 기록과 프로필을 새로 읽고, 아래 항목을 고른다.
   - 기록: `uploaded[id] !== (updatedAt || timestamp)`인 것
   - 삭제 id: `deletedLogIds` 가운데 `tombstoned`에 없는 것
   - 고른 항목을 `limits.push`건(2.6.2, 기본 400건) 이하, 직렬화 크기 900KB(`utf8ByteLength`로 잰 UTF-8 바이트, 2.5) 이하로 자른 묶음 하나를 `pull` 없이 보낸다. 회차의 첫 요청에는 `pushProfile`을 싣는다.
   - 응답을 2.6.1의 원자적 저장으로 반영하고, 남은 항목이 없을 때까지 반복한다. 한 회차의 묶음 수는 20개로 제한하고, 남으면 다음 회차가 이어 간다.
   - **회차 시간 예산:** 회차를 시작하고 8초가 지나면 종류와 상관없이 새 요청을 시작하지 않는다. 요청 하나의 상한이 10초(`cloudClient.ts:43`)라서, 8초 전에 시작한 마지막 요청은 18초 안에 끝나고, 20초 상한까지 2초가 남아 그 응답의 원자적 저장을 마칠 수 있다. 그래서 큰 첫 올리기도 상한에 걸려 오류로 끝나지 않고, 저장을 마친 묶음까지 반영한 채 회차를 끝낸다.
     - **기준점:** "회차를 시작한 때"는 러너(2.11)가 `withSyncDeadline`으로 상한을 거는 시점이다. 러너는 그 시각을 `syncWithCloud`의 선택 인자 `startedAt`으로 넘기고, `syncWithCloud`는 백업과 connect에 쓴 시간까지 예산에 넣는다. 4단계의 6초 예산도 같은 기준점에서 잰다. `startedAt`이 없으면(러너를 거치지 않는 호출) `syncWithCloud`에 들어온 시각을 쓴다.
     - **2초 안에 저장이 끝나지 않으면:** 상한이 와서 `aborted`가 켜지므로 대기열에서 아직 시작하지 않은 `applySyncResponse`는 저장하지 않는다. 서버에는 이미 반영된 묶음이라서 다음 회차가 그 항목을 다시 올리고, 서버는 같은 버전을 쓰지 않는다(2.3). 손실이 아니라 요청 하나의 낭비다.
   - **이어 가기 표시:** 시간 예산, 20묶음 상한, 전체 모드 미완료 때문에 할 일이 남은 채 회차를 끝내면 결과에 `continuing: true`를 싣는다. 오류나 `uploadStalled`로 끝난 회차에는 싣지 않는다. 다음 회차를 누가 언제 부르는지는 2.11에 적는다.
   - **진전 표시:** 결과에 `progressed: boolean`을 싣는다. 이 회차에서 `applySyncResponse`가 저장을 한 번이라도 마쳤으면(기록, 프로필, 장부 가운데 하나라도 바뀌었으면) 참이다. 크기 조절(2.6.2)만 저장한 경우는 진전으로 치지 않는다. 러너는 이 값으로 이어 가기를 판정한다(2.11의 6번).
   - **전체 모드가 끝나지 않은 회차:** 4단계를 마쳤는지와 상관없이 올린다. 항목은 기존 장부(`uploaded`, `tombstoned`)와 비교해 고르고, 응답에서 확인한 항목은 기존 장부와 `full.*` 양쪽에 적는다. 기존 장부가 없으면(처음 전체 모드) 모든 항목이 차이로 잡힌다. 그래서 큰 가족의 전체 대조가 여러 회차에 걸쳐도 새 기록은 바로 올라가고, 전체 대조가 끝난 회차에 올리는 것도 차이뿐이다(`05` 2.7-7). 서버에 더 새 버전이나 삭제 표식이 있는 항목을 올려도 2.3·2.4의 조건 때문에 서버 행은 바뀌지 않고, 분류 응답으로 서버 값이 돌아온다.
   - **큰 항목:** 직렬화 크기가 900KB를 넘는 기록 하나는 묶음에 넣지 않는다. 회차 결과에 `oversizedIds`로 알리고, 동기화 상태에 "공유하지 못한 기록이 있습니다(너무 큼)"를 보여 준다. 그 기록은 기기에 그대로 있고, 다른 기록의 올리기를 막지 않는다.
   - **진전 없음 중단:** 묶음의 응답을 반영한 뒤 장부(`uploaded`, `tombstoned`, 전체 모드면 `full.*`)에 새로 적힌 항목이 하나도 없으면, 그 묶음의 id를 이 회차의 제외 목록에 넣고 남은 항목으로 다음 묶음을 고른다. 제외 목록은 저장하지 않으므로 다음 회차에 다시 시도한다. 진전 없는 묶음이 한 회차에 두 번 나오면 올리기를 멈추고 회차 결과에 `uploadStalled: true`를 싣는다. 비교 규칙이 조금만 어긋나도 같은 묶음을 20번 보내는 일을 막는다. 화면은 이 회차를 성공으로 표시하지 않고 동기화 상태에 "일부 기록을 올리지 못했습니다. 다음 동기화 때 다시 시도합니다."를 보여 준다. 이 회차는 `continuing`을 싣지 않으므로 곧바로 다시 돌지 않고, 다음 저장이나 폴링 때 다시 시도한다(2.11).
   - 동기화 뒤 삭제 재전송 호출(`sync.ts:287-295`)은 없앤다. 응답을 기다리는 동안 생긴 삭제는 다음 묶음을 고를 때 저장소에서 다시 읽히므로 같은 회차에 올라간다.
6. **증분 당겨 받기:** 전체 모드인 회차(4단계를 마쳤든 시간 예산으로 끊겼든)는 건너뛴다. 그 밖에는 `pull`(처음은 `(cursorMillis, '')`, 끊긴 적이 있으면 `pullAfter`)부터 `hasMore`가 거짓일 때까지 `limits.pull`행씩 받는다. 이 요청이 회차의 첫 요청이면 `pushProfile`을 싣는다. 페이지마다 2.6.1로 저장하고 `pullAfter`를 적는다.
   - `pullCursorAtStart`는 **값이 없을 때만** 그 페이지의 `cursorCandidate`로 적는다. 끊겼다가 이어 받는 회차의 첫 페이지는 이 값을 덮어쓰지 않는다. 덮어쓰면 원래 커서와 `pullAfter` 사이에 늦게 확정된 행이 빠진다.
   - 마지막 페이지를 받으면 `cursorMillis = pullCursorAtStart`로 정하고 `pullAfter`, `pullCursorAtStart`를 지운다.
   - 전체 모드의 `full.cursorAtStart`도 같은 규칙(값이 없을 때만 적는다)을 따른다.
   - 뒤 페이지의 커서 후보를 쓰지 않는 이유: 첫 페이지 이후 늦게 확정된 행이 첫 페이지 범위에 들어갈 수 있기 때문이다.
7. 요청 사이마다 `abortToken`을 확인한다. 중단되면 그때까지 저장한 페이지와 장부는 그대로 두고 돌아간다.

#### 2.6.1 원자적 저장과 장부 기록 규칙
- `storage.ts`에 `applySyncResponse(...)`를 새로 둔다. 이 함수는 `runStorageWrite` 대기열 안에서 아래를 한 번에 한다.
  1. 지금 저장된 기록과 프로필을 읽고, `remoteLogs`, `remoteDeletedIds`, `remoteProfile`을 지금의 `saveSyncedDataWithoutLoss`와 같은 규칙으로 합친다. 가족 키 확인(`expectedStoredSyncKey`)과 `abortToken` 확인도 같다.
     - **원격 아기 정보 검사:** `remoteProfile`은 공유 항목 4개가 모두 있고 형식이 2.3의 서버 검사와 같을 때만 비교 대상으로 삼는다. 하나라도 빠지거나 형식이 다르면 `remoteProfile`이 없는 것으로 본다. 이 검사는 순수 함수 `isCompleteSharedProfile(value)`로 `src/database/syncDecision.ts`에 두고 단위 검사한다. 지금 `sync.ts:263-266`의 `val !== undefined` 가드가 하던 일을 이 검사가 대신한다. 비교 전에 걸러 내므로, 빈 객체나 일부 항목만 있는 값이 같은 시각의 타이브레이커에서 이겨 이름을 기본값으로 바꾸는 일이 없다.
  2. 합친 결과를 보고 장부 항목을 정한다.
     - **받은 기록:** `remoteLogs`의 각 기록이 합친 결과의 같은 id 기록과 canonical JSON까지 같으면 `uploaded[id] = 그 기록의 updatedAt || timestamp`를 적는다. 다르면(기기 쪽이 더 새 버전) 적지 않으므로 다음 묶음에서 올라간다.
     - **보낸 기록:** `acceptedIds`의 각 id에 대해, 합친 결과의 기록이 보낸 기록과 canonical JSON까지 같으면 보낸 기록의 시각을 적는다. 요청 중에 사용자가 그 기록을 고쳤으면 적지 않는다.
     - **삭제:** 보낸 삭제 id와 `remoteDeletedIds`는 `tombstoned`에 넣는다. 서버의 삭제 표식 upsert(2.4)는 행이 없어도 표식을 남기므로, 응답이 성공했으면 서버에 표식이 있다.
     - 그 밖의 id(요청 중에 새로 생긴 기록이나 삭제)는 적지 않는다.
  3. 기록, 프로필, 장부를 `AsyncStorage.multiSet` 한 번으로 저장한다. 그래서 앱이 저장 도중 종료돼도 기록과 장부가 어긋나지 않는다.
- 기대 키 확인(2.6의 1단계)에 실패하면 아무것도 저장하지 않고 회차를 끝낸다.
- 장부 정리 규칙은 지금 `writeSyncLedger`(`storage.ts:427-447`)와 같다. 기기에 없는 기록의 `uploaded` 항목은 버린다.
- 전체 모드 진행 중에는 2번의 항목을 기존 장부(`uploaded`, `tombstoned`)와 `full.uploaded`, `full.tombstoned` **양쪽에** 적는다. 당겨 받은 페이지의 항목도, 올리기 응답의 항목도 같다. 두 경우 모두 서버에 있다고 방금 확인한 내용이므로 기존 장부에 적어도 불변 조건 6을 지킨다. 페이지로 받은 기록을 `full.*`에만 적으면, 새로 합류한 기기가 같은 회차의 5단계에서 받은 기록 전체를 차이로 골라 다시 올린다(서버 쓰기는 0이지만 읽기와 시간을 쓴다).
- 전체 모드가 끝날 때 기존 장부를 `full.*`로 바꿔 끼우므로, 서버에서 사라진 기록(데이터베이스 교체 등)은 다음 올리기에서 다시 올라간다. 기존 장부에만 있고 `full.*`에 없는 항목이 이때 빠진다.
- 새 장부 키는 지금 옛 키를 지우는 두 곳에서도 지운다: `storage.ts:522`(데이터 가져오기)와 `storage.ts:580`(백업 복원). 옛 키를 지우는 동작은 그대로 둔다.

새 장부 형식:

```ts
interface CloudSyncLedger {
  familyKey: string;
  cursorMillis: number;            // 증분 당겨 받기 시작점
  lastFullReadAt: number;          // 마지막 전체 모드 완료 시각(기기 시각)
  uploaded: Record<string, number>; // 서버에 있다고 확인한 기록 id → updatedAt
  tombstoned: string[];            // 서버에 표식이 있다고 확인한 삭제 id
  pullAfter?: { updatedAt: number; logId: string };
  pullCursorAtStart?: number;
  limits?: {                       // 2.6.2. 없으면 기본값
    push: number; pull: number;
    pushStreak: number; pullStreak: number; // 연속 성공 횟수
    serverPush?: number; serverPull?: number; // 마지막으로 받은 서버 힌트
  };
  full?: {
    after: { updatedAt: number; logId: string };
    cursorAtStart?: number;
    uploaded: Record<string, number>;
    tombstoned: string[];
  };
}
```

- 형식 검사에 실패하면 장부가 없는 것으로 보고 전체 모드로 돈다(불변 조건 6).
- AsyncStorage 용량(약 6MB)에서 장부가 차지하는 양은 기록 3,000건 기준 약 150KB다. `full`이 있는 동안은 두 배까지 늘 수 있다.

#### 2.6.2 요청 크기 조절
묶음과 페이지 크기를 앱 상수로만 두면, CPU 한도 초과나 느린 망 때문에 실패하는 요청을 앱을 새로 배포하기 전까지 같은 크기로 반복하게 된다. 그러면 결함 1의 영구 정지가 다른 모양으로 다시 생긴다. 그래서 크기를 기기마다 조절한다.

- 장부에 `limits: { push: number, pull: number }`를 둔다. 기본값은 `push = 400`, `pull = 500`이고, 하한은 둘 다 25다.
- 실제로 쓰는 크기는 `min(장부 값, 서버 힌트)`다. 서버 힌트는 응답의 `maxPushItems`, `maxPageRows`이고, 받을 때마다 장부의 `limits.serverPush`, `limits.serverPull`에 저장한다. 그래서 다음 회차의 첫 요청도 서버 설정을 따른다. 서버 상수를 낮춰 배포하면, 각 기기는 낮춘 뒤 받은 첫 응답부터 따른다. 그 전에 나간 요청 하나는 서버가 2.5의 요청 한도와 `pull.limit` 자르기로 막는다.
- 같은 종류의 요청이 연속 10번 성공하면 크기를 두 배로 늘린다. 늘린 값은 기본값과 저장된 서버 힌트를 모두 넘지 않는다. 그래서 서버 힌트가 기본값보다 낮을 때 두 배로 늘렸다가 실패하는 회차가 생기지 않는다. 성공 횟수는 장부의 `limits`에 함께 적는다.
- **실패 처리 규칙:** 실패 종류에 따라 크기와 다음 단계를 아래처럼 정한다. 크기를 바꾸면 장부에 바로 저장한다.

  | 실패 | 크기 | 같은 회차의 다음 단계 |
  |---|---|---|
  | 413, 5xx(CPU 한도 초과 503과 1102 포함), 요청 시간 초과(`cloudClient.ts:43`의 10초) | 그 종류의 크기를 절반으로(하한 25) | 당겨 받기가 실패했으면 남은 당겨 받기를 건너뛰고 올리기는 한다. 올리기가 실패했으면 남은 올리기와 6단계를 건너뛴다 |
  | 네트워크 끊김(`TypeError`) | 그대로 | 회차를 끝낸다. 다음 요청도 실패할 것이기 때문이다 |
  | 404, 410 | 그대로 | 회차를 끝내고 2.7대로 처리한다 |
  | 그 밖의 4xx | 그대로 | 그 종류의 남은 요청을 건너뛴다. 다른 종류의 요청은 한다 |

  - 증분 회차의 순서는 5단계(올리기) 뒤 6단계(당겨 받기)이므로, 당겨 받기 실패는 이미 끝난 올리기에 영향을 주지 않는다. 전체 모드 회차는 4단계(당겨 받기) 뒤 5단계(올리기)이므로 위 규칙 덕분에 당겨 받기가 실패해도 새 기록은 올라간다.
  - 회차의 결과는 실패가 하나라도 있으면 실패이고, 오류 문장은 첫 실패의 것을 쓴다.
- **하한에서 시간 초과:** 크기가 하한 25인데 당겨 받기가 시간 초과로 실패하면, 페이지 하나의 행이 커서(긴 메모 몇 개로 800KB 가까이) 느린 망에서 10초 안에 받지 못하는 경우다. 크기를 줄여도 풀리지 않으므로 결과에 `pullTooSlow: true`를 싣고, 동기화 상태에 "네트워크가 느려 기록을 받지 못했습니다. 와이파이에서 다시 시도해 주세요."를 보여 준다. 다음 회차는 같은 지점부터 다시 시도한다. 올리기가 하한에서 실패하면 지금처럼 오류를 보여 주고, 그 묶음은 다음 회차에 다시 시도한다.
- 이 조절은 `syncDecision.ts`의 순수 함수 `nextLimits(limits, outcome)`와 `nextStepAfterFailure(stage, failure)`로 만들어 단위 검사한다.

#### 2.6.3 가족 만들기와 합류의 시간 상한
- 가족 만들기와 합류도 20초 상한(`App.tsx:36`) 안에서 돈다. 기록이 많으면 첫 저장 뒤에 상한에 걸릴 수 있다. 그때 키는 이미 저장됐는데 화면은 "가족 연결 실패"를 띄우고 초대 링크 공유를 건너뛴다(`Profile.tsx:316-331`).
- "키가 저장소에 있으면 연결 확정"으로 정한다. 판정은 상한이 온 시점의 기억 값이 아니라 저장소에 실제로 남은 값으로 한다.
  - 진행 상태 플래그로 판정하면 경쟁 구간이 생긴다. `withSyncDeadline`(`syncDeadline.ts:13-16`)은 상한이 오면 곧바로 `aborted`를 켜고 대체 결과를 돌려준다. 그 순간 저장 대기열 안의 `multiSet`이 이미 진행 중이면, 키는 결국 저장되는데 화면은 연결 실패를 띄운다.
- `storage.ts`에 `readProfileAfterPendingWrites()`를 둔다. 이 함수는 `runStorageWrite` 대기열에 읽기 작업을 넣어, 앞서 시작한 저장이 모두 끝난 뒤 프로필을 읽는다. 대기열에 있지만 아직 시작하지 않은 `applySyncResponse`는 `aborted`를 보고 저장하지 않으므로, 이 읽기 결과가 최종 상태다.
- 상한 처리(지금 `App.tsx:212-218`)는 2.11의 `syncRunner.ts`로 옮긴다. `connecting`이면 대체 결과를 곧바로 쓰지 않는다. 대신 `readProfileAfterPendingWrites()`를 기다려 저장된 `syncKey`가 이 회차의 키와 같은지 본다. 같으면 `success: true`, `continuing: true`를 돌려준다. 그러면 `Profile.tsx`가 키를 정하고 초대 링크를 공유한다. 러너는 `continuing` 규칙(2.11)에 따라 평소 동기화를 이어서 요청해 남은 페이지와 묶음을 처리한다.
- 회차 시간 예산(2.6의 5단계) 덕분에 보통은 상한 전에 회차가 `continuing: true`로 끝난다. 상한 뒤 판정은 요청이 10초 상한까지 늘어질 때 연결 결과를 바로잡는 안전장치다.
- **상한 아닌 실패에도 같은 판정 (5판):** 연결 회차가 첫 저장으로 키를 저장한 뒤 다른 페이지나 묶음이 실패하면, 2.6.2의 "실패가 하나라도 있으면 회차는 실패" 규칙 때문에 `syncWithCloud`는 `success: false`를 돌려준다. 이 결과를 그대로 넘기면 `Profile.tsx:316-331`이 "가족 연결 실패"를 띄우고 초대 링크 공유를 건너뛰는데, 키는 이미 저장돼 있다. 그래서 러너는 `connecting` 회차가 실패로 끝나면, 실패 종류와 상관없이 위와 같이 `readProfileAfterPendingWrites()`로 저장된 키를 읽어 판정한다. 키가 이 회차의 키와 같으면 `success: true, continuing: true`를 돌려준다. 남은 일은 이어 요청한 평소 동기화가 처리하고, 그 회차가 실패하면 평소처럼 오류를 보여 준다.
  - **예외:** 410(`familyUnavailable`)과 404(`familyNotFound`)는 이 판정을 하지 않고 실패로 돌려준다. 410은 2.7대로 키를 저장하지 않거나 지운다. 404는 서버에 가족이 없다는 뜻이므로 연결을 확정하면 안 된다. 첫 저장 뒤 404가 오는 경우(연결 도중 데이터베이스 교체)는 저장된 키가 남지만, 불변 조건 3에 따라 앱이 스스로 끊지 않고 다음 평소 동기화가 404 오류를 보여 준다.
  - **판정 위치:** 이 판정과 상한 뒤 판정은 `syncDecision.ts`의 `decideAfterSync(result, context)`에 넣는다. `context`에는 `connecting`, `timedOut`, 그리고 러너가 읽은 `storedKeyMatches`(저장된 키가 이 회차의 키와 같은지)를 담는다. 러너는 `connecting` 회차가 실패하거나 상한에 걸렸을 때만 `readProfileAfterPendingWrites()`를 불러 `storedKeyMatches`를 채운다. 그래서 평소 회차에는 읽기가 늘지 않는다.
- 저장된 키가 다르거나 없으면 지금처럼 실패로 돌려준다. 이때는 키가 저장되지 않았으므로 다시 시도하면 된다.

### 2.7 클라이언트: 404와 410 처리 (결함 7, 불변 조건 3)
- `syncWithCloud`의 결과에 `familyNotFound?: boolean`을 더한다. 410이면 `familyUnavailable: true`, 404면 `familyNotFound: true`이고 둘은 함께 오지 않는다.
- `App.tsx:254-269`의 연결 해제는 `familyUnavailable`일 때만 일어난다. 이 부분의 조건은 지금과 같고, `familyUnavailable`의 뜻만 410으로 좁아진다.
- 404는 동기화 상태를 오류로 두고 "서버에서 가족 정보를 찾지 못했습니다. 기록은 이 기기에 그대로 있습니다."를 보여 준다. 가족 합류(`connecting`)에서는 지금처럼 합류 실패로 처리하고, 메시지는 "초대 정보를 찾지 못했습니다. 초대 링크를 다시 받아 주세요."다.
- 가족 합류 중 410을 받으면 키를 저장하지 않고 합류 실패로 처리한다. 메시지는 "이 가족 공유는 영구 삭제되었습니다. 새 초대 링크를 받아 주세요."다. 가족 만들기(`allowCreate: true`)에서 410을 받는 경우는 삭제된 가족과 같은 키를 다시 쓸 때뿐이며, 이때도 키를 저장하지 않고 같은 문장을 보여 준다.
- `describeSyncError`(`sync.ts:99-110`)는 404와 410을 다른 문장으로 구분한다.
- 변경 토큰 폴링(`subscribeToCloudChanges`)은 410을 받으면 폴링을 멈추고, 오류 객체에 `status: 410`을 실어 `onError`를 부른다. `App.tsx`의 `onError` 처리는 410이면 재연결 대신 평소 동기화를 한 번 요청한다. 그 동기화가 410을 받아 연결을 끊는다. 404는 지금처럼 재연결 간격(최대 60초)을 두고 다시 시도한다.
- **판정 함수 분리:** "동기화 결과 → 할 일"(연결 해제, 오류 표시, 성공, 이어 가기)과 "토큰 오류 → 할 일"(재연결, 폴링 중지 후 동기화)의 판정은 `src/database/syncDecision.ts`의 순수 함수 `decideAfterSync(result, context)`와 `decideAfterTokenError(error)`로 뺀다. "동기화 결과 → 할 일"은 2.11의 러너가 부르고, 러너는 그 결과를 App의 화면 콜백으로 넘긴다. 하네스는 순수 함수를 단위 검사하고, 러너는 실제 서버 모드에서 실행한다(2.11).
- 가족 삭제 관련 함수(`sync.ts:360-425`)는 410을 "이미 삭제된 가족"으로 알려 준다. `deleteFamilyCloudData`는 410을 성공으로 본다(다른 기기가 먼저 지웠다).

### 2.8 평소 동기화 합치기 (결함 8)
- `App.tsx:160`의 조건을 `!createBackup && !allowFamilyCreation && !connecting && !forceFullRead`로 고친다. 이 조건은 2.11의 `syncRunner.ts`에 순수 함수 `isCoalescibleSync(options)`로 두고, 대기열과 합치기 처리(지금 `App.tsx:137-296`의 `syncLatestData`)도 함께 옮긴다. 같은 가족 키의 평소 동기화가 이미 돌고 있으면 대기 중인 다음 회차 하나에 합쳐진다.
- 합쳐진 회차는 시작할 때 저장소를 새로 읽으므로(2.6의 5단계), 합치는 동안 들어온 기록도 그 회차에 올라간다.

### 2.10 실제 서버 코드로 도는 하네스 모드 (`05` 5.1)
실제 서버 모드는 Worker와 D1 흉내를 **HTTP 서버 프로세스 하나**로 띄우고, 기기마다 프로세스를 따로 띄워 그 서버에 요청하게 한다(아래 "방식 선택"의 방식 B).

#### 방식 선택: 방식 B (서버 프로세스와 기기 프로세스)
2차 검토는 한 프로세스 안에서 두 기기를 흉내 낼 수 없다고 지적했다. async-storage 흉내의 전역 `mem`과 `HARNESS_STORAGE_FILE`(`stubs/async-storage.mjs:4-14`), `cachedClientId`(`sync.ts:18`), `readyFamilyKeys`(`sync.ts:130`), `storageWriteQueue`(`storage.ts:15`)가 모두 모듈 수준 상태라서 두 기기가 함께 쓰게 된다. 대안 두 가지를 비교해 방식 B를 고른다.

| | 방식 A: 기기마다 모듈을 다시 불러오기 | 방식 B: 서버와 기기를 프로세스로 나누기 |
|---|---|---|
| 기기 상태 분리 | loader가 기기 표시를 모든 하위 import와 흉내 모듈에 빠짐없이 넘겨야 한다. 앞으로 모듈 상태가 하나 더 생기거나 표시가 한 곳에서 빠지면, 두 기기가 상태를 공유한 채 **오류 없이** 시험이 통과한다. | 프로세스가 다르면 모든 모듈 상태와 `Date.now`가 저절로 분리된다. 새 모듈 상태가 생겨도 따로 할 일이 없다. |
| 기존 자산 | 새로 만든다. | `run.mjs`와 `device.mjs`가 이미 기기마다 프로세스를 띄우고 줄 단위 JSON으로 명령한다(`run.mjs:19-60`). 이 구조를 그대로 쓴다. |
| 운영과의 차이 | `fetch`를 함수 호출로 바꿔치기하므로 HTTP 직렬화와 `content-length` 처리를 거치지 않는다. | 실제 HTTP 요청이 오가므로, 2.5의 본문 크기 검사(`content-length`가 없는 경우 포함)와 응답 문자열 이어 붙이기를 운영과 같은 경로로 검사한다. |
| 강제 종료 | 같은 프로세스 안에서 중단 토큰으로만 흉내 낸다. | 기기 프로세스를 `SIGKILL`로 끝내고 같은 저장 파일로 다시 띄워, 실제 앱 강제 종료와 같은 조건을 만든다(시나리오 9). |
| 비용 | 프로세스 1개 | 프로세스 3~4개. 훅과 시계를 제어 엔드포인트로 다뤄야 한다. |

방식 A가 실패하면 시험이 통과한 채로 지나가고, 실제로는 두 기기를 검사하지 못했다는 사실이 어떤 출력에도 드러나지 않는다. 그래서 더 위험하다. 방식 B의 비용(제어 엔드포인트와 프로세스 관리)은 구현 시간으로만 나타나므로 받아들인다.

#### 서버 프로세스 (`tools/sync-harness/real-server.mjs`)
- loader로 `server/src/index.ts`를 변환해 불러오고, Node `http` 서버를 `127.0.0.1`의 빈 포트에 띄운다. 첫 줄 출력으로 포트를 알린다. 요청마다 Node 요청을 `Request`로 바꿔 Worker의 `fetch(request, env)`를 부르고, 응답을 그대로 돌려준다.
- **D1 흉내:** Node 24의 `node:sqlite`로 `prepare`, `bind`, `first`, `all`, `run`, `batch`를 만든다. 메모리 DB에 `server/schema.sql`을 적용한다. `run()`과 `batch()` 결과에는 `meta.changes`를 담는다. `batch()`는 `BEGIN`~`COMMIT` 트랜잭션으로 돌리고, 실패하면 `ROLLBACK`한다. `BEGIN`부터 `COMMIT`까지는 `await` 없이 동기로 실행하므로, 다른 요청이 확정 전 행을 볼 수 없다. 바인딩 매개변수가 100개를 넘는 문장은 실제 D1처럼 오류를 낸다. Worker 호출 하나의 쿼리 수가 50회를 넘어도 오류를 낸다.
- **서버 시계 주입:** `Env`에 시험 전용 선택 필드 `clock?: () => number`를 둔다. 서버의 모든 `Date.now()`는 `now(env)`로 바꾸고, `now(env)`는 `env.clock`이 있으면 그 값을, 없으면 `Date.now()`를 쓴다. `wrangler.toml`에는 이 바인딩이 없으므로 운영에서는 항상 `Date.now()`다. 서버 프로세스는 `env.clock`을 제어 엔드포인트로 맞추는 값으로 준다.
- **제어 엔드포인트:** 경로는 `/__harness/`로 시작하고, 서버 프로세스가 Worker에 넘기기 전에 가로챈다. Worker 코드에는 이 경로가 없다.

  | 엔드포인트 | 하는 일 |
  |---|---|
  | `clock` | 서버 시계를 정하거나 진행한다(냉각 기간 1시간, 커서 여유 2분 시나리오) |
  | `hold` | 조건(`X-Client-Id`, 요청 종류: 올리기·당겨 받기·연결, 배치 종류: 쓰기·읽기)에 맞는 요청이나 배치를 멈추고 id를 돌려준다. 자동으로 풀릴 시간 `delayMs`를 주면 그 시간 뒤 저절로 풀린다(느린 서버 흉내). 배치는 **`BEGIN` 전**에 멈춘다. `node:sqlite`는 연결이 하나뿐이라서, `BEGIN` 뒤에 멈추면 다른 요청이 확정 전 행을 보게 되어 결함 6이 재현되지 않는다 |
  | `release` | 멈춘 요청이나 배치를 풀어 준다. 풀기 전에 시계를 앞서 찍어 두면, 멈춘 쪽이 이른 시각으로 늦게 확정하는 상황을 만든다 |
  | `fail` | 조건에 맞는 다음 배치를 `COMMIT` **전**에 실패시켜 `ROLLBACK`하거나(커밋 실패), `COMMIT` **뒤**에 예외를 던진다(확정 뒤 응답 실패, 시나리오 8-1). CPU 한도 흉내로 조건에 맞는 요청에 503을 돌려주는 종류도 둔다(시나리오 16) |
  | `state` | 서버 상태 조회 어댑터(아래)의 질의를 실행한다 |
  | `inject` | 상대 기기 없이 서버 행을 직접 넣거나 고친다(기존 회귀의 `state.docs.set` 대체) |
  | `wipe` | 기록만 지우거나(시나리오 14-1), 데이터베이스 전체를 비우거나(시나리오 11의 설정 오류 흉내), 저장해 둔 사본으로 되돌린다 |

#### 기기 프로세스 (`device.mjs`의 실제 서버 모드)
- `HARNESS_REAL_WORKER=1`이면 `device.mjs`는 `firebase`를 불러오지 않고, 시작할 때 `setCustomWorkerUrl('http://127.0.0.1:<포트>')`(`cloudConfig.ts:7`)를 부른다. 기기마다 `HARNESS_STORAGE_FILE`이 다르다.
- 명령을 더한다: 기록 추가·수정·삭제, `syncWithCloud` 실행(중단 토큰 포함), 저장소와 장부 읽기, 기기 시계 진행(`Date.now` 바꿔치기, 6시간 전체 대조 시나리오), 저장 고장 주입.
- **저장 고장 주입:** AsyncStorage 흉내(`stubs/async-storage.mjs`)에 훅 세 가지를 더한다. 저장 도중 앱이 종료되거나 저장이 늦어지는 상황을 흉내 낸다.
  - "N번째 쓰기 뒤 예외"와 "N번째 쓰기 직후 프로세스 종료"
  - "N번째 쓰기 지연": 그 쓰기를 파일에 반영하기 전에 멈추고, 기기 명령 `releaseWrite`가 올 때까지 기다린다. 시나리오 7-1의 "`multiSet` 도중 상한"을 만든다.
  - **세는 쓰기:** 훅을 걸 때 키 목록을 함께 준다. 기본값은 기록 키 `@baby_logs`와 새 장부 키 `@baby_sync_ledger_cf_v1`이다. `setItem`, `multiSet`, `removeItem` 가운데 이 키를 하나라도 담은 호출만 센다. 그래서 백업(`@baby_local_backup`), 프로필만 바꾸는 쓰기, clientId 저장은 "첫 쓰기"에 들어가지 않는다.
- **러너 명령:** 기기 프로세스는 2.11의 `createSyncRunner`를 실제 `syncWithCloud`와 저장소 함수로 만들어 두고, `request`(평소 동기화, 가족 만들기, 합류, 새로고침 선택 포함)와 러너가 화면 콜백으로 넘긴 사건 목록 읽기를 명령으로 받는다. 상한은 명령마다 정할 수 있다(시나리오 7-1의 짧은 상한).
- **요청 상한 줄이기:** `cloudClient.ts`의 요청 상한(10초)과 2.6의 시간 예산(6초, 8초)은 모듈 상수로 두되, 시험 전용 설정 함수 `setSyncTimingForTests({ requestTimeoutMs, pullBudgetMs, cycleBudgetMs })`로 바꿀 수 있게 한다. 기기 프로세스는 시작할 때 이 값과 러너의 상한(`timeoutMs`, 20초)을 실제의 10분의 1로 줄여 시나리오 2, 16-b가 오래 걸리지 않게 한다. 비율을 그대로 두므로 "8초 전에 시작한 요청은 18초 안에 끝난다"는 관계도 그대로다. 앱 코드는 이 함수를 부르지 않는다.
- **같은 버전 재전송 명령:** 기기 명령 `forgetUploaded(ids?)`는 장부의 `uploaded`에서 주어진 id(없으면 전부)를 지운다. 다음 회차는 그 기록을 차이로 골라 서버에 같은 버전을 다시 보낸다. 시나리오 5에서 서버의 "같은 버전 무시"를 직접 시험하는 데 쓴다. 장부를 지우는 것은 불변 조건 6(장부는 힌트)이 허용하는 조작이다.
- **자기 검사:** 시나리오를 시작할 때 각 기기의 `getSyncClientId()`와 저장 파일 경로를 받아 서로 다른지 확인하고, 첫 연결 뒤 서버의 `members`에 서로 다른 `client_id`가 두 개 있는지 확인한다. 하나라도 같으면 시나리오를 실패로 끝낸다.

#### 서버 상태 조회 어댑터와 기존 회귀
- `regression.mjs`는 가짜 Worker의 내부 상태(`state.commits`, `state.docs`의 문서 경로)를 직접 검사한다. 이 검사를 어댑터로 바꾸고, 가짜 Worker용(같은 프로세스의 `state`)과 실제 서버용(`/__harness/state`) 두 구현을 둔다.
- 어댑터의 질의: 가족 존재와 삭제 기록, 기록 행 목록(살아 있는 행과 삭제 표식), 아기 정보와 토큰, 쓴 행 수와 읽은 행 수, 요청 목록(종류, `X-Client-Id`, `pull.after`, 묶음 건수, 응답 상태). 전체 모드와 증분 모드의 구별은 `pull.after`가 `(0, '')`인지로 한다.
- 어댑터의 조작: 시계 진행(냉각 기간 경과), 서버 행 직접 넣기, 요청 멈춤과 풀기, 실패 주입.
- 실제 서버 모드의 `regression.mjs`는 기기 하나만 쓰므로 회귀 스크립트 프로세스가 기기 역할을 하고, 서버만 따로 띄운다.
- 기존 검사 가운데 바꾸거나 없애는 것은 5.1의 시나리오 15에 적는다.

#### 집계와 실행
- D1 흉내는 읽은 행 수와 쓴 행 수를 센다. 쓴 행 수는 삽입과 갱신을 나눠 근사한다. 문장마다 실행 전후의 테이블 행 수 차이를 삽입 수로 보고, `meta.changes`에서 삽입 수를 뺀 값을 갱신 수로 본다.
  - 삽입 한 건은 `1 + 그 테이블의 인덱스 수`다. 인덱스 수는 `sqlite_master`에서 자동 인덱스까지 센다. 그래서 `logs`를 보통 테이블로 되돌리면 새 기록 하나가 2행이 아니라 3행으로 집계된다.
  - 갱신 한 건은 `1 + SET이 바꾸는 열을 담은 인덱스 수`다. 기본 키는 바꾸지 않으므로 자동 인덱스는 세지 않는다. 그래서 갱신은 보통 테이블이든 `WITHOUT ROWID`든 2행으로 같다(추측: D1의 실제 과금이 이 모형과 같은지는 배포 뒤 지표로 확인한다).
  - 읽은 행 수는 결과 행 수로 근사한다. 4장 예산과 시나리오 5·9의 판정에 쓴다. 요청마다 Worker 처리 시간도 적어 4장 CPU 참고값으로 남긴다.
- `verify.sh`에 `real` 모드를 더하고, `offline`은 `unit`, `regression`, `real`, `reminder`를 모두 돌린다. 판정 함수(2.7, 2.6.1의 `isCompleteSharedProfile`, 2.6.2의 `nextLimits`) 단위 검사는 `unit`에 넣는다.
- `real` 모드는 서버 1개와 기기 2~3개를 띄운다. ratchet 규칙대로 `ulimit -u` 상한 안에서 돌리고, 끝날 때 남은 자식 프로세스를 모두 끝낸다.

### 2.11 동기화 러너: App의 판정을 하네스가 실행하는 모듈로 옮긴다 (결함 8, 2.6.3)
3차 검토는 상한 뒤 연결 판정(2.6.3)과 평소 동기화 합치기(2.8)가 `App.tsx`에 남아, 하네스가 실제 코드로 돌릴 수 없다고 지적했다. 그러면 두 판정의 변이는 어떤 시나리오로도 실패시킬 수 없다. 그래서 `syncLatestData`(`App.tsx:144-296`)의 화면과 무관한 부분을 새 모듈 `src/database/syncRunner.ts`로 옮긴다.

- **경계:** 이 모듈은 `react`, `react-native`, `expo-*`를 불러오지 않는다. 저장소와 동기화 함수는 인자로 받는다. 그래서 하네스는 loader의 흉내 모듈 없이 이 파일을 그대로 불러온다.

  ```ts
  export interface SyncRequest {
    syncKey: string;
    createBackup?: boolean;
    allowFamilyCreation?: boolean;
    connecting?: boolean;
    forceFullRead?: boolean;
  }

  export interface SyncRunnerDeps {
    syncWithCloud: typeof import('./sync').syncWithCloud;
    getLogs(): Promise<BabyLogEntry[]>;
    getProfile(): Promise<BabyProfile>;
    saveProfile(profile: BabyProfile): Promise<boolean>;
    readProfileAfterPendingWrites(): Promise<BabyProfile>; // 2.6.3
    timeoutMs: number;                                       // App은 SYNC_TIMEOUT_MS(20초)
    onEvent(event: SyncRunnerEvent): void;                   // 화면 반영은 App이 한다
  }

  export function isCoalescibleSync(request: SyncRequest): boolean;  // 2.8
  export function createSyncRunner(deps: SyncRunnerDeps): {
    request(request: SyncRequest): Promise<SyncRunResult>;
    abortActive(): void;   // 지금 activeSyncAbortRef가 하던 일
  };
  ```

- **러너가 맡는 일:** 아래는 지금 `syncLatestData` 안에 있는 동작이고, 순서와 조건을 그대로 옮긴다. 바뀌는 것은 2.6.3, 2.7, 2.8에 적은 판정뿐이다.
  1. 가족 키별 대기열과 합치기(`isCoalescibleSync`, 지금 `pendingSyncByKeyRef`, `isSyncRunningRef`, `syncQueueRef`)
  2. 회차 시작 전 키 확인(지금 `App.tsx:183-197`)
  3. `withSyncDeadline`으로 상한 걸기와 상한 뒤 연결 판정(2.6.3)
  4. 회차 뒤 최신 기록과 프로필 다시 읽기, 가족이 바뀌었거나 해제됐는지 확인(지금 `App.tsx:219-245`)
  5. `decideAfterSync`(2.7)의 결과에 따라 410이면 `saveProfile`로 키를 지우기. 기록은 지우지 않는다
  6. **이어 가기:** 결과에 `continuing: true`와 `progressed: true`(2.6의 5단계)가 함께 있으면, 같은 키의 평소 동기화를 하나 더 요청한다(합치기 대상이라서 대기열이 늘지 않는다). 상한 뒤 판정이나 연결 회차 실패 판정(2.6.3)으로 `success: true, continuing: true`를 만든 경우는 저장된 키가 있다는 것 자체가 첫 저장을 마쳤다는 뜻이므로 `progressed: true`로 보고 이어 간다. 연속 이어 가기는 30회로 제한하고, 그 뒤에는 다음 저장이나 폴링이 이어 간다. 기록 1만 건 가족의 첫 올리기는 400건 묶음 25개라서 30회 안에 끝난다. 진전이 없는 회차는 이어 가지 않으므로, 같은 일을 끝없이 반복하지 않는다.
- **App에 남는 일:** `onEvent`로 받은 사건을 화면에 반영하는 일이다. 동기화 상태와 오류 문장, `lastSyncFailedRef`, 마지막 동기화 시각, 410 연결 해제 알림 창(`Alert`), 화면의 기록과 프로필 갱신이 여기에 해당한다. App은 러너를 `useRef`로 한 번만 만든다. 사건은 아래 다섯 가지다.

  | 사건 | App이 하는 일 |
  |---|---|
  | `started` | 동기화 상태를 `syncing`으로 |
  | `succeeded` | 상태 `idle`, 오류 지우기, 마지막 동기화 시각 기록 |
  | `failed` | 상태 `error`, 오류 문장 표시(404, `uploadStalled`, `pullTooSlow` 문장 포함), `lastSyncFailedRef = true` |
  | `disconnected` | 410으로 연결을 끊었다. 상태 `idle`, 프로필 갱신, 연결 해제 알림 창 |
  | `detached` | 회차 도중 사용자가 연결을 해제했거나 가족을 바꿨다. 상태 `idle`, 오류 지우기(지금 `App.tsx:227-245`) |

- **AppState 처리 정리:** 지금 `App.tsx:405-416`은 앱이 앞으로 돌아오면 `syncQueueRef`에 `refreshCloudConnection()`을 이어 붙인 뒤 `pullRemoteChanges()`를 부른다. `refreshCloudConnection`(`sync.ts:37-39`)은 REST 방식에서 아무 일도 하지 않는 함수이고, 대기열은 러너로 옮겨 가므로 이 연결 고리는 갈 곳이 없다. 그래서 `syncQueueRef` 연결과 `refreshCloudConnection` 호출을 지우고 `pullRemoteChanges()`만 남긴다. `refreshCloudConnection`의 export도 다른 호출처가 없으면 지운다.

- **하네스에서 실행하는 것:** 시나리오 7-1(상한 뒤 연결 판정, 이어 가기), 14-2(합치기), 1·2(큰 가족의 이어 가기)는 기기 프로세스의 러너 명령(2.10)으로 돌린다. 판정은 러너가 돌려준 결과, 사건 목록, 서버 요청 목록으로 한다. App의 화면 콜백은 하네스 밖이지만, 사건을 화면 상태로 옮기는 일만 하므로 판정이 남지 않는다.

## 4. D1 예산
무료 등급은 하루 읽기 500만 행, 쓰기 10만 행이며 모든 가족이 함께 쓴다. 인덱스가 걸린 열을 쓰면 인덱스마다 쓰기 1행이 더 붙는다(Cloudflare D1 가격 문서). 아래 표의 "× 2"는 `logs`가 `WITHOUT ROWID`(2.5)라서 테이블 1행과 `idx_logs_family_updated_log` 1행을 쓴다는 뜻이다. 보통 테이블이었다면 새 행 삽입은 기본 키 자동 인덱스 때문에 × 3이다. 이미 있는 행의 갱신은 기본 키를 바꾸지 않으므로 두 경우 모두 × 2다(추측, 2.10 집계의 모형). 그래서 `WITHOUT ROWID`가 줄이는 것은 "처음 올리기"의 쓰기뿐이다. 하네스의 쓰기 집계(2.10)로 이 값을 확인한다. Workers 무료 등급은 하루 요청 10만 회, 요청당 CPU 10ms다.

| 항목 | 읽기 행 | 쓰기 행 | 조건 |
|---|---|---|---|
| 처음 올리기 (기록 N건) | 약 2N (분류 읽기 포함) | 약 2N | 가족당 1회 |
| 전체 모드 (6시간마다, 새로고침) | 약 N | 바뀐 기록 수 × 2 | 같은 버전은 쓰지 않는다 |
| 증분 회차 | 바뀐 행 수 + 최근 2분 행 수 + 1 | 바뀐 기록 수 × 2 | 저장할 때마다 |
| 변경 토큰 폴링 | 1 | 0 | 기기당 90초마다(앱이 켜져 있을 때) |

- 기록 3,000건 가족, 기기 2대, 하루 전체 모드 4회, 저장 100회 기준으로 가족당 하루 읽기는 약 3만 행, 쓰기는 약 400행이다. 결함 4를 고치기 전 추정(쓰기 약 4만 8천 행)보다 크게 줄어든다.
- 처음 올리기는 기록 N건을 2N행으로 쓴다. N=10,000이면 2만 행이라서, 하루에 큰 가족 여러 곳이 처음 연결하면 한도에 가까워질 수 있다. 실사용 가족이 두 곳이므로 이 위험은 받아들이고, 배포 전 실데이터 점검에서 기록 수를 확인한다.
- **CPU:** 올리기 400건 요청의 canonical 변환과 당겨 받기 500행 응답의 문자열 이어 붙이기가 10ms 안에 드는지는 두 단계로 확인한다. 배포 전에는 하네스 실제 서버 모드에서 요청별 처리 시간을 재서 참고값으로 남기고, 배포 후에는 Workers 지표의 CPU 시간을 본다(배포는 승인 전). 한도에 걸리면 페이지와 묶음 크기를 줄인다.

## 5. 검증 계획

### 5.1 시나리오
특별히 적지 않으면 실제 서버 모드(2.10)에서 돌린다.

1. **500건 초과:** 혼자 쓰던 기기(기록 1,200건, 삭제 표식 300건)가 새 가족을 만들면 기록 전체가 나눠 보내기로 올라가고, 합류한 두 번째 기기가 모두 받는다. 요청마다 500건, 1MB 한도를 넘지 않는다. 가족 만들기는 러너(2.11)로 요청하고, 첫 회차가 `continuing: true`로 끝나면 러너가 스스로 이어 가서 사용자 동작 없이 모든 묶음이 올라가는지 본다. 판정은 서버 요청 목록의 묶음마다 건수 500 이하, 본문 UTF-8 바이트 1MB 이하, 응답 상태 200이다. (결함 1, 2.11)
   - **1-a 바이트 묶음:** 기록 400건의 메모를 한글 1,000자(UTF-8로 약 3,000바이트, JavaScript 문자열 길이로 1,000)로 채운다. 400건 묶음은 UTF-8로 약 1.2MB라서, 묶음을 바이트로 자르지 않거나 문자열 길이로 재면 413이 난다. 판정은 413이 0회이고 기록이 모두 올라가는 것이다. (2.5 바이트 단위, 2.6의 5단계)
   - **1-b 느린 서버:** 기록 2,400건(400건 묶음 6개) 기기가 새 가족을 만들고, `hold`의 `delayMs`로 모든 올리기 요청을 요청 상한의 60%만큼 늦춘다. 판정은 세 가지다. 첫 회차의 결과가 `continuing: true`다. 러너의 사건 목록에 상한 때문에 생긴 `failed`가 없다. 결국 모든 기록이 올라간다. 실제 시간으로 환산하면 묶음 하나가 6초라서, 시간 예산(8초)이 있으면 0초와 6초에 시작한 두 묶음만 보내고 12초에 끝난다. 예산이 없으면 묶음 6개에 36초가 걸려 20초 상한에 걸리므로 이 판정이 실패한다. (4판의 1,500건과 40% 지연은 16초라서 상한 안에 끝나 변이를 잡지 못했다.) (2.6의 5단계 회차 시간 예산, 2.11)
2. **3,000건 전체 대조:** 기록 3,000건 가족의 전체 모드와 증분 회차가 성공하고, 당겨 받기가 여러 페이지로 나뉜다. 회차가 끝난 뒤 두 기기의 살아 있는 기록 집합(id와 canonical JSON의 쌍), 서버의 살아 있는 행 집합, 세 곳의 삭제 id 집합이 각각 정확히 같다. 건수만 비교하지 않는다. 시간 예산(2.6의 4단계)에 걸려 전체 모드가 여러 회차에 걸치는 경우도, 그 사이 새로 만든 기록이 같은 회차에 올라가는지와 함께 확인한다. 시간 예산은 서버의 `hold`로 페이지 응답을 늦춰 넘기게 한다. (결함 1, 2.6의 5단계)
   - **2-a 합류 기기의 재전송:** 기록이 없는 기기 C가 3,000건 가족에 합류한다. `hold`의 `delayMs`로 C의 당겨 받기 페이지 응답을 늦춰, C의 전체 모드가 **두 회차 이상**에 걸치게 한다. 판정은 둘이다. 서버 요청 목록에서 C의 전체 모드가 두 회차 이상에 걸쳤다(전제 확인). 전체 모드를 마칠 때까지 C의 올리기 요청에 담긴 기록 수가 0이다(C가 만든 기록이 없으므로). 페이지로 받은 기록을 `full.*`에만 적으면, 첫 회차의 5단계가 기존 장부(비어 있음)와 비교해 받은 기록 전체를 다시 올리므로 이 판정이 실패한다. 전체 모드가 한 회차에 끝나면 끝에서 장부를 바꿔 끼우므로 변이가 드러나지 않는다. 그래서 전제 확인을 판정에 넣는다. (2.6.1)
3. **장부 정확성:** 올리기 요청이 서버에서 기다리는 동안 같은 기기에서 기록 하나를 추가하고 하나를 고친다. 회차가 끝난 뒤 장부에 두 기록이 "올림"으로 적혀 있지 않고, 다음 증분 회차에 두 기록이 올라가 상대 기기에 들어간다. 삭제도 같은 방식으로 확인한다. (결함 2)
4. **삭제 표식 보존:** A가 기록을 만들고 올리기 전에 지운다. 같은 id 기록을 B가 올려도 되살아나지 않고, A와 B 모두에서 사라진 상태로 수렴한다. 순서를 바꿔 B가 먼저 올리고 A가 표식을 올리는 경우도 확인한다. (결함 3)
5. **같은 버전 무시:** 바뀐 기록 없이 전체 모드와 당겨서 새로고침을 반복해도 D1 기록 행 쓰기가 0이고, 변경 토큰이 바뀌지 않으며, 상대 기기의 다음 증분 당겨 받기가 0행이다(최근 2분 안의 행은 제외). 기록 하나를 고치면 쓰기는 그 행 하나(인덱스 포함 2행)다. 아기 정보를 고친 적 없는 두 기기(둘 다 `sharedUpdatedAt: 0`)는 두 경우로 확인한다. 생일을 같은 날로 고정한 경우와, `DEFAULT_PROFILE.birthDate`(`storage.ts:27`)가 앱을 불러온 날짜라서 생일이 다른 경우다. 판정은 "두 기기가 번갈아 한 번씩 동기화를 마친 뒤(A, B, A 순서)에는 이후 회차를 몇 번 돌려도 변경 토큰과 `shared_json`이 바뀌지 않는다"이다. 생일이 다른 경우는 그 전까지 아기 정보 쓰기가 2회 이하여야 한다. (결함 4)
   - **5-a 같은 버전 직접 재전송 (5판):** 위 단계만으로는 서버에 같은 버전이 다시 가지 않는다. 전체 모드도 장부와 다른 항목만 올리기 때문이다. 그래서 A가 기록 50건을 올려 수렴한 뒤 기기 명령 `forgetUploaded()`(2.10)로 A의 `uploaded`를 비우고 증분 회차를 돈다. 판정은 세 가지다. 서버 요청 목록에 A가 50건을 다시 보낸 올리기 요청이 있다(전제 확인). 그 요청의 D1 기록 행 쓰기가 0행이다. 변경 토큰(`families.updated_at`)과 50개 행의 `updated_at`이 그 전과 같다. 기록 upsert 조건을 `>=`로 되돌리면 50행을 다시 쓰고 토큰이 바뀌므로 이 판정이 실패한다.
6. **동률 수렴:** 두 기기가 같은 `updatedAt`으로 같은 기록을 다르게 고친다. 한 기기의 메모는 `"😀"`(U+1F600), 다른 기기의 메모는 `"！"`(U+FF01)로 고정한다. 두 값은 UTF-16 순서와 코드 포인트 순서가 반대라서, 비교 규칙이 어긋나면 이 시나리오가 실패한다. 두 기기와 서버가 같은 내용으로 수렴한다. 아기 정보도 같은 `sharedUpdatedAt`에 이름만 위 두 값으로 다르게 해서 확인한다. (결함 4, 불변 조건 2)
   - **순서 고정:** A가 먼저 올려 확정한다. B는 증분 모드(장부가 있고 전체 대조가 6시간 안)에서 지는 쪽 내용을 올린다. 전체 모드는 올리기 전에 당겨 받기를 먼저 하므로 이 판정에 쓰지 않는다. B가 올릴 때 이때 B의 **당겨 받기 요청을 `hold`로 멈춘** 상태에서 B의 저장소를 읽는다. 그 시점에 B의 기록이 이미 서버 값과 같아야 한다. 이 판정에서 수렴 경로는 올리기 응답의 분류(2.5)뿐이므로, 분류를 빼는 변이가 증분 당겨 받기로 우회해 살아남지 못한다. 판정 뒤 멈춘 요청을 풀고 최종 수렴도 확인한다.
   - **6-a 빈 이름:** A가 아기 이름을 빈 문자열 `''`로 고친다(B보다 큰 `sharedUpdatedAt`). B가 증분 회차를 마치면 B의 이름도 `''`이다. 서버가 응답에서 빈 문자열을 `undefined`로 바꾸면 `isCompleteSharedProfile`이 그 값을 버리므로 B의 이름이 그대로 남아 이 판정이 실패한다. (2.3 응답 모양)
7. **동시 생성:** 두 기기가 같은 키로 동시에 새 가족을 만들어도 둘 다 성공하고, 가족 행은 하나이며, 한쪽만 `isNewFamily: true`를 받는다. 다음 회차 안에 서로의 기록을 받는다. (결함 5)
   - **연출 순서:** ① `hold`로 "연결 요청의 쓰기 배치"를 A와 B 모두에 건다. ② A와 B가 연결을 요청한다. 두 요청 모두 가족 읽기에서 "없음"을 보고 생성 배치에서 멈춘다. ③ 서버의 멈춘 목록에 두 요청이 모두 있는지 확인한다. ④ A를 풀고 응답을 받은 뒤 B를 푼다. 두 요청이 가족 읽기를 마치기 전에 한쪽을 풀면 늦은 쪽이 기존 가족 경로로 가서 "`INSERT`로 되돌리기" 변이가 드러나지 않는다.
7-1. **여러 요청 가족 만들기:** 모든 판정은 러너(2.11)의 `request`로 가족 만들기를 요청해서 한다. 상한은 명령에서 짧게 정한다.
   - 기록 1,200건 기기가 새 가족을 만들면 같은 회차의 두 번째 이후 묶음도 저장된다.
   - 첫 저장 뒤 상한에 걸리면 결과가 `success: true, continuing: true`이고, 러너가 이어 요청한 평소 동기화가 남은 묶음을 올린다.
   - 첫 저장 전에 상한에 걸리면 키가 저장되지 않고 결과는 실패다.
   - **첫 저장 뒤 다른 요청 503 (5판):** 기록 1,200건 기기가 새 가족을 만든다. `fail`로 첫 저장을 마친 뒤의 두 번째 올리기 묶음에 503을 주입한다. 상한에는 걸리지 않는다. 판정은 러너 결과가 `success: true, continuing: true`이고, 이어 요청한 평소 동기화가 남은 묶음을 올리는 것이다. 저장소 판정을 상한일 때만 하면 `syncWithCloud`의 `success: false`가 그대로 나와 이 판정이 실패한다. 같은 조건에서 첫 저장 전(첫 요청)에 503을 주입하면 키가 없으므로 결과는 실패다.
   - **연결 중 404와 410:** 첫 저장 뒤 `wipe`로 데이터베이스를 비우면(404) 결과는 실패이고, 410(다른 기기가 영구 삭제)이면 결과는 실패이고 키가 남지 않는다. 두 경우 모두 저장소 판정으로 성공을 만들지 않는다.
   - **`multiSet` 도중 상한:** 저장 고장 주입의 "첫 쓰기 지연"(2.10)으로 첫 저장을 멈춘다. 멈춘 동안 상한이 지나게 한 뒤 `releaseWrite`로 푼다. 키가 저장됐으므로 결과가 `success: true`다. 진행 상태 플래그로 판정하면 상한 시점에는 저장이 끝나지 않았으므로 실패가 돌아와 이 판정이 실패한다.
   - 회차 도중 연결을 해제하면 다음 저장이 거부되어 키가 되살아나지 않는다. 러너의 사건 목록에 `detached`가 있다.
   (2.6, 2.6.3, 2.11)
8. **커서 여유:** A의 쓰기 배치를 확정 지연 훅으로 멈춘 채 B가 회차를 마치고, 그 뒤 A를 확정한다. 시계를 1분 진행한 뒤 B의 다음 증분 회차가 A의 기록을 받는다. 여러 페이지를 받는 도중 첫 페이지 범위에 늦은 확정을 끼워 넣어도 다음 회차에 받는다. 증분 당겨 받기를 두 번째 페이지에서 끊고, 원래 커서와 `pullAfter` 사이에 늦은 확정을 끼워 넣은 뒤 이어 받아도 그 행을 다음 회차에 받는다. (결함 6)
   - **연출 순서:** ① 서버 시계를 `T`로 둔다. ② A가 올린다. A의 쓰기 배치는 시각 `T`를 찍은 뒤 `BEGIN` 전에 멈춘다. ③ 시계를 `T + 30초`로 진행한다. ④ B가 증분 회차를 마친다. B의 커서 후보는 `T + 30초 - 2분`이다. ⑤ A를 푼다. A의 행은 이른 시각 `T`로 늦게 확정된다. ⑥ 시계를 1분 더 진행하고 B가 다음 증분 회차를 돈다. 판정은 B가 A의 기록을 받는 것이다. 서버 시계를 멈춰 두면 커서 여유가 0이어도 커서가 `T`와 같아져 행을 놓치지 않으므로, ③에서 시계를 반드시 진행한다. 여유를 0으로 바꾼 변이에서 B의 커서는 `T + 30초`라서 A의 행을 놓친다.
   - **8-b 여러 페이지 중 늦은 확정 (5판 연출):** 변이 "마지막 페이지의 커서 후보를 최종 커서로"를 잡는다. ① 시계를 `T`로 두고, A의 쓰기 배치가 `T`를 찍은 뒤 `BEGIN` 전에 멈추게 한다. ② 시계를 `T + 10초`로 두고 `inject`로 B가 받을 행을 두 페이지 분량(페이지 크기를 25로 둔다) 넣는다. ③ `hold`로 B의 두 번째 당겨 받기 요청을 멈춘 채 B의 증분 회차를 시작한다. 첫 페이지의 후보는 `c1 = T + 10초 - 2분`이다. ④ 시계를 `T + 3분`으로 진행하고 B의 두 번째 요청을 푼다. 그 페이지의 후보는 `c2 = T + 1분`이다. B의 회차가 끝나면 커서는 `c1`이다. ⑤ A를 푼다. A의 행은 시각 `T`로 늦게 확정된다. ⑥ B의 다음 증분 회차가 A의 행을 받는다. 변이에서는 커서가 `c2 = T + 1분`이라서 `T`의 행을 놓친다.
   - **8-c 끊긴 뒤 이어 받기 중 늦은 확정 (5판 연출):** 변이 "재개 첫 페이지의 커서 후보로 `pullCursorAtStart` 덮어쓰기"를 잡는다. ① 시계를 `T`로 두고 B가 증분 회차의 첫 페이지를 받는다(`pullCursorAtStart = T - 2분`). 두 번째 요청을 `hold`로 멈추고 B 프로세스를 `SIGKILL`로 끝낸다. ② 시계를 `T + 1분`으로 두고 A의 쓰기 배치가 `T + 1분`을 찍은 뒤 `BEGIN` 전에 멈추게 한다. ③ 시계를 `T + 4분`으로 진행하고 B를 다시 띄워 `pullAfter`부터 이어 받는다. 이어 받는 첫 페이지의 후보는 `T + 2분`이다. B의 회차가 끝나면 커서는 `T - 2분`이다. ④ A를 푼다. ⑤ B의 다음 증분 회차가 A의 행을 받는다. 변이에서는 커서가 `T + 2분`이라서 `T + 1분`의 행을 놓친다. 8-b와 8-c는 서로 다른 후보(`c2`와 재개 첫 페이지 후보)를 쓰므로, 한 변이가 다른 시나리오에서만 잡히는 등가 상황이 생기지 않는다.
8-1. **토큰 확정:** `fail` 엔드포인트(2.10)의 "COMMIT 뒤 예외"로 A의 쓰기 배치가 확정된 직후 응답이 실패하게 한다. 순서는 아래처럼 고정한다. (2.3)
   - ① A의 올리기 배치가 확정된 뒤 응답이 실패한다. ② A가 다시 보내기 **전에** B가 변경 토큰을 한 번 읽는다. 판정: 토큰이 바뀌었고, B의 다음 증분 회차가 A의 기록을 받는다. 토큰 갱신을 배치 밖 마지막 문장으로 되돌리면(지금 `index.ts:350-355`의 `hasWrites` 방식) 확정 뒤 예외 때문에 그 문장이 실행되지 않아 토큰이 그대로이므로 이 판정이 실패한다. A가 먼저 다시 보내면 `hasWrites` 방식은 재전송 요청에서 토큰을 바꾸므로 변이가 살아남는다. 그래서 순서를 고정한다.
   - ③ 그 뒤 A가 같은 항목을 다시 보낸다. 판정: 그 요청의 D1 기록 행 쓰기가 0행이고 토큰이 ②에서 읽은 값과 같다(5판).
9. **강제 종료 시점:** 아래 지점마다 기기 프로세스를 `SIGKILL`로 끝내고 같은 저장 파일로 다시 띄워 회차를 다시 시작해도 기록이 줄지 않고, 이미 받은 페이지를 처음부터 다시 받지 않으며, 모든 기록이 결국 서버에 올라간다.
   - 전체 모드 당겨 받기 페이지 중간, 마지막 페이지 직후(올리기 전)
   - 올리기 묶음 중간(요청 전송 후 응답 전), 마지막 묶음 직후
   - 증분 당겨 받기 페이지 중간
   - 원자적 저장 도중(저장 고장 주입으로 첫 쓰기 뒤 종료). "첫 쓰기"는 2.10의 세는 쓰기(기록 키나 새 장부 키를 담은 호출)만 센다. 지금 설계는 그런 쓰기가 한 번이라서 기록과 장부가 함께 남거나 함께 남지 않는다.
   - **집합 판정:** 지점마다 재시작한 기기가 증분 회차를 한 번 마친 뒤, 시계를 6시간 진행하기 **전에** 기기의 살아 있는 기록 집합(id와 canonical JSON)과 서버의 살아 있는 행 집합이 정확히 같아야 한다. 전체 대조로 뒤늦게 맞춰지는 경우를 통과로 치지 않으려는 것이다. 장부를 먼저 저장하고 기록을 나중에 저장하다 그 사이에 종료되면, 장부의 커서는 받은 페이지 뒤로 갔는데 기록은 없으므로 이 판정이 실패한다.
   - **재전송 쓰기 판정 (5판):** "올리기 묶음 중간(요청 전송 후 응답 전)"에서 종료한 경우, 재시작한 기기는 서버가 이미 확정한 묶음을 다시 보낸다. 그 재전송 요청의 D1 기록 행 쓰기가 0행이고, 변경 토큰이 종료 직전 값과 같아야 한다.
10. **영구 삭제와 410:** A가 영구 삭제하면 B의 다음 동기화와 변경 토큰 폴링이 410을 받고, B는 연결을 끊되 기록은 그대로 남는다. B의 폴링은 410 뒤 재연결하지 않는다. 같은 키로 `allowCreate: true` 연결을 보내도 410이고 가족이 생기지 않는다. 삭제와 생성 요청을 겹쳐도 같다. (결함 7, 불변 조건 4)
11. **404 보존:** 두 기기가 연결된 상태에서 D1을 비우면(설정 오류 흉내) 동기화가 오류만 보이고 연결은 끊기지 않는다. D1을 되돌리면 동기화가 다시 이어진다. 가족 합류에서 없는 키를 넣으면 합류 실패 메시지가 나온다. 판정 함수(2.7) 단위 검사로 "404 → 오류 표시, 연결 유지", "410 → 연결 해제", "토큰 410 → 폴링 중지 후 동기화 요청", "토큰 404 → 재연결"을 확인한다. (결함 7, 불변 조건 3)
12. **혼자 쓰기:** `syncKey` 없이 기록을 추가, 수정, 삭제하고 앱을 다시 열어도 요청이 0회다. (불변 조건 5, 가짜 Worker 모드로도 확인)
13. **장부 손상:** 새 장부 키에 깨진 값을 넣거나 다른 가족 장부를 넣으면 전체 모드로 돌고 기록이 줄지 않는다. 옛 키 `@baby_sync_ledger_v1`의 값은 회차 전후로 그대로다. (불변 조건 6)
14. **가져오기와 복원:** 데이터 가져오기와 백업 복원 뒤 새 장부 키가 지워지고, 다음 회차가 전체 모드로 돈다.
14-1. **서버 교체 뒤 다시 올리기:** 두 기기가 동기화를 마친 뒤 D1 기록을 비우고(가족 행은 남김) 시계를 6시간 진행하면, 다음 전체 모드가 끝난 뒤 두 기기의 기록이 모두 다시 올라간다. (2.6.1의 장부 바꿔 끼우기)
14-2. **합치기:** 러너(2.11)로 평소 동기화를 하나 요청하고, 그 회차의 올리기 요청을 `hold`로 멈춘다. 그 사이 기록을 다섯 번 저장하고 저장마다 평소 동기화를 요청한다(App이 저장 뒤 하는 일과 같다). 요청을 풀면 회차는 처음 것 하나와 합쳐진 것 하나, 모두 두 번만 돌고, 다섯 기록이 모두 올라간다. 판정은 서버 요청 목록의 회차 수와 기록 집합이다. 하네스는 `App.tsx`가 아니라 러너의 실제 대기열을 실행한다. (결함 8, 2.11)
   - `isCoalescibleSync`는 단위 검사로 네 가지 선택(`createBackup`, `allowFamilyCreation`, `connecting`, `forceFullRead`)이 각각 켜졌을 때 거짓인지도 확인한다.
15. **기존 회귀:** 기존 `regression.mjs` 시나리오가 가짜 Worker 모드와 실제 서버 모드 양쪽에서 통과한다. 다만 아래 검사는 이 설계가 일부러 바꾼 동작이나 Firestore식 내부 상태에 기대므로, 표대로 바꾸거나 없앤다. 줄 번호는 3판을 쓸 때의 `regression.mjs` 기준이다.

    | 기존 검사 (`regression.mjs`) | 처리 | 바꾼 판정 |
    |---|---|---|
    | 데이터 쓰기마다 가족 알림 문서가 같은 트랜잭션에 있다(`:23-27`) | 대체 | 쓰기가 있는 배치마다 토큰이 함께 바뀐다(2.3). 어댑터의 토큰과 쓴 행 수로 판정한다 |
    | 커서 없는 회차의 `constraints.length === 0`, 증분 회차의 `constraints.length > 0`(`:108`, `:116`, `:181`, `:224`, `:251`) | 대체 | 어댑터 요청 목록에서 당겨 받기 요청의 `pull.after`가 `(0, '')`이면 전체, 아니면 증분이다 |
    | 밀린 기록이 있으면 장부의 `lastFullReadAt === 0`이 되어 다음 회차가 전체 대조다(`:241-254`) | 폐기 후 대체 | 밀린 기록은 `uploaded`에 적히지 않고, 같은 회차의 분류 응답(`remoteLogs`)으로 서버 값에 수렴한다. 다음 회차는 증분 모드이고 그 기록을 다시 올리지 않는다 |
    | 옛 장부 키 `@baby_sync_ledger_v1`을 지우고 읽는 검사(`:178`, `:202`, `:242`) | 대체 | 새 키 `@baby_sync_ledger_cf_v1`로 바꾼다. 옛 키는 시나리오 13처럼 값이 그대로인지만 본다 |
    | `state.docs.set`으로 상대 기기 기록을 넣는 검사(`:133-159`, `:197`, `:213`, `:234`) | 대체 | 어댑터의 `inject`로 넣는다. 서버 시각은 시계 주입으로 정한다 |
    | `state.beforeRead`, `state.beforeTransaction`으로 요청 중 끼어드는 검사(`:34-41`, `:53-57`, `:232`) | 대체 | 어댑터의 `hold`로 요청을 멈춘 사이에 저장소를 바꾸거나 서버 행을 넣고, `release`로 푼다 |
    | `state.beforeCommit` 커밋 실패(`:79-86`) | 대체 | 어댑터의 `fail`(COMMIT 전 실패)로 바꾼다. 서버 행이 그대로인지 판정한다 |
    | 냉각 기간을 `pendingDeletionAt`을 직접 고쳐 지나게 하는 검사(`:284-286`) | 대체 | 어댑터의 시계 진행으로 1시간을 지나게 한다 |

    표에 없는 검사는 그대로 둔다. 어댑터로 옮길 수 없는 검사가 새로 나오면 가짜 Worker 모드에서만 돌리고, 목록을 `regression.mjs` 머리말에 적는다.
16. **요청 크기 조절:** 실제 서버 모드에서 `fail`의 503 주입으로 400건 묶음을 실패시키면 장부의 `limits.push`가 200으로 줄고, 다음 회차가 200건 묶음으로 나머지를 올린다. 당겨 받기도 같은 방식으로 `limits.pull`이 준다. 하한 25에서는 더 줄지 않는다. 서버 상수 `maxPushItems`를 100으로 낮추면 장부 값과 상관없이 다음 응답 뒤 묶음이 100건 이하다. 기기 프로세스를 다시 띄워도 첫 묶음부터 100건 이하다(힌트를 장부에 저장하므로). 연속 10회 성공하면 크기가 두 배로 돌아가되, 서버 힌트가 100이면 100을 넘지 않고 그 뒤 실패 회차가 없다. 900KB를 넘는 기록 하나는 `oversizedIds`로 알리고, 나머지 기록은 모두 올라간다. 단위 검사로 `nextLimits`의 경계값(413, 503, 시간 초과, 네트워크 끊김, 4xx, 서버 힌트 상한)을 확인한다. (2.6.2)
   - **16-a 당겨 받기 실패 뒤 올리기:** 전체 모드 회차의 첫 페이지 요청에 503을 주입한다. 같은 회차의 올리기 요청이 나가서 새 기록이 서버에 올라가고, `limits.pull`이 절반으로 준다. 네트워크 끊김을 흉내 내면(서버 프로세스가 연결을 끊음) 그 회차는 올리기 없이 끝난다. 단위 검사로 `nextStepAfterFailure`의 표(2.6.2) 전체를 확인한다.
   - **16-b 하한에서 시간 초과:** `limits.pull`이 25인 상태에서 페이지 요청을 `hold`로 요청 상한보다 오래 멈추면, 결과에 `pullTooSlow: true`가 있고 크기는 25 그대로이며 러너 사건이 `failed`다.
17. **아기 정보 가드:** `shared_json`이 NULL인 가족(기록만 올린 상태)의 응답에 `remoteProfile`이 없다. 같은 `sharedUpdatedAt`에서 `{}`, 일부 항목만 있는 값, `targetFormula`가 문자열인 값을 `remoteProfile`로 넣어도(가짜 Worker 모드의 응답 조작과 `isCompleteSharedProfile` 단위 검사) 기기의 아기 이름이 바뀌지 않는다. 서버에 일부 항목만 있는 `pushProfile`을 보내면 `profileRejected: true`이고 `shared_json`이 바뀌지 않는다. (2.3, 2.6.1)
18. **진전 없음 중단:** 올릴 기록을 3묶음 이상(1,200건) 두고, 서버 분류가 항상 "받아들이지 않음"을 돌려주도록 가짜 Worker를 조작한다. 그러면 한 회차의 올리기 요청은 2묶음에서 멈추고 결과에 `uploadStalled: true`가 있다. 러너의 사건은 `failed`이고, 러너는 이 회차를 이어 가지 않는다(`continuing`이 없다). 다음 회차는 같은 항목을 다시 시도한다. (2.6의 5단계, 2.11)

## 6. 남은 판단
- 페이지 크기(500행)와 묶음 크기(400건, 900KB)의 기본값은 CPU 측정 결과에 따라 줄일 수 있다. 서버 힌트(`MAX_PUSH_ITEMS`, `MAX_PAGE_ROWS`)로 줄이면 앱을 새로 출시하지 않아도 되고, 줄여도 설계의 다른 부분은 바뀌지 않는다(2.6.2).
- 단계 B(기존 사용자 이전)는 이 문서의 장부 형식(`@baby_sync_ledger_cf_v1`)과 410 처리를 전제로 다시 설계한다.
- **전체 모드가 같은 페이지에서 계속 실패할 때 (5판, 4차 검토 경미 지적):** `full`이 남아 있는 동안 증분 당겨 받기는 건너뛰므로(2.6의 6단계), 같은 페이지가 회차마다 실패하면 상대 기기의 새 기록을 받지 못한다. 이 상태에서도 올리기는 하고(2.6.2 실패 처리 규칙), 동기화 상태에 오류가 보이며, 크기 절반 줄이기와 `pullTooSlow`가 주된 원인(CPU 한도, 느린 망)을 다룬다. 그래서 1.8.0에서는 따로 대책을 두지 않는다. 배포 뒤 오류 보고에서 이 경우가 나오면, "N회차 넘게 `full.after`가 그대로면 `cursorMillis`에서 증분 당겨 받기를 한 번 한다"를 더한다.
