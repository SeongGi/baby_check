# 05-기존 사용자 이전 설계 (1.8.0 보완, 4판)

`02-설계.md`는 새로 시작하는 가족을 기준으로 쓴 설계다. 이미 Firestore로 동기화하던 가족이 1.8.0으로 업데이트하는 경로는 다루지 않았다. 이 문서는 그 경로에서 찾은 결함과 대책을 적는다. 실사용자(jjukkom, sgchoi1547) 데이터를 반드시 보전해야 한다는 제약이 가장 앞선다.

- 2판은 1차 독립 검토를 반영했다. 1판의 "서버는 바꾸지 않는다"는 철회했다.
- 3판은 2차 독립 검토(판정: 수정 필요)를 반영했다.
- 4판은 3차 독립 검토(판정: 수정 필요)를 반영했다. 검토 상한 3회를 넘겼지만 성기님이 반영 후 4차 검토를 승인했다(2026-10-30). 반영 내역은 8장에 모았다.
- 2차 검토에서 찾은 결함 J(500건 한도)는 이전 경로만의 문제가 아니다. 이미 구현한 1.8.0 동기화에도 있는 결함이라서, 새 가족도 기록이 500건을 넘으면 동기화가 멈춘다.

## 0. 불변 조건
아래 조건은 이 설계의 모든 단계가 지켜야 한다. 검증 시나리오도 이 조건을 기준으로 판정한다.

1. **기록 보존:** 기기의 기록은 합치기만 하고 줄이지 않는다. 이전 단계와 이전 직전 백업 복원은 기록을 지우지 않는다.
2. **Firestore 쓰기 제한:** Firestore에 쓰는 일은 아래 세 가지뿐이다.
   - 이전 단계의 회원 문서 생성 (1.7.9와 같은 동작)
   - 사용자가 확인 절차를 거쳐 요청한 영구 삭제 흐름의 예약 쓰기, 예약 취소 쓰기, 실제 삭제 (2.8)
   - 사용자가 선택한 삭제 예약 취소와 1.7.9 삭제 마무리 (2.4.1, 2.6)
3. **자동 연결 해제 제한:** 앱이 스스로 가족 연결을 끊는 근거는 서버의 "삭제된 가족" 응답(410)뿐이다. 404는 이전 완료 여부와 상관없이 "동기화 중지와 오류 표시"로만 처리한다. 1.8.0은 아직 출시 전이라 `deleted_families` 없이 사라진 가족은 있을 수 없고, 이전 뒤의 404는 서버 설정 오류(D1 바인딩 잘못, 되돌리기)의 신호이기 때문이다. Firestore 거부도 근거가 되지 않는다.
4. **부활 금지:** 영구 삭제한 가족은 어떤 경로로도 D1에 다시 생기지 않는다.
5. **혼자 쓰기 무요청:** `syncKey`가 없으면 네트워크 요청이 0회다.
6. **Firestore 무요청 기본값:** Firestore 시절의 근거(2.4의 근거 조건)가 없는 기기는 Firestore에 요청하지 않는다. 1.8.0에서 새로 시작한 가족과 그 가족에 합류한 기기의 Firestore 요청은 0회다.

## 1. 찾은 결함

### 결함 A: 업데이트 직후 두 기기의 가족 연결이 끊긴다
- 평소 동기화(`syncLatestData`)와 당겨서 새로고침(`handleRefresh`)은 `allowFamilyCreation=false`로 `syncWithCloud`를 부른다.
- D1에는 기존 가족이 아직 없다. 그래서 `POST /api/family/connect`(`allowCreate=false`)가 `family_not_found`(404)를 돌려준다.
- `syncWithCloud`는 이 응답을 받으면 `familyUnavailable: true`를 돌려준다(`sync.ts:170-176`, `sync.ts:332-341`). `App.tsx:254`는 이 값을 "다른 기기가 가족을 영구 삭제했다"고 해석하고 `syncKey`를 지운다.

### 결함 B: 업데이트 후 최대 6시간 동안 기존 기록이 D1에 올라가지 않는다
- Cloudflare 코드는 Firestore 시절과 같은 장부 키(`@baby_sync_ledger_v1`)를 쓴다.
- 업데이트 직후의 장부에는 Firestore 커서와 "이미 올린 기록" 목록이 들어 있다. `lastFullReadAt`이 6시간 안이면 증분 모드가 켜져서, 장부에 있는 기록은 D1에 올리지 않는다.

### 결함 C: 영구 삭제한 가족이 Firestore에서 되살아난다
- "D1에 없고 Firestore에 있으면 이어받는다"는 규칙만 두면, 1.8.0에서 영구 삭제한 가족이 Firestore에 남아 있다가 다음 이전 시도에서 D1에 다시 생긴다.
- 1.7.9의 영구 삭제(`deleteFamilyCloudData`)는 다른 회원 문서, 기록, 프로필, 내 회원 문서, 가족 문서 순서로 지운다(`7d4753b` `sync.ts:766-773`). `firestore.rules`는 `pendingDeletionAt`이 timestamp이고 그 시각이 지난 뒤에만 이 삭제를 허용한다. 따라서 부분 삭제 상태의 가족 문서에는 timestamp인 `pendingDeletionAt`이 반드시 남아 있다.
- 1.7.9의 예약 취소는 `pendingDeletionAt: null`을 쓴다(`7d4753b` `sync.ts:721`). 그래서 판단 기준은 "필드가 있다"가 아니라 "값이 timestamp다"여야 한다.

### 결함 D: 20초 상한 안에서 이전하면 저장이 버려지고 할당량이 소모된다
- `App.tsx:36`의 `SYNC_TIMEOUT_MS=20s`가 동기화 한 번 전체를 감싼다. 이전 단계가 그 안에서 돌면 Firestore 전체 읽기와 병합이 상한에 걸릴 때 병합 결과가 버려진다.
- 기록을 저장할 때마다 동기화가 돌기 때문에, 이전이 끝나지 않으면 저장할 때마다 Firestore 전체 읽기를 다시 한다.

### 결함 E: D1에 행이 없을 때 올린 삭제 표식이 사라진다
- `server/src/index.ts:292-300`은 삭제 표식을 `UPDATE logs SET deleted_at …`로 처리한다. 행이 없으면 아무 일도 일어나지 않는다.
- 클라이언트는 그 id를 장부의 `tombstoned`에 적는다(`sync.ts:310-311`). 이후 증분 모드에서는 다시 보내지 않는다. 다른 기기가 나중에 같은 기록을 올리면 삭제했던 기록이 되살아난다.
- 가짜 Worker(`fake-worker.mjs:156-161`)는 행이 없어도 표식을 만든다. 하네스가 실제 서버 대신 가짜 Worker를 쓰기 때문에(`loader.mjs:22-24`) 이 결함을 잡지 못했다.

### 결함 F: 연결 해제 오판
- Firestore 회원 문서 생성의 `permission-denied`는 가족이 없을 때 외에도, `inviteHash`가 없는 예전 가족 문서나 익명 로그인 uid가 바뀐 기기에서 나온다.

### 결함 G: 한 기기만 업데이트하면 사실상 연결이 끊긴다
- A(1.8.0)가 D1에 쓴 기록은 B(1.7.9)에게 가지 않는다. B가 Firestore에 쓴 기록도 A가 따로 읽지 않으면 A에게 오지 않는다.

### 결함 H: 두 기기가 동시에 가족을 만들면 늦은 쪽이 500을 받는다
- `index.ts:119-130`의 가족 생성은 충돌 처리가 없는 `INSERT`다.

### 결함 I: 키 형식 불일치 가능성
- 서버는 `Bearer` 키를 16~64자로만 받고(`index.ts:60`), 키를 소문자로 바꿔서 해시한다(`index.ts:63`). Firestore 해시는 키를 원래 대소문자 그대로 해시한다(`7d4753b` `sync.ts:75-78`).
- 지금 만드는 키는 32자 소문자 16진수(`randomUUID`에서 `-` 제거)라서 문제가 없지만, 실사용자 키는 확인하지 않았다.

### 결함 J: 요청 하나에 500건이 넘으면 동기화가 멈춘다 (2차 검토, 기존 1.8.0 코드 결함)
- 서버는 요청 하나에 기록과 삭제 표식을 합쳐 500건(`index.ts:34`, `index.ts:251-253`), 본문 1MB(`index.ts:33`)까지만 받는다.
- 클라이언트는 전체 모드에서 모든 기록과 삭제 표식을 요청 하나에 담는다(`sync.ts:200-213`). `postSync`(`cloudClient.ts:118-127`)는 나눠 보내지 않는다.
- 500건이 넘는 가족은 전체 모드 동기화가 매번 413으로 실패한다. 장부가 갱신되지 않으므로 다음 회차도 전체 모드가 되어 동기화가 영구히 멈춘다. 가짜 Worker에 한도가 없어서 하네스는 통과했다.

### 결함 K: 동시 업로드 때 당겨 받기 커서가 앞서간다 (2차 검토)
- 서버는 요청 시작 때 `serverTime`을 정하고(`index.ts:263`), 쓰기를 100문장씩 나눠 확정한다(`index.ts:357-359`). 당겨 받기는 `updated_at > lastSyncedAt`이다.
- A의 요청이 쓰기를 확정하기 전에 B의 요청이 당겨 받기를 마치면, B의 커서(B의 `serverTime`)가 A의 행 시각(A의 `serverTime`)보다 뒤로 간다. B는 A의 기록을 다음 6시간 전체 대조 때까지 받지 못한다.

### 결함 L: 백업 복원이 기록을 줄인다 (2차 검토)
- `restoreFromLocalBackup`(`storage.ts:556-582`)은 합치지 않고 기록과 프로필을 통째로 바꾸며, 모든 기록의 `updatedAt`을 지금으로 올린다.
- 이전 직전 백업을 이 경로로 복원하면, 아직 올리지 못한 기기 기록이 사라지고 상대가 나중에 고친 기록이 옛 내용으로 덮인다.

## 2. 대책

### 2.1 장부 키 분리 (결함 B)
- Cloudflare 장부는 새 키 `@baby_sync_ledger_cf_v1`에 저장한다. 평소 동기화는 옛 키 `@baby_sync_ledger_v1`을 읽지 않는다.
- 업데이트 후 첫 D1 동기화는 반드시 전체 모드로 돈다.
- 새 장부 키는 지금 옛 키를 지우는 두 곳에서도 지운다: `storage.ts:522`(데이터 가져오기)와 `storage.ts:580`(백업 복원).
- 옛 장부는 이전 판단(2.4의 근거 조건, 2.5)에만 쓰고 지우지 않는다. 전환기 커서는 옛 장부가 아니라 2.6의 별도 키에 둔다.

### 2.2 이전 상태 저장
가족 키마다 `@baby_cf_migration_v1:<syncKey>`에 아래 값을 둔다.

```ts
type MigrationState = {
  firestoreMergedAt?: number;  // Firestore 기록을 기기에 합친 시각 (읽을 필요가 없다고 판정한 경우도 적는다)
  d1UploadedAt?: number;       // 합친 기록을 D1에 전체 모드로 모두 올린 시각
  nextFirestoreAttemptAt?: number; // Firestore를 다시 읽어도 되는 시각 (실패 간격)
  firestoreReadAfter?: string; // 페이지 나눠 읽기에서 마지막으로 합친 문서 id (2.4-4)
  firestoreMaxUpdatedAt?: number; // 지금까지 읽은 문서 updatedAt의 최댓값 (전환기 커서의 처음 값)
  lastError?: string;          // 마지막 실패 사유 (화면 안내용)
};
```

- 이전 완료는 `firestoreMergedAt`과 `d1UploadedAt`이 모두 있는 상태다. 병합은 끝났는데 업로드가 실패한 경우 Firestore를 다시 읽지 않고 업로드만 다시 한다.
- 이 값은 데이터 가져오기, 백업 복원, 가족 영구 삭제, 연결 해제에서도 지우지 않는다. 그래서 삭제한 가족을 다시 이전하거나 되살리는 일이 없다.
- **1.7.9 연결 근거 표식:** 1.8.0을 처음 실행할 때, `syncKey` 유무와 상관없이 `@baby_cf_legacy_key_v1`에 아래 값을 **항상** 한 번 적는다. 이미 값이 있으면 다시 계산하지도, 덮어쓰지도 않는다.

  ```ts
  type LegacyKeyMarker = {
    checkedAt: number;
    keys: string[]; // 첫 실행 시점의 프로필 syncKey, 그리고 옛 장부(@baby_sync_ledger_v1)의 familyKey. 없으면 빈 배열
  };
  ```

  - 이 표식이 2.4의 근거 조건이 보는 유일한 값이다. 첫 실행 뒤에는 프로필 키나 옛 장부를 근거로 쓰지 않는다. 그래서 혼자 쓰던 기기나 새로 설치한 기기가 1.8.0에서 가족에 합류해도 그 키는 근거가 되지 않는다.
  - 출시 전 1.8.0 시험 빌드를 쓴 기기(성기님 시험 기기)는 옛 장부 키를 D1 장부로 썼으므로 근거가 잘못 잡힐 수 있다. 출시 빌드를 깔기 전에 이 기기의 앱 데이터를 지우거나, 개발 메뉴에서 표식을 비운다. 실사용자 기기는 1.8.0 시험 빌드를 쓴 적이 없다.
- 위 값들은 모두 수백 바이트라서 AsyncStorage 용량(약 6MB)에 영향이 없다.

### 2.3 이전 단계 실행 방식 (결함 D)
- 이전 단계는 `syncWithCloud` 안이 아니라 별도 함수 `runFamilyMigration(syncKey)`로 둔다. `App.tsx`는 동기화를 시작하기 전에 이 함수를 부르고, `SYNC_TIMEOUT_MS` 상한을 씌우지 않는다.
- 기기당 하나만 돈다. 모듈 수준의 진행 중 Promise를 가족 키와 함께 보관하고, 같은 키로 이미 도는 중이면 같은 Promise를 돌려준다. 다른 키로 바뀌면 앞 작업의 결과는 저장하지 않고 버린다(저장 직전에 현재 프로필의 `syncKey`를 다시 확인한다).
- **실패 간격은 Firestore를 읽어 비용이 드는 실패에만 적용한다.** D1 네트워크 실패와 D1 업로드 실패는 평소 동기화 주기대로 다시 시도한다. Firestore 실패는 비용에 따라 둘로 나눈다.
  - **가벼운 실패:** `logs` 전체 읽기를 시작하기 전에 난 실패(로그인, 회원 확인, 가족 문서 읽기, 거부, 삭제 예약)다. 읽기 3회 이하만 쓴다. `nextFirestoreAttemptAt`을 30분, 1시간, 2시간 순서로 늘리고 최대 6시간으로 둔다.
  - **무거운 실패:** `logs` 읽기를 시작한 뒤에 난 실패(상한 초과, 중간 오류)다. 2.4-4의 페이지 나눠 읽기 덕분에 한 번의 실패로 버리는 읽기는 최대 한 페이지(500건)다. 다음 시도는 1시간부터 두 배씩 늘려 최대 12시간 간격으로 하고, 저장된 위치부터 이어 읽는다.
  - **할당량 소진(`resource-exhausted`):** 다시 시도해도 실패하므로 태평양 시간 자정(할당량 초기화) 뒤로 미룬다.
  - 사용자가 당겨서 새로고침을 해도 Firestore 실패 간격은 지킨다.
- 이전 단계 전용 예산은 전체 90초다. Firestore 호출 하나마다 15초 상한을 둔다. 상한에 걸리면 `terminate(db)`로 Firestore 인스턴스를 닫는다.
- `firebase.ts`는 지금 모듈을 불러올 때 `db`를 만든다(`firebase.ts:52-67`). 이를 `getFirestoreDb()`와 `resetFirestoreDb()`로 바꿔서 처음 쓸 때 만들고, `terminate` 뒤에는 새로 만든다. `terminate` 뒤 같은 앱으로 `initializeFirestore`를 다시 부를 수 있는지 구현 첫 단계에서 확인한다. 안 되면 이름을 붙인 새 앱 인스턴스로 만든다.
- `firestoreImport.ts`와 `firebase.ts`는 이전 단계, 전환기 읽기(2.6), 영구 삭제(2.8)에서만 동적 `import()`로 불러온다.
- 이전 단계가 기기에 합친 결과를 저장하면 `App.tsx`는 저장소에서 기록과 프로필을 다시 읽어 화면에 반영한다.

### 2.4 이전 단계 순서
`firestoreMergedAt`과 `d1UploadedAt`이 모두 있으면 아무것도 하지 않는다. 그렇지 않으면 아래 순서를 밟는다.

1. **이전 직전 백업:** `@baby_pre_cloudflare_backup_v1`에 현재 기록과 프로필을 저장한다. 이미 있으면 덮어쓰지 않는다. `createBackup` 값과 상관없이 실행한다.
   - 저장이 실패하면(용량 부족 포함) 이전을 멈추고 "기기 저장 공간이 부족해 업데이트 전 백업을 만들지 못했습니다"를 보여 준다. 사용자가 "백업 없이 계속"을 고르면 진행한다. 이전 단계는 기록을 합치기만 하므로 백업이 없어도 기록은 줄지 않는다.
2. **D1 가족 확인:** `connectFamily(allowCreate=false)`를 부른다. 결과는 `exists`, `missing`(404), `deleted`(410, 2.7) 중 하나다. 네트워크 오류면 실패로 끝낸다(Firestore 실패 간격은 적용하지 않는다).
   - `deleted`이면 이전을 멈추고 `familyUnavailable: true`를 돌려준다.
3. **Firestore를 읽을지 판단 (`firestoreMergedAt`이 없을 때만):**
   - **근거 조건:** `@baby_cf_legacy_key_v1.keys`에 지금 키가 있다(2.2). 이 기기는 1.7.9 시절 이 가족에 연결돼 있었다.
   - D1이 `exists`이고 근거 조건이 없으면 Firestore를 읽지 않는다. `firestoreMergedAt`을 지금 시각으로 적고 7번으로 간다. 1.8.0에서 만든 가족에 1.8.0 기기가 합류하는 경우가 여기에 해당한다.
   - D1이 `missing`이면 근거 조건과 상관없이 Firestore를 읽는다. 상대가 아직 1.7.9인 가족의 초대 링크로 새 기기가 합류하는 경우를 받기 위해서다.
   - `nextFirestoreAttemptAt`이 지나지 않았으면 Firestore를 읽지 않는다. D1이 `exists`이면 7번으로 가고, `missing`이면 실패로 끝낸다.
4. **Firestore 읽기:** 새 모듈 `src/database/firestoreImport.ts`가 1.7.9 코드에서 읽기 경로만 옮겨 온다. Firestore 해시는 1.7.9와 같이 키를 대소문자 그대로 해시한다.
   1. 익명 로그인 후 `families/<familyId>/members/<uid>`를 읽는다. 없으면 1.7.9와 같이 초대 해시로 회원 문서를 한 번 만든다.
   2. 회원 문서 생성이 `permission-denied`이면 결과는 `firestore_denied`다. 2.5에서 해석한다.
   3. 가족 문서를 읽는다. `pendingDeletionAt`이 timestamp이면(미래든 과거든) 결과는 `firestore_pending_deletion`이다. `null`이거나 없으면 다음으로 간다.
   4. `logs` 컬렉션 전체와 `profile/shared`를 읽는다. `deleted: true` 문서는 삭제 표식으로, 나머지는 `payload`를 기록으로 모은다. 결과는 `firestore_ok`다.
      - `logs`는 문서 id 순서로 500건씩 나눠 읽고, 한 페이지마다 15초 상한을 둔다. 페이지를 받을 때마다 그 페이지를 기기에 합쳐 저장하고(5번과 같은 방식), 마지막 문서 id와 지금까지의 `updatedAt` 최댓값을 `@baby_cf_migration_v1`의 `firestoreReadAfter`, `firestoreMaxUpdatedAt`에 적는다. 중간에 실패하면 다음 시도는 그 위치부터 읽는다. 느린 망에서도 한 번 읽은 페이지를 다시 읽지 않는다.
      - 모든 페이지를 읽으면 `profile/shared`를 읽고 5번으로 간다.
   5. 할당량 소진(`resource-exhausted`), 상한 초과, 그 밖의 오류는 `firestore_error`다.
5. **병합 (`firestore_ok`일 때):** Firestore 기록과 삭제 표식을 `mergeLogs`와 프로필 LWW 규칙으로 기기에 합치고 `saveSyncedDataWithoutLoss`로 저장한다. 이때 2.6의 전환기 커서를 함께 적는다. 저장이 끝나면 `firestoreMergedAt`을 적는다.
6. **D1 가족 결정:**

   | D1 | Firestore | 처리 |
   |---|---|---|
   | deleted | 읽지 않음 | `familyUnavailable: true`. 연결을 끊는다. |
   | exists | 읽지 않음(근거 없음) | 7번으로 간다. |
   | exists | ok | 병합 후 7번으로 간다. |
   | exists | denied, pending_deletion, error | 병합 없이 7번으로 간다. `firestoreMergedAt`은 적지 않고, 실패 간격 뒤 Firestore 읽기만 다시 시도한다. 상대가 이미 D1로 옮겼으므로 평소 동기화는 계속한다. |
   | missing | ok | `connectFamily(allowCreate=true)`로 D1에 가족을 만들고(이어받기) 7번으로 간다. |
   | missing | pending_deletion | 2.4.1에 따른다. |
   | missing | denied | 2.5에 따른다. |
   | missing | error | 실패로 끝내고 연결은 유지한다. 실패 간격 뒤 다시 시도한다. |

7. **D1 전체 업로드:** 새 장부 키로 평소 동기화(`syncWithCloud`)를 돌린다. 2.1 덕분에 전체 모드로 돌고, 2.7의 나눠 보내기와 삭제 표식 upsert가 적용된다. 모든 묶음이 성공하면 `d1UploadedAt`을 적는다.
   - 이 동기화는 `App.tsx`의 동기화 대기열(`syncQueueRef`)에 넣어 돌린다. 평소 동기화와 동시에 돌지 않으므로 두 작업이 장부를 서로 덮어쓰지 않는다.
   - Firestore 읽기(1~6번)는 대기열 밖에서 돈다. 그 사이 평소 동기화가 장부를 고쳐도, 이전 단계는 장부를 쓰지 않고 기록 저장만 하므로 경합이 없다. 기록 저장은 `saveSyncedDataWithoutLoss`가 합치기로 처리한다.

#### 2.4.1 삭제 예약 중인 가족 (`missing` + `pending_deletion`)
1.7.9에서 삭제를 예약했거나 삭제가 도중에 멈춘 가족이다. 1.8.0의 예약, 취소, 삭제 버튼은 D1만 부르므로(`sync.ts:378-425`) 그대로 두면 아무도 이 상태를 풀 수 없다. 그래서 사용자에게 고르게 한다.

- 화면 안내: "다른 기기에서 가족 서버 데이터 삭제가 예약되어 있습니다." 선택지는 세 가지다.
  - **예약 취소하고 계속 쓰기:** Firestore 가족 문서에 `pendingDeletionAt: null`을 쓰고(1.7.9 취소와 같은 쓰기) 바로 2.4를 다시 실행한다. 부분 삭제가 이미 진행된 가족이면 남은 기록만 이어받는다. 기기 기록은 그대로 있으므로 두 기기가 가진 기록은 D1로 모인다.
  - **삭제 마치기:** 예약 시각이 지났으면 2.8의 Firestore 삭제를 실행한다. 가족 문서까지 지워진 것을 다시 읽어 확인한 뒤에만 서버에 `POST /api/family/delete`를 보내 `deleted_families`에 기록한다(2.7-1). 상대가 그 사이 예약을 취소해 Firestore 삭제가 규칙에 막히면 D1에는 아무것도 보내지 않고, "다른 기기에서 삭제 예약을 취소했습니다"를 보여 준다. 예약 시각 전이면 남은 시간을 보여 주고 그때 다시 묻는다. 끝나면 연결을 해제한다. 기기 기록은 지우지 않는다.
  - **나중에:** 연결을 유지하고 아무것도 하지 않는다. 앱을 다시 열 때 다시 묻는다(Firestore 실패 간격 적용).

#### 2.4.2 이전 전 평소 동기화
- D1에 가족이 있으면(`exists`) 평소 동기화는 그대로 돈다.
- D1에 가족이 없으면 평소 동기화와 변경 토큰 폴링은 D1에 요청하지 않는다. 동기화 상태는 "이전 준비 중"으로 보여 주고 `familyUnavailable`은 돌려주지 않는다. 이전이 끝나면 폴링을 다시 시작한다.
- `postSync`의 404(`sync.ts:332-341`), `connectFamily`의 404(`sync.ts:170-176`), 변경 토큰의 404는 이전 완료 여부와 상관없이 `familyUnavailable`로 바꾸지 않는다(불변 조건 3). 동기화 상태는 오류로 두고 "서버에서 가족 정보를 찾지 못했습니다. 기록은 이 기기에 그대로 있습니다."를 보여 준다. 410만 `familyUnavailable`로 바꾼다.

### 2.5 연결 해제 오판 방지 (결함 F)
`firestore_denied`는 2.4의 근거 조건으로 나눈다.

- 근거 조건이 맞으면 이 기기는 Firestore에서 이 가족과 실제로 연결돼 있었다. 이때 `denied`는 uid 변경이나 예전 문서 형식 때문일 수 있으므로 `firestore_error`로 낮춘다. 연결은 유지하고 실패 간격 뒤 다시 시도한다.
- 근거 조건이 없으면 초대 키가 잘못됐거나 가족이 이미 삭제된 것이다. 동기화 오류로 "가족 연결을 확인할 수 없습니다. 초대 링크를 다시 받아 주세요."를 보여 준다. 앱이 스스로 연결을 끊지는 않는다.
- 연결을 끊지 않아도 기록은 기기에 남는다. 연결을 잘못 끊으면 두 사람이 초대 링크를 다시 주고받아야 하지만, 연결을 남기면 사용자가 버튼 하나로 정리할 수 있다. 그래서 남기는 쪽을 택한다.
- `denied`가 7일 넘게 이어지면 안내를 "가족 연결을 다시 확인해 주세요. 기록은 이 기기에 그대로 있습니다."로 바꾼다. 재시도 간격은 최대 6시간이므로 하루 재시도는 몇 회에 그친다.

### 2.6 전환기 (결함 G)
- 전환기는 `firestore_ok` 병합을 마친 기기에만 있다. 시작은 `firestoreMergedAt`이고 끝은 14일 뒤다. 그 전이라도 D1 변경 토큰의 `last_client_id`가 이 기기와 다른 값으로 관측되면 상대도 1.8.0으로 옮긴 것이므로 끝낸다.
- 전환기 상태는 `@baby_cf_transition_v1:<syncKey>`에 따로 둔다. 데이터 가져오기와 백업 복원은 이 값을 지우지 않는다.

  ```ts
  type TransitionState = {
    endsAt: number;
    logCursor: number;            // 지금까지 읽은 Firestore 기록 문서 updatedAt의 최댓값
    seenFamilyChangedAt: number;  // 마지막으로 처리한 가족 문서 lastChangedAt
  };
  ```

- **커서 정의:** `logCursor`는 기기 시각이 아니라 읽은 Firestore 문서(삭제 표식 포함)의 `updatedAt` 최댓값이다. 1.7.9와 같은 방식이다(`7d4753b` `sync.ts:453-461`). 2.4의 전체 읽기에서 처음 정한다.
- **읽기 순서:** 평소 동기화가 끝난 뒤, 5분에 한 번 이하로 가족 문서 하나를 읽는다. `lastChangedAt`이 `seenFamilyChangedAt`보다 새로우면 아래를 읽고, 처리를 마친 뒤 `seenFamilyChangedAt`을 그 값으로 바꾼다.
  - `logs`에서 `updatedAt >= logCursor`인 문서. 삭제 표식(`deleted: true`)도 포함한다. 경계 문서는 다시 받지만 `mergeLogs`가 중복을 처리한다.
  - `profile/shared` 문서 하나. 프로필 LWW 규칙으로 합친다.
- `lastChangedAt`이 바뀌지 않았으면 가족 문서 1회만 읽는다. 프로필 변경 뒤에도 `seenFamilyChangedAt`이 따라가므로 같은 문서를 반복해서 읽지 않는다.
- **1.7.9 기기의 영구 삭제 감지:** 1.7.9의 삭제 예약은 `pendingDeletionAt`만 쓰고 `lastChangedAt`은 바꾸지 않는다(`7d4753b` `sync.ts:704`). 실제 삭제는 기록 문서를 표식 없이 지운다. 그래서 전환기의 가족 문서 읽기(추가 비용 없음)에서 아래 두 가지도 본다.
  - `pendingDeletionAt`이 timestamp이면 "상대 기기(이전 버전)에서 가족 서버 데이터 삭제를 예약했습니다"를 보여 주고 고르게 한다. 선택지는 **예약 취소**(Firestore에 `pendingDeletionAt: null`)와 **삭제에 따르기**, **나중에**다. 삭제에 따르기를 고르면 2.8의 1.8.0 영구 삭제 절차(D1 예약, 실제 삭제, Firestore 정리)를 이 기기에서 시작한다.
  - 가족 문서가 없거나 회원 확인이 거부되는 상태가 두 번 연속(5분 이상 간격) 관측되면, 상대가 1.7.9에서 삭제를 마친 것이다. "상대 기기(이전 버전)에서 가족 서버 데이터를 삭제했습니다. 새 서버의 사본도 삭제할까요?"를 보여 주고 고르게 한다. **삭제**를 고르면 2.8 절차를 시작하고, **유지**를 고르면 전환기를 끝낸다.
  - 어느 경우에도 앱이 스스로 D1을 지우거나 연결을 끊지 않는다. 사용자의 선택이 있어야 한다.
- 받은 기록은 기기에 합치고, 다음 평소 동기화가 D1에 올린다.
- Firestore 쪽 오류는 평소 동기화 결과에 섞지 않는다. 전환기 읽기가 실패하면 실패 간격(2.3)을 적용한다.
- 첫 이전이 끝나면 한 번 안내를 보여 준다: "새 버전부터 동기화 서버가 바뀌었습니다. 가족 모두 1.8.0으로 업데이트해야 서로의 새 기록이 보입니다."
- 전환기가 끝나면 Firestore 읽기를 멈춘다. 옛 장부는 이전 판단 근거로 남겨 둔다(수백 바이트에서 수십 KB).

### 2.7 서버 변경 (결함 C, E, H, I, J, K)
1. **삭제된 가족 기록:** 새 테이블을 둔다.

   ```sql
   CREATE TABLE IF NOT EXISTS deleted_families (
     id TEXT PRIMARY KEY,       -- familyId (SHA-256 해시)
     deleted_at INTEGER NOT NULL
   );
   ```

   - 영구 삭제 배치(`index.ts:230-232`)에 `INSERT OR IGNORE INTO deleted_families`를 함께 넣는다.
   - `POST /api/family/delete`는 D1에 가족이 없을 때도 `deleted_families`에 기록하고 성공을 돌려준다(2.4.1의 "삭제 마치기"용). 가족이 있으면 지금처럼 예약 시각을 확인한다.
   - 가족이 없을 때 모든 경로(connect, sync, token, deletion-status, schedule, cancel)는 먼저 이 테이블을 본다. 있으면 410 `family_deleted`, 없으면 404 `family_not_found`다. connect는 `allowCreate`와 상관없이 410을 돌려준다.
   - 클라이언트는 `syncWithCloud`의 catch(`sync.ts:332`)와 변경 토큰 경로(`App.tsx:388-391`의 구독 오류 처리) 양쪽에서 410을 `familyUnavailable`로 처리한다. 변경 토큰 경로는 410이면 재연결을 멈춘다.
   - 저장 값은 키의 해시뿐이라서 이 테이블에 개인정보는 없다.
   - `families`에 `firestore_origin INTEGER NOT NULL DEFAULT 0` 열을 더한다. 이어받기로 만든 가족만 1이다(2.8). connect 요청에 `fromFirestore: true`를 실어 보내면 서버가 새 가족을 만들 때 이 값을 적는다. 이미 있는 가족에는 1로만 바꿀 수 있고 0으로 되돌리지 않는다.
2. **삭제 표식 upsert:** `index.ts:292-300`을 아래처럼 바꾼다. `raw_json`은 NOT NULL이라서 최소 JSON을 넣는다.

   ```sql
   INSERT INTO logs (family_id, log_id, client_updated_at, updated_at, deleted_at, raw_json)
   SELECT ?1, ?2, 0, ?3, ?3, ?4
   WHERE EXISTS (SELECT 1 FROM families WHERE id = ?1)
   ON CONFLICT(family_id, log_id) DO UPDATE SET
     deleted_at = excluded.deleted_at, updated_at = excluded.updated_at
   WHERE logs.deleted_at IS NULL
   ```

   - `?4`는 `{"id":"<logId>","deleted":true}`다. 당겨 받기(`index.ts:367-380` 이후)가 `deleted_at`이 있는 행을 id만으로 내보내는지 구현 단계에서 확인하고, `raw_json`을 기록으로 쓰는 곳이 있으면 함께 고친다.
   - 기록 upsert도 같은 `WHERE EXISTS` 조건을 붙인다. 영구 삭제 배치와 동시에 도는 sync 요청이 고아 행을 남기지 않게 한다(2차 검토 경미 14).
   - 기록 upsert의 갱신 조건(`index.ts:284-285`)을 `excluded.client_updated_at > logs.client_updated_at OR (excluded.client_updated_at = logs.client_updated_at AND excluded.raw_json <> logs.raw_json)`로 바꾼다. 같은 버전을 다시 올려도 행을 쓰지 않고 `updated_at`도 바꾸지 않는다. 그래서 상대 기기가 같은 기록을 다시 받지 않는다.
3. **동시 생성:** 가족 생성(`index.ts:119-130`)을 `INSERT OR IGNORE INTO families`로 바꾸고, 회원 행은 `ON CONFLICT(family_id, client_id) DO UPDATE SET last_active_at = …`로 넣는다. 응답의 `isNewFamily`는 가족 `INSERT`의 변경 행 수로 정한다.
4. **나눠 보내기 (결함 J):**
   - 클라이언트는 올릴 항목을 400건 이하, 직렬화 크기 900KB 이하의 묶음으로 나눈다. 모든 `postSync` 호출이 이 규칙을 따른다. 동기화 뒤 삭제 표식을 다시 보내는 호출(`sync.ts:291-295`)도 포함하며, 이 호출에는 `skipPull: true`를 붙인다(지금은 `lastSyncedAt` 없이 보내서 매번 전체 당겨 받기를 하고 결과를 버린다).
   - 올리기 묶음에는 `skipPull: true`를 보낸다. 서버는 이 값이 있으면 쓰기만 하고 당겨 받기를 건너뛴다. 당겨 받기는 2.7-7의 순서에 따라 별도 요청으로 한다.
   - 묶음 하나가 성공할 때마다 그 묶음의 id를 새 장부의 `uploaded`, `tombstoned`에 적는다. 중간에 실패하거나 앱이 종료돼도 다음 회차는 남은 항목만 올린다.
   - 당겨 받기는 한 응답에 1,000행까지만 돌려준다. 서버는 `(updated_at, log_id)` 순서로 정렬하고 `hasMore`와 `nextAfter`(마지막 행의 `updated_at`, `log_id`)를 함께 준다. 클라이언트는 `hasMore`가 거짓일 때까지 이어서 받는다. 전체 모드의 정렬도 `client_updated_at`이 아니라 같은 키로 바꾼다.
   - 페이지를 받을 때마다 그 페이지를 기기에 합쳐 저장하고, 장부에 `pullAfter`(다음 페이지 시작 위치)를 적는다. 그래서 20초 상한(`App.tsx:36`)에 걸리거나 앱이 종료돼도 다음 회차는 받은 페이지를 다시 받지 않고 이어서 받는다. 저장은 합치기라서 중간에 끊겨도 기록이 줄지 않는다.
   - 장부에 `pendingFull: boolean`을 둔다. 전체 모드가 모든 페이지를 받고 차이 업로드를 마칠 때까지는 `lastFullReadAt`을 갱신하지 않는다. 다음 회차는 `pullAfter`부터 전체 모드를 이어 간다.
   - 무료 Workers의 CPU 한도에서 1,000행 페이지가 동작하는지는 `wrangler dev --local`과 배포 후 확인에서 잰다. 한도에 걸리면 한 응답의 행 수를 줄인다.
5. **커서 여유 (결함 K):** 서버는 각 응답의 커서 후보를 `serverTime - 120000`(2분 전)으로 돌려준다. 다른 요청이 그보다 이른 `serverTime`으로 늦게 확정한 행도 다음 당겨 받기에 들어온다. 다시 받는 행은 `mergeLogs`가 중복을 처리한다.
   - 여러 페이지를 받을 때 장부의 최종 커서(`cursorMillis`)는 **첫 페이지 응답의 커서 후보**(가장 이른 값)로 정한다. 뒤 페이지의 값을 쓰면 첫 페이지 이후 늦게 확정된 행을 건너뛸 수 있다.
   - 오프라인 재시도처럼 회차 사이가 2분을 넘어도, 다음 회차가 저장된 커서부터 다시 받으므로 문제가 없다.
6. **키 길이와 대소문자:** 배포 전 실데이터 점검(5장)에서 실사용자 키가 16~64자인지, 대문자가 있는지 확인한다. 범위를 벗어난 키가 있으면 서버 정규식을 그 키가 통과하도록 넓힌다. D1 해시는 소문자 키 기준이고 Firestore 해시는 원래 키 기준이므로, 이전 모듈은 두 해시를 각자 기준대로 만든다. 확인 전에는 서버 정규식을 바꾸지 않는다.
7. **차이 업로드 (3차 검토):** 전체 모드는 "서버의 모든 행을 당겨 받는다"는 뜻으로만 쓴다. 올리기는 모든 기록이 아니라 차이만 보낸다.
   - 순서: (1) 당겨 받기 페이지를 모두 받는다. 이때 서버 행의 `log_id`별 `client_updated_at`과 삭제 여부를 메모리에 모은다. (2) 기기 기록 가운데 서버에 없거나, 기기의 `updatedAt`이 서버 값보다 크거나, 같은 버전인데 내용이 다른 기록만 올린다. (3) 기기 삭제 표식 가운데 서버에서 아직 삭제되지 않은 id만 올린다.
   - 증분 모드는 지금처럼 장부(`uploaded`, `tombstoned`)와 비교해 바뀐 것만 올린다.
   - 1.7.9의 전체 대조도 같은 방식이었다(`7d4753b` `sync.ts:539-559`).
   - 그래서 전체 대조와 당겨서 새로고침(`App.tsx:562`의 `forceFullRead`)이 D1에 쓰는 행은 바뀐 기록 수만큼이다(4.1).

### 2.8 영구 삭제 (결함 C)
- 1.8.0의 영구 삭제는 D1과 Firestore 양쪽을 지운다. 사용자는 "가족 서버 데이터 영구 삭제"를 요청했으므로, Firestore에 사본이 남으면 그 요청을 지키지 못한다.
- **Firestore 사본이 있는 가족의 표시:** 이어받기(`missing` + `ok`)로 D1 가족을 만들 때 `families.firestore_origin = 1`을 적는다. connect 응답과 deletion-status 응답에 이 값을 싣는다. 그래서 1.7.9 시절 근거가 없는 기기(1.8.0에서 합류한 기기)가 삭제해도 Firestore 정리를 한다. 이 기기도 가족 키를 알고 있으므로 초대 해시로 회원 문서를 만들어 삭제할 수 있다. `firestore_origin`이 0인 가족은 Firestore에 요청하지 않는다.
- **예약:** D1 예약을 먼저 한다. 성공하면 Firestore 가족 문서에 `pendingDeletionAt`을 D1과 같은 시각(지금부터 60분 뒤)으로 쓴다. 규칙은 지금부터 50분 뒤보다 늦은 시각만 받는다. Firestore 쓰기가 실패해도 D1 예약은 그대로 두고, 정리 대기에 `schedule` 작업을 남긴다.
- **취소:** D1 취소와 함께 Firestore에 `pendingDeletionAt: null`을 쓴다. 이 키의 정리 대기 항목이 `schedule`이면 지운다(예약이 반영되지 않았으므로 취소할 것도 없다). Firestore 쓰기가 실패했고 예약이 반영돼 있었으면 `cancel` 작업으로 바꾼다.
- **삭제:** D1을 먼저 지운다. D1 배치가 `deleted_families`를 남기므로, 이후 Firestore 삭제가 도중에 실패해도 가족은 되살아나지 않는다. D1 삭제가 성공한 뒤에만 1.7.9의 `deleteFamilyCloudData` 순서로 Firestore를 지운다. 실패하면 정리 대기에 `delete` 작업을 남긴다.
- **정리 대기:** `@baby_cf_firestore_cleanup_v1`에 가족 키마다 항목 **하나**만 둔다. 같은 키의 새 작업은 앞 작업을 대신한다.

  ```ts
  type CleanupEntry = {
    syncKey: string;      // inviteHash를 다시 만들려면 키가 필요하다 (키는 이미 프로필에 평문으로 저장돼 있다)
    action: 'schedule' | 'cancel' | 'delete';
    nextAttemptAt: number;
    attempts: number;
  };
  ```

  - 연결을 해제해도 이 항목은 지우지 않는다. 재시도는 30분부터 두 배씩 늘려 최대 24시간 간격으로 한다.
  - **모든 재시도는 D1 상태를 먼저 확인한다.** deletion-status를 부르고, 그 결과가 작업과 맞지 않으면 Firestore에 요청하지 않고 항목을 지운다.
    - `schedule`: D1에 예약이 그대로 있을 때만 진행한다. D1 예약이 취소됐으면 항목을 지운다. D1이 410이면 이미 삭제된 것이므로 `delete`로 바꾼다. 진행할 때는 `max(D1 예약 시각, 지금부터 60분 뒤)`로 Firestore에 예약을 쓴다.
    - `cancel`: D1에 예약이 없을 때만 진행한다. D1에 다시 예약돼 있으면 `schedule`로 바꾼다. 진행할 때는 Firestore에 `pendingDeletionAt: null`을 쓴다.
    - `delete`: D1이 410(삭제 확정)일 때만 진행한다. `delete` 항목은 D1 삭제가 성공한 뒤에만 생기므로 정상이라면 항상 410이다. 410이 아니면 Firestore를 지우지 않고 항목을 지운 뒤 오류로 기록한다.
  - `delete` 진행은 가족 문서 1건만 먼저 읽는다. 문서가 없거나 회원 생성이 거부되면 끝난 것으로 보고 항목을 지운다. `pendingDeletionAt`이 timestamp가 아니면 지금부터 60분 뒤로 예약을 쓰고 그 시각 뒤로 미룬다. D1 삭제가 이미 확정됐으므로 이 재예약은 사용자의 삭제 요청을 마치는 쓰기다. 예약 시각 전이면 그 시각 뒤로 미룬다. 예약 시각이 지났을 때만 기록과 회원 목록을 읽고 지운다. 그래서 규칙에 막힌 삭제 때문에 기록 N건을 반복해서 읽지 않는다.
  - 화면에는 "서버의 예전 사본 정리가 남아 있습니다"를 보여 준다.

### 2.9 새로 만드는 가족과 합류
- `allowFamilyCreation=true`로 새 가족을 만들면 Firestore에 있을 수 없으므로 `firestoreMergedAt`과 `d1UploadedAt`을 바로 적는다. Firestore를 읽지 않고 전환기도 없다.
- 초대 링크로 합류하는 기기는 2.4를 밟는다. D1에 가족이 있고 근거 조건이 없으면 Firestore를 읽지 않으므로(2.4-3), 1.8.0에서 만든 가족에 합류하는 기기의 Firestore 요청은 0회다.

### 2.10 이전 직전 백업 복원 (결함 L)
- 설정 화면의 백업 목록에 `@baby_pre_cloudflare_backup_v1`을 "1.8.0 업데이트 직전 기록"으로 보여 준다.
- `restoreFromLocalBackup`(통째로 바꾸기, `storage.ts:556-582`)과 `importDataWithoutLoss`(`storage.ts:457` 이하)는 쓰지 않는다. `importDataWithoutLoss`는 기기에서 지운 기록을 `restored-<digest>`라는 새 id로 되살리고(`storage.ts:480-492`), 프로필을 백업 값으로 덮어쓰며(`storage.ts:500-515`), 옛 장부를 지운다(`storage.ts:522`).
- 전용 함수 `restorePreMigrationBackup()`을 새로 만든다.
  - 백업 기록 가운데 id가 지금 기기 기록에도 없고 지금 프로필의 `deletedLogIds`에도 없는 기록만 추가한다. 새 id를 만들지 않는다.
  - 추가하는 기록의 `updatedAt`은 백업 값 그대로 둔다. 서버에 같은 id가 더 새 버전으로 있으면 다음 동기화에서 서버 쪽이 이긴다.
  - 프로필과 삭제 표식은 바꾸지 않는다.
  - 장부(새 장부, 옛 장부), 이전 상태(2.2), 근거 표식(2.2), 전환기 상태(2.6)는 지우지 않는다. 그래서 Firestore를 다시 읽지 않는다.
  - 저장은 `saveSyncedDataWithoutLoss`와 같은 합치기 저장으로 한다.
- 추가한 기록은 장부에 없으므로 다음 증분 동기화가 D1에 올린다.
- 이 백업은 사용자가 지우기 전까지 남긴다.

### 2.11 혼자 쓰기 (동기화 없음)
- 가족 연결 키(`syncKey`)가 없는 사용자는 지금처럼 기기 안에서만 기록을 저장한다. 현재 `App.tsx`의 동기화 진입점(초기 로드, 변경 구독, 저장 후 동기화, 새로고침)은 모두 `syncKey`가 있을 때만 돈다. 이 동작을 유지한다.
- `syncKey`가 없으면 Cloudflare와 Firestore에 요청을 한 번도 보내지 않는다. 이전 단계와 전환기 읽기도 실행하지 않고, `firebase.ts`도 불러오지 않는다. 예외는 2.8의 정리 대기 항목이 남은 경우뿐이다(사용자가 요청한 삭제를 마치기 위한 요청).
- 혼자 쓰다가 나중에 가족을 만들거나 초대 링크로 합류하면, 그때 기기의 기록 전체가 D1에 올라간다(2.1의 전체 모드, 2.7-4의 나눠 보내기).
- 가족 연결을 해제하면 기록은 기기에 남고 혼자 쓰기로 돌아간다. 지금 동작과 같다.

## 3. 바꾸지 않는 것
- Firestore에는 불변 조건 2에 적은 쓰기 외에는 아무것도 쓰지 않는다. Firestore 데이터는 그대로 남는다.
- `firestore.rules`는 바꾸지 않는다.
- 이전 안내, 삭제 예약 선택 화면, 오류 문구, 백업 목록 항목 외에 사용자 화면은 바꾸지 않는다.
- 실사용자에게 앱 삭제나 재설치를 안내하지 않는다. Android는 앱을 지워야 이전 버전으로 되돌릴 수 있으므로 "1.7.9로 되돌리기"는 지원 경로로 두지 않는다.

## 4. Firestore 할당량 예산
하루 읽기 5만, 쓰기 2만은 1.7.9 사용자를 포함한 프로젝트 전체가 함께 쓴다. 기록 N건인 가족 하나의 하루 최대치는 아래와 같다.

| 항목 | 읽기 | 쓰기 | 조건 |
|---|---|---|---|
| 첫 이전 | N + 3 | 1 (회원 문서) | 기기당 1회. 성공하면 다시 하지 않는다. |
| 가벼운 실패 재시도 | 회당 3 | 회당 최대 1 | 30분부터 늘려 최대 6시간 간격. 첫날 최대 7회 |
| 무거운 실패 재시도 | 회당 버리는 읽기 최대 500 + 3 | 회당 최대 1 | 1시간부터 늘려 최대 12시간 간격. 첫날 최대 5회. 읽은 페이지는 다시 읽지 않는다. |
| 전환기 가족 문서 | 288 | 0 | 기기당, 5분 간격, 14일 이내 |
| 전환기 증분 | 상대가 바꾼 문서 수 + 1 | 0 | `lastChangedAt`이 바뀐 때만 |
| 영구 삭제 정리 | 1 (대기 중) / N + 회원 수 (실행) | N + 회원 수 + 2 | 사용자가 삭제를 요청한 경우만 |
| 1.8.0 신규 가족 | 0 | 0 | 불변 조건 6 |

- 실사용자 가족이 둘이고 N을 각각 3,000으로 잡는다. 첫날 최악은 기기 네 대가 모두 무거운 실패를 다섯 번씩 겪는 경우다. 이때 읽기는 4 × (3,003 + 5 × 503 + 7 × 3 + 288) ≈ 2만 4천 회로, 하루 한도의 절반 이하다. 정상 경로는 4 × (3,003 + 288) ≈ 1만 3천 회다.
- 페이지 나눠 읽기가 없으면 실패할 때마다 N건을 다시 읽는다. 이때 가벼운 실패와 같은 간격(하루 7회)을 쓰면 최악이 4 × (7 × 3,003 + 288) ≈ 8만 5천 회가 되어 한도를 넘는다. 페이지 나눠 읽기와 진행 위치 저장이 이 예산의 전제다.
- 6장 점검에서 실제 N을 확인한 뒤 이 표를 실측값으로 고친다. 최악 합계가 한도의 60%를 넘으면 무거운 실패 간격의 시작값을 늘린다.

### 4.1 D1 예산
D1 무료 등급은 하루 읽기 500만 행, 쓰기 10만 행이다(구현 첫 단계에서 Cloudflare 문서로 수치와 인덱스 행 집계 방식을 확인한다). 이 값은 모든 가족이 함께 쓴다.

| 항목 | 읽기 행 | 쓰기 행 (인덱스 포함 추정) | 조건 |
|---|---|---|---|
| 첫 이전 업로드 | 약 N | 약 2N | 가족당 1회. 두 번째 기기는 2.7-7의 차이 업로드로 바뀐 기록만 쓴다. |
| 전체 대조 (6시간마다, 새로고침) | 약 N | 바뀐 기록 수 × 2 | 2.7-7. 같은 버전은 다시 쓰지 않는다. |
| 증분 동기화 | 바뀐 행 수 | 바뀐 기록 수 × 2 | 저장할 때마다 |

- 차이 업로드(2.7-7)가 없으면 전체 대조 때마다 약 2N행을 쓴다. N=3,000, 기기 2대, 하루 4회면 가족당 4만 8천 행이고, 두 가족이면 한도에 이른다. 차이 업로드가 이 예산의 전제다.

## 5. 검증 계획

### 5.1 실제 서버 코드로 검증
- 서버 변경(2.7)은 가짜 Worker가 아니라 실제 `server/src/index.ts`로 검증한다. Node 24의 `node:sqlite`로 D1 흉내(`prepare`, `bind`, `first`, `all`, `run`, `batch`)를 만들고, `server/schema.sql`을 적용한 메모리 DB 위에서 Worker의 `fetch`를 직접 부른다. 하네스에는 `HARNESS_REAL_WORKER=1` 모드를 추가하고, 클라이언트의 `fetch`를 이 Worker로 보낸다.
- D1 흉내는 `run()` 결과에 `meta.changes`를 담는다(2.7-3의 `isNewFamily` 판정용).
- 실제 서버 모드에는 두 가지 훅을 둔다.
  - **서버 시계 주입:** Worker의 `Date.now()`를 시험이 정한 값으로 바꾼다.
  - **확정 지연:** 특정 요청의 `env.DB.batch` 확정을 시험이 풀어 줄 때까지 멈춘다. 결함 K(동시 업로드 커서)를 재현하고, 2분 여유를 빼는 변이가 시나리오 5에서 실패하게 만든다.
- 서버 변이는 이 모드에서만 판정한다. 가짜 Worker는 클라이언트만 보는 빠른 검사에 남기고, 한도(500건, 1MB), 삭제 표식 upsert, 같은 버전 무시를 실제 서버와 맞춘다.

### 5.2 가짜 Firestore
- 지금 `loader.mjs:22-24`는 `./firebase`와 `firebase/firestore`를 모두 가짜 Worker로 보낸다. `context.parentURL`을 보고 `firestoreImport.ts`와 새 `firebase.ts`에서 온 import만 `stubs/fake-firestore.mjs`로 보낸다.
- 가짜 Firestore가 흉내 내는 것:
  - `firestore.rules`의 회원 생성 규칙(`inviteHash` 일치, 예전 문서의 `inviteHash` 없음), 회원이 아닐 때의 읽기 거부, 삭제 규칙과 50분 예약 조건
  - `pendingDeletionAt`의 timestamp, `null`, 부분 삭제 상태
  - 끝나지 않는 호출(상한 검사용), `resource-exhausted` 오류
  - 문서 단위 읽기·쓰기 수 집계
  - `terminate` 호출과 그 뒤 재생성
  - 쓰기와 읽기 사이에 다른 기기의 쓰기를 끼워 넣는 훅 (커서 검사용)

### 5.3 시나리오
1. Firestore 장부가 남은 기기가 업데이트하면, 첫 D1 동기화가 기록 전체를 D1에 올린다. (결함 B)
2. 두 기기가 차례로 업데이트해도 어느 쪽도 연결이 해제되지 않고, 둘의 기록이 D1에서 합쳐진다. (결함 A)
3. **부활:** 1.8.0에서 영구 삭제한 가족에 다른 기기가 이전을 시도하면 410을 받고 D1에 가족이 생기지 않는다. 변경 토큰 경로도 410에서 재연결을 멈춘다. (결함 C)
4. **삭제 예약 중인 가족:** Firestore 가족 문서의 `pendingDeletionAt`이 미래 또는 과거 timestamp이면 이어받지 않고 연결도 끊지 않는다. `null`이면 이어받는다. "예약 취소하고 계속 쓰기"를 고르면 1.8.0 기기만으로 이어받기까지 끝난다. "삭제 마치기"를 고르면 Firestore에서 가족이 사라지고 D1은 410을 돌려준다. (결함 C, 2.4.1)
5. **동시 생성:** 두 기기가 같은 키로 동시에 이어받아도 둘 다 성공하고, 가족 행은 하나이며, 다음 동기화 1회 안에 서로의 기록을 받는다. (결함 H, K)
6. **삭제 표식 보존:** 이전 직후 빈 D1에 삭제 표식을 올린 뒤, 다른 기기가 같은 기록을 올려도 되살아나지 않는다. (결함 E, 실제 서버 모드)
7. **uid 변경:** 근거 조건이 있는 기기에서 회원 생성이 거부되면 연결을 유지하고 실패 간격 뒤 다시 시도한다. 근거 조건이 없으면 오류만 보여 주고 연결은 끊지 않는다. (결함 F)
8. **강제 종료 시점:** 아래 지점마다 중단하고 다시 시작해도 기록이 줄지 않는다.
    - 백업 직후, Firestore 페이지 읽기 중간(다음 시도는 저장된 위치부터 읽고 읽은 페이지를 다시 읽지 않는다), 병합 저장 직후
    - D1 당겨 받기 페이지 중간(다음 회차는 `pullAfter`부터 받는다), 올리기 묶음 중간, 마지막 묶음 직후
    - 이전 7단계와 평소 동기화가 같은 시기에 요청돼도 대기열 덕분에 장부의 `pendingFull`과 `uploaded`가 되돌아가지 않는다.
9. **이전 중 가족 전환:** 이전 단계가 도는 동안 다른 가족 키로 바꾸면, 앞 가족의 병합 결과가 새 가족 상태에 섞이지 않는다.
10. **이전 직후 복원:** 이전 뒤 아래 상태에서 이전 직전 백업을 복원한다. 복원 뒤 두 기기가 동기화를 마쳤을 때, 추가한 기록과 상대의 수정이 그대로 남고, 지운 기록이 어떤 id로도 되살아나지 않으며, 아기 정보는 상대가 고친 값이다. Firestore를 다시 읽지 않는다. (결함 L)
    - 이 기기에서 기록 하나 추가, 백업에 있던 기록 하나 삭제
    - 상대 기기에서 백업에 있던 기록 하나 수정, 아기 정보 수정
11. **전환기 중 복원과 가져오기:** 전환기 중에 백업 복원이나 데이터 가져오기를 해도 전환기 커서가 유지되고, 다음 전환기 읽기가 전체 읽기로 바뀌지 않는다.
12. **A→B 전달과 커서:** A만 업데이트한 상태에서 B(1.7.9)가 Firestore에 쓴 기록, 삭제, 프로필 변경이 A에 들어오고, A가 받은 기록이 D1에 올라간다. A의 전체 읽기와 커서 기록 사이에 B의 쓰기를 끼워 넣어도 그 쓰기가 누락되지 않는다. B가 프로필만 고친 뒤에는 가족 문서 외의 읽기가 반복되지 않는다. 상대 변경 토큰이 보이면 전환기가 끝난다. (결함 G)
13. **하루 읽기 총량:** 기록 3,000건 가족에서 아래를 흉내 냈을 때 가짜 Firestore 집계가 4장 표의 상한 이하다. (결함 D)
    - 정상 이전 1회 + 하루 동안 저장 100회 + 90초 주기 동기화
    - Firestore가 하루 종일 실패하는 경우 (재시도 간격 확인)
    - 1.8.0에서 새로 만든 가족과 그 가족에 합류한 기기 (Firestore 요청 0회). 혼자 쓰던 기기가 1.8.0을 처음 실행한 뒤 가족에 합류하는 경우와, 새로 설치한 기기가 합류하는 경우를 모두 포함한다. 재시작을 여러 번 해도 0회다.
14. **상한:** Firestore 호출이 끝나지 않으면 15초 뒤 `terminate`가 불리고, 다음 시도는 새 인스턴스로 동작한다. 평소 동기화는 20초 상한과 별개로 계속 돈다. (결함 D)
15. Firestore 오류와 D1 없음이 겹치면 연결을 유지하고 `familyUnavailable`을 주지 않는다. 다음 회차에 Firestore가 살아나면 이어받는다. D1 네트워크 실패에는 Firestore 실패 간격이 적용되지 않는다.
16. 이전 직전 백업은 첫 상태 그대로 남고, 두 번째 이전 시도가 덮어쓰지 않는다. 백업 저장이 실패하면 사용자가 고르기 전까지 이전을 시작하지 않는다.
17. `syncKey` 없이 기록을 추가, 수정, 삭제하고 앱을 다시 열어도 Cloudflare와 Firestore 요청이 0회이고, 기록은 기기에 그대로 남는다.
18. 혼자 쓰던 기기(기록 1,200건, 삭제 표식 300건)가 새 가족을 만들면 기존 기록 전체가 나눠 보내기로 D1에 올라가고, 합류한 두 번째 기기가 그 기록을 모두 받는다. (결함 J)
19. **영구 삭제:**
    - 1.8.0에서 영구 삭제하면 D1과 가짜 Firestore 양쪽에서 가족이 사라진다. 1.8.0에서 합류한 기기가 삭제해도(`firestore_origin = 1`) 같다.
    - D1 삭제 뒤 Firestore 삭제가 실패하면 정리 대기가 다시 예약하고, 예약 시각 전 재시도는 가족 문서 1건만 읽는다. 예약 시각 뒤 정리가 끝난다.
    - **취소 존중:** 예약 → Firestore 예약 쓰기 실패 → 사용자가 취소 → 정리 대기 간격이 여러 번 지나도 Firestore 가족과 기록이 그대로 있고, 상대(1.7.9) 기기의 동기화가 계속된다. 예약만 하고 최종 삭제를 누르지 않은 경우도 같다.
20. **500건 초과 평소 동기화:** 이전과 상관없이 기록 3,000건 가족의 전체 대조와 당겨 받기가 실제 서버 모드에서 성공한다. 당겨 받기 페이지 사이에 다른 기기의 확정을 끼워 넣어도(확정 지연 훅) 그 기록을 다음 회차에 받는다. (결함 J, K)
21. **404 보존:** 이전을 마친 두 기기에서 D1을 비운 상태(서버 설정 오류 흉내)로 동기화해도 연결이 끊기지 않고 오류만 보인다. D1을 되돌리면 동기화가 다시 이어진다. (불변 조건 3)
22. **전환기 중 1.7.9 삭제:** A만 이전한 상태에서 B(1.7.9)가 삭제를 예약하면 A에 선택 화면이 뜬다. B가 삭제를 마치면 A에 "새 서버 사본도 삭제할까요?"가 뜬다. A가 고르기 전까지 D1은 그대로이고 연결도 유지된다. (3차 검토)
23. **D1 쓰기량:** 기록 3,000건 가족에서 바뀐 기록 없이 전체 대조와 당겨서 새로고침을 반복해도 D1 기록 행 쓰기는 0이고, 상대 기기의 다음 증분 당겨 받기는 0행이다. 기록 하나를 고치면 쓰기는 그 행 하나다. (4.1)
24. **삭제 재전송:** 동기화 뒤 삭제 표식 재전송 호출(`sync.ts:291-295`)은 `skipPull: true`로 가고, 표식이 500건을 넘으면 나눠서 간다.

## 6. 배포 전 실데이터 점검 (읽기 전용)
배포 전에 실사용자 두 가족을 읽기만 해서 아래를 확인하고 결과를 이 문서에 적는다. Firestore에는 쓰지 않는다.

- 가족 키 길이, 대문자 포함 여부 (서버 정규식 16~64자 통과 여부)
- 가족 문서의 `inviteHash`, `pendingDeletionAt`(값의 종류), `lastChangedAt` 유무
- `logs` 문서 수와 삭제 표식 수 (4장 예산을 실측값으로 고친다)
- 회원 문서 수

점검 방법은 구현 단계에서 정한다. 읽기 전용 스크립트를 쓰고, 실행 전에 성기님에게 확인을 받는다. 키와 해시는 화면에 그대로 출력하지 않고 길이와 앞 4자만 보여 준다.

## 7. 남은 판단
- 전환기 14일, 실패 간격(30분에서 6시간), 묶음 크기(400건, 900KB), 당겨 받기 1,000행, 커서 여유 2분은 추정값이다. 6장 점검과 배포 후 확인에서 실측해 고친다.
- `terminate` 뒤 `initializeFirestore` 재호출 가능 여부는 구현 첫 단계에서 확인한다(2.3).
