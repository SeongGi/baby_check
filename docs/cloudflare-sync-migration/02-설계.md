# 02-설계: Cloudflare Workers + D1 기반 데이터 동기화 시스템

## 1. 시스템 아키텍처 개요

```
┌────────────────────────────────────────────────────────┐
│                 Baby-Check Mobile App                  │
│                                                        │
│  [ UI Screens ] (LogFormula, Profile, Main, etc.)      │
│        ▲                                               │
│        ▼                                               │
│  [ Database Layer ]                                    │
│    - storage.ts (AsyncStorage 로컬 저장/장부 보존)      │
│    - sync.ts (LWW 충돌 병합, 오프라인 큐, 상태 관리)    │
│    - cloudClient.ts (Cloudflare REST 통신 모듈)        │
└──────────────────────────┬─────────────────────────────┘
                           │ HTTPS REST / JSON
                           ▼
┌────────────────────────────────────────────────────────┐
│              Cloudflare Edge Network                   │
│                                                        │
│  Cloudflare Worker (TypeScript 경량 라우터)            │
│    - syncKey SHA-256 인증 및 가족 데이터 완전 격리     │
│    - D1 batch 기반 원자적 증분 동기화 및 LWW 충돌 해결 │
│    - 에코 루프 방지 (last_client_id 기반 감지)         │
│    - 1시간 냉각 기간 가족 삭제 수명주기 관리           │
│                                                        │
│  Cloudflare D1 (Serverless SQLite)                     │
│    - families / members / logs 테이블                  │
└────────────────────────────────────────────────────────┘
```

---

## 2. 보안 및 인증 모델

1. **가족 인증 키 (`syncKey`) 및 단방향 격리**:
   * 기존과 동일하게 32자리 16진수 랜덤 키 (`createFamilySyncId()`).
   * 클라이언트는 `syncKey`를 소유하며, 모든 API 요청의 `Authorization: Bearer <syncKey>` 헤더로 전송.
   * Worker는 DB에 원본 `syncKey`를 저장하지 않고 단방향 SHA-256 해시인 `familyId`를 산출하여 인덱싱:
     $$\text{familyId} = \text{SHA-256}(\text{"babycheck:family:v2:"} + \text{syncKey})$$
   * 모든 D1 쿼리는 `WHERE family_id = ?`로 엄격히 스코핑되어 타 가족의 데이터 접근이 수학적으로 불가능.
2. **익명 클라이언트 식별 (`clientId`)**:
   * 기기별 고유 UUID를 로컬에 영구 보존하며, `X-Client-Id` 헤더로 전달.
   * `families.last_client_id` 추적을 통해 변경을 일으킨 기기 본인의 에코 루프(불필요한 자기 풀)를 차단.
3. **요청 보호 및 한도 관리**:
   * 본문 크기 제한 (최대 1MB), 단일 동기화 배치 수 제한 (최대 500개 기록).
   * 악의적인 요청 시도를 막기 위한 기본 검증(유효한 32자리 16진수 키 포맷 검사).

## 3. Cloudflare D1 데이터베이스 스키마

D1은 SQLite 기반 서버리스 DB이며, 상호작용 트랜잭션 대신 `db.batch([...])`를 통한 원자적 일괄 실행을 지원합니다. 외래키 캐스케이드에 의존하지 않고 명시적 배치 삭제를 수행합니다.

```sql
-- families: 가족 그룹 메타데이터 및 공용 프로필
CREATE TABLE IF NOT EXISTS families (
  id TEXT PRIMARY KEY,                       -- familyId (SHA-256 해시)
  created_at INTEGER NOT NULL,               -- 생성 시각 (밀리초)
  updated_at INTEGER NOT NULL,               -- 마지막 변경 시각 (토큰용)
  last_client_id TEXT DEFAULT NULL,          -- 마지막으로 변경을 커밋한 클라이언트 ID
  deletion_ready_at INTEGER DEFAULT NULL,    -- 삭제 예약 시각 (1시간 냉각 기간 종료 시점)
  shared_name TEXT,                          -- 아기 이름
  shared_birth_date TEXT,                    -- 생년월일
  shared_birth_weight TEXT,                  -- 출생 체중
  shared_target_formula INTEGER,             -- 목표 수유량
  profile_updated_at INTEGER DEFAULT 0       -- 프로필 수정 시각
);

-- members: 연결된 가족 기기 목록
CREATE TABLE IF NOT EXISTS members (
  family_id TEXT NOT NULL,
  client_id TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  last_active_at INTEGER NOT NULL,
  PRIMARY KEY (family_id, client_id)
);

-- logs: 육아 기록 (유연한 raw_json 스토리지 + 증분 색인)
CREATE TABLE IF NOT EXISTS logs (
  family_id TEXT NOT NULL,
  log_id TEXT NOT NULL,
  client_updated_at INTEGER NOT NULL,        -- 클라이언트 측정/수정 시각 (LWW 충돌 판정용)
  updated_at INTEGER NOT NULL,               -- 서버 수신 시각 (증분 풀 커서용)
  deleted_at INTEGER DEFAULT NULL,           -- 삭제 표식 (tombstone)
  raw_json TEXT NOT NULL,                    -- 전체 BabyLogEntry JSON
  PRIMARY KEY (family_id, log_id)
);

CREATE INDEX IF NOT EXISTS idx_logs_family_updated 
ON logs (family_id, updated_at);
```

## 4. 백엔드 API 명세 (Cloudflare Worker)

### 1) `POST /api/family/connect`
* **목적**: 가족 연결 또는 신규 가족 생성
* **요청 헤더**: `Authorization: Bearer <syncKey>`, `X-Client-Id: <clientId>`
* **요청 본문**: `{ "allowCreate": boolean }`
* **동작**:
  * `familyId`로 `families` 조회.
  * 존재하면 `members`에 `(family_id, client_id, now, now)` upsert 후 `{ "ok": true, "isNewFamily": false }` 반환.
  * 존재하지 않을 때:
    * `allowCreate === true`: 신규 행 삽입 후 `{ "ok": true, "isNewFamily": true }` 반환.
    * `allowCreate === false`: `404 Not Found`, `{ "ok": false, "error": "family_not_found" }` 반환.

### 2) `GET /api/family/token`
* **목적**: 실시간 변경 감지용 초경량 토큰 조회 (Head/Get)
* **응답 본문**:
  ```json
  {
    "ok": true,
    "changeToken": "1700000005000:client-uuid-1",
    "profileUpdatedAt": 1700000002000,
    "deletionReadyAt": null
  }
  ```
  * `changeToken`: `${families.updated_at}:${families.last_client_id}` 조합으로, 클라이언트가 본인 변경 시 즉시 풀 루프를 방지.
  * `deletionReadyAt`: 가족 삭제 예약 여부를 UI에 즉시 반영할 수 있도록 제공.

### 3) `POST /api/family/sync`
* **목적**: 증분 푸시 및 풀을 한 번의 왕복으로 완료
* **요청 본문**:
  ```json
  {
    "lastSyncedAt": 1700000000000,
    "pushLogs": [ ...BabyLogEntry ],
    "pushProfile": { ...Partial<BabyProfile> },
    "pushDeletedIds": [ "id1", "id2" ]
  }
  ```
* **동작 및 LWW 충돌 해결 규칙**:
  1. `families` 존재 여부 확인. 없으면 `404` (`family_not_found`) 반환 -> 클라이언트는 `familyUnavailable: true`로 처리.
  2. $T_{\text{server}} = \text{Date.now()}$.
  3. **로그 푸시 및 묘비명(tombstone) 보호**:
     * 이미 삭제된 로그(`deleted_at IS NOT NULL`)는 푸시로 되살아나지 않아야 함.
     * 기존 원격 로그가 더 최신(`client_updated_at > pushLog.client_updated_at`)이면 덮어쓰지 않음.
     * SQLite 조건부 구문:
       ```sql
       INSERT INTO logs (family_id, log_id, client_updated_at, updated_at, deleted_at, raw_json)
       VALUES (?1, ?2, ?3, ?4, NULL, ?5)
       ON CONFLICT(family_id, log_id) DO UPDATE SET
         client_updated_at = excluded.client_updated_at,
         updated_at = excluded.updated_at,
         raw_json = excluded.raw_json
       WHERE logs.deleted_at IS NULL 
         AND excluded.client_updated_at >= logs.client_updated_at;
       ```
  4. **삭제 표식(`pushDeletedIds`) 적용**:
     ```sql
     UPDATE logs SET deleted_at = ?serverTime, updated_at = ?serverTime
     WHERE family_id = ?familyId AND log_id IN (?ids);
     ```
  5. **프로필 갱신**:
     * `pushProfile`이 있고 `pushProfile.sharedUpdatedAt > families.profile_updated_at`일 때만 공유 필드 갱신.
  6. **증분 풀 (`remoteLogs`, `remoteDeletedIds`)**:
     * `lastSyncedAt === 0`: 활성 로그만 전체 조회 (`deleted_at IS NULL`).
     * `lastSyncedAt > 0`: `updated_at > lastSyncedAt`인 변경 로그 조회. `deleted_at IS NOT NULL`인 것은 `remoteDeletedIds`로, 나머지는 `remoteLogs`로 분리.
  7. 모든 쓰기와 조회를 `db.batch()`로 묶어 원자적 완료.
* **응답 본문**:
  ```json
  {
    "ok": true,
    "serverTime": 1700000005000,
    "remoteLogs": [ ...BabyLogEntry ],
    "remoteDeletedIds": [ "id3" ],
    "remoteProfile": { ...Partial<BabyProfile> },
    "supersededIds": [ "id4" ]
  }
  ```

### 4) 가족 삭제 관리 엔드포인트
* `POST /api/family/delete-schedule`:
  * `deletion_ready_at = Date.now() + (60 * 60 * 1000)` (1시간 냉각 기간으로 `Profile.tsx`와 일치).
* `POST /api/family/cancel-delete`:
  * `deletion_ready_at = NULL` 초기화.
* `POST /api/family/delete`:
  * `deletion_ready_at`이 경과했거나 요청에 따라 명시적 원자적 삭제:
    ```sql
    DELETE FROM logs WHERE family_id = ?;
    DELETE FROM members WHERE family_id = ?;
    DELETE FROM families WHERE id = ?;
    ```
* `GET /api/family/deletion-status`:
  * 현재 가족의 삭제 예약 상태 `{ "scheduled": boolean, "readyAt": number | null, "canDeleteNow": boolean }` 반환.

## 5. 클라이언트 (`sync.ts`) 변경 및 기존 코드 호환성

* **기존 인터페이스 100% 보존**:
  * `createFamilySyncId()`, `createFamilyInviteLink()`, `parseFamilySyncId()`: 그대로 유지.
  * `syncWithCloud(...)`: `cloudClient.postSync(...)` 호출 및 LWW 병합 로직 유지.
  * `readFamilyChangeToken(...)`: `cloudClient.getToken(...)` 호출.
  * `subscribeToCloudChanges(...)`: 상시 WebSocket 대신, 포그라운드 복귀 시(`AppState === 'active'`) 즉시 대조 + 활성 상태 90초 주기 토큰 대조.
  * `scheduleFamilyDeletion(...)`, `cancelFamilyDeletion(...)`, `deleteFamilyCloudData(...)`, `getFamilyDeletionStatus(...)`: Worker REST API 호출로 1:1 대체.
* **에코 루프 방지**:
  * `changeToken`의 클라이언트 식별자 대조 (`token.split(':')[1] === myClientId`)를 통해 본인 변경 시 재동기화 차단.
* **오프라인 및 장부(`syncLedger`) 보존**:
  * AsyncStorage의 `syncLedger`(`lastSyncedServerTime`, `uploaded`, `pendingSync`) 메커니즘을 그대로 유지하여 오프라인에서 기록 추가 후 온라인 복귀 시 누락 없이 전송.
