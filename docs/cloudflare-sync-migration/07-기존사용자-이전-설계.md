## 0. 불변 조건
모든 단계가 지켜야 하고, 검증 시나리오도 이 조건으로 판정한다. 1·3·4·5는 단계 A가 D1 쪽에서 이미 지키고 있으며, 이 문서는 Firestore 쪽과 이전 단계에서 같은 조건을 지킨다.

1. **기록 보존:** 기기의 기록은 합치기만 하고 줄이지 않는다. 이전 단계, 전환기 읽기, 직전 백업 복원도 기록을 지우지 않는다.
2. **Firestore 쓰기 제한 (2판):** 앱이 Firestore에 쓰는 일은 두 가지뿐이다. Firestore 문서를 지우는 코드는 앱에 두지 않는다.
   - 회원 문서 생성: 이전 단계, 1.7.9 가족 합류(2.9), 전환기의 재가입. 1.7.9와 같은 쓰기다.
   - 1.7.9 삭제 예약의 취소: 사용자가 고른 경우에만 가족 문서에 `pendingDeletionAt: null`을 쓴다(2.4.1, 2.6.3). 1.7.9 취소와 같은 쓰기다.
3. **자동 연결 해제 제한:** 앱이 스스로 가족 연결을 끊는 근거는 D1의 410뿐이다(단계 A `06` 2.7). Firestore 거부와 D1 404는 근거가 되지 않는다.
4. **부활 금지:** 영구 삭제한 가족은 어떤 경로로도 D1에 다시 생기지 않는다. 단계 A의 `deleted_families`가 지킨다. Firestore에 사본이 남아 있어도 이어받기는 410에서 멈춘다.
5. **혼자 쓰기 무요청 (4판):** `syncKey`가 없으면 Cloudflare와 Firestore 요청이 모두 0회다. 예외는 사용자가 직접 시작한 합류와 가족 만들기뿐이다. 합류 중에는 저장된 키가 없어도 D1 연결 회차와 `legacyJoin`(2.9)의 Firestore 요청이 나간다. 키를 잘못 입력해도 404 뒤 `legacyJoin`이 Firestore에 한 번 묻는다.
6. **Firestore 무요청 기본값:** 아래 두 경우가 아니면 Firestore에 요청하지 않는다.
   - 이 기기에 1.7.9 연결 근거(2.1)가 있는 키
   - D1에 가족이 없는(`missing`) 키. 상대가 아직 1.7.9인 가족의 초대 링크로 합류하는 경우다(2.9).
   따라서 1.8.0에서 새로 만든 가족과 그 가족에 합류한 기기의 Firestore 요청은 0회다.

## 2. 대책

### 2.1 1.7.9 연결 근거 표식
- 1.8.0을 처음 실행할 때 `syncKey` 유무와 상관없이 `@baby_cf_legacy_key_v1`에 아래 값을 **항상** 한 번 적는다. 값이 이미 있으면 다시 계산하지도 덮어쓰지도 않는다.

  ```ts
  type LegacyKeyMarker = {
    checkedAt: number;
    keys: string[]; // 첫 실행 시점의 프로필 syncKey와 옛 장부(@baby_sync_ledger_v1)의 familyKey. 없으면 빈 배열
  };
  ```

- 이 표식이 "1.7.9 시절 이 기기가 이 가족에 연결돼 있었다"를 판단하는 유일한 값이다. 첫 실행 뒤의 프로필 키나 옛 장부는 근거로 쓰지 않는다.
- **위치 (1차 검토 경미):** `migrateStoredData`(`storage.ts:77`)의 스키마 버전 조기 반환(`storage.ts:84`) **앞**에서 적는다. 1.7.9 기기는 이미 스키마 2라서(`7d4753b` `storage.ts:11`), 반환 뒤에 두면 실사용자 기기에는 표식이 적히지 않는다.
- 출시 전 1.8.0 시험 빌드를 쓴 기기(성기님 시험 기기)를 위해 개발 메뉴에서 표식을 비우는 방법을 둔다. **비우기는 키를 지우지 않고 `{ checkedAt: 지금, keys: [] }`로 덮어쓴다 (4판).** 키를 지우면 다음 실행이 표식을 다시 계산해 지금 프로필 키를 근거로 적는다.

### 2.2 이전 상태
가족 키마다 `@baby_cf_migration_v1:<syncKey>`에 아래 값을 둔다.

```ts
type MigrationState = {
  mergeSource?: 'ok' | 'skipped';   // 'ok'는 Firestore를 읽어 합침, 'skipped'는 읽을 필요가 없거나 읽기를 멈춤
  mergedAt?: number;
  d1UploadedAt?: number;            // 합친 기록을 D1에 전체 모드로 모두 올린 시각
  firestoreReadAfter?: string;      // 페이지 나눠 읽기에서 마지막으로 합친 문서 id
  baselineChangedAt?: number;       // 첫 읽기 시도에서 읽은 가족 문서 lastChangedAt
  nextFirestoreAttemptAt?: number;  // Firestore를 다시 읽어도 되는 시각
  failureCount?: number;
  blockedSince?: number;            // denied, pending_deletion, absent가 처음 관측된 시각 (2.5)
  legacyJoinedAt?: number;          // 1.7.9 가족 합류(2.9)를 시작한 시각. D1 가족을 만들기 전에 적는다
  legacyDeletionNoticeAt?: number;  // exists + pending_deletion 안내를 보인 시각 (2.4-6)
  promptedPendingDeletionAt?: number; // 이미 물어본 1.7.9 예약의 pendingDeletionAt 값(밀리초). 2.4.1, 2.4-6, 2.6.3이 함께 쓴다 (4판)
  lastError?: string;               // 화면 안내용
};
```

- **`promptedPendingDeletionAt`의 위치 (4판, 3차 검토 경미 6):** 3판은 이 값을 전환기 상태에 두었지만, 2.4.1과 2.4-6의 선택 화면은 전환기가 생기기 전에 뜬다. 그래서 이 값을 이전 상태로 옮겨 세 화면이 같은 값을 쓴다. 화면에 보일 예약 값이 이 값과 같으면 다시 묻지 않는다. 가족 문서의 `pendingDeletionAt`이 `null`이거나 필드가 없으면 이 값을 지운다.

- **근거 (3판):** 이 문서에서 "근거가 있다"는 `@baby_cf_legacy_key_v1.keys`에 키가 있거나, 이 키의 `legacyJoinedAt`이 있다는 뜻이다. 두 값은 모든 판단(2.3 관문, 2.4-3, 2.5, 2.9)에서 똑같이 쓴다.

- **이전 완료**는 `mergedAt`과 `d1UploadedAt`이 모두 있는 상태다. 병합은 끝났는데 업로드가 남으면 Firestore를 다시 읽지 않고 업로드만 다시 한다.
- **병합 전 업로드 (4판, 3차 검토 경미 3):** D1이 `exists`이고 Firestore 읽기가 실패하면 병합 없이 7단계를 하므로 `d1UploadedAt`이 먼저 적힌다. 뒤에 병합이 성공하면 `mergedAt`과 함께 `d1UploadedAt`을 지워, 병합한 기록을 올리는 7단계를 한 번 더 한다. 반대로 `d1UploadedAt`이 있고 이번 시도에서 새로 병합하지 않았으면 7단계를 건너뛴다. 그래서 앱을 켤 때마다 `forceFullRead`가 반복되지 않는다.
- 이 값은 데이터 가져오기, 백업 복원, 영구 삭제, 연결 해제에서 지우지 않는다.
- 모든 값은 수백 바이트다.

### 2.3 실행 방식
- **모듈:** 새 모듈 `src/database/familyMigration.ts`에 `createFamilyMigrator(deps)`를 둔다. 러너(`06` 2.11)처럼 `react`, `react-native`, `expo-*`를 불러오지 않고, 저장소 함수, Firestore 읽기 함수(2.3.1), D1 함수, 러너 요청 함수, 시계를 인자로 받는다. 하네스가 실제 코드를 그대로 실행한다.
  - **화면 콜백 (4판):** 사용자에게 묻는 화면(백업 실패, 2.4.1, 2.4-6, 2.6.3의 선택 화면)과 안내 문구도 인자(`deps.askBackupFailure`, `deps.askLegacyDeletionChoice`, `deps.notify`)로 받는다. App은 경고창으로 묻고, 하네스는 시나리오가 정한 답을 돌려준다. 선택에 따른 처리(재확인, 서버 요청, 상태 기록)는 모두 이 모듈 안에 있다.
- **기기당 하나:** 같은 키의 이전이 돌고 있으면 같은 Promise를 돌려준다. 다른 키로 바뀌면 앞 작업은 결과를 저장하지 않는다. 기기 저장은 `mergeLegacyFirestoreData`의 `expectedSyncKey` 확인으로 하므로(`storage.ts:1178` 부근), 키 확인과 저장이 저장 큐 안에서 한 번에 일어난다.
- **상한 밖:** Firestore 부분(2.4의 1~6)은 러너의 20초 상한 밖에서 돈다. 전체 예산은 90초이고, Firestore 호출 하나마다 15초 상한을 둔다. 상한에 걸리면 `terminate(db)`로 인스턴스를 닫고 다음 호출은 새 인스턴스를 만든다.
- **Firestore 사용 직렬화:** 이전 단계, 1.7.9 가족 합류, 전환기 읽기는 같은 Firestore 인스턴스와 익명 로그인을 쓴다. 모듈 수준의 잠금 하나로 한 번에 하나만 돌게 해서, 한 작업의 `terminate`가 다른 작업의 호출을 끊지 않게 한다.
- **D1 업로드는 러너로:** 2.4의 7단계는 러너에 `forceFullRead: true` 요청으로 넣는다. 평소 동기화와 같은 대기열에서 돌므로 장부를 서로 덮어쓰지 않는다.
  - **`d1UploadedAt` 판정 (1차 검토 경미):** 전체 모드는 당겨 받기가 끝나면 `full`을 지우고, 남은 올리기는 러너의 이어 가기 회차가 맡는다. 그래서 이전 모듈은 러너 사건을 구독하고, 이 키의 `succeeded` 사건 가운데 `result.continuing`이 거짓이고 장부에 `full`이 없는 첫 사건에서 `d1UploadedAt`을 적는다. 그 사이의 이어 가기 회차도 같은 구독으로 본다.
  - **사건 식별 (4판, 3차 검토 경미 2):** 지금 러너 사건에는 키도 요청 식별자도 없다(`syncRunner.ts:19-24`). 러너를 아래처럼 고친다.
    - 모든 사건에 `syncKey`와 `requestId`를 싣는다. `requestId`는 러너가 요청을 받을 때 1씩 늘려 매기는 번호이고, 이어 가기 회차는 부모 요청의 번호를 물려받는다. 합쳐진 평소 요청은 처음 받은 요청의 번호를 쓴다.
    - `request()`는 결과와 함께 `requestId`를 알 수 있어야 한다. `request(req, { onAccepted(id) })`처럼 번호를 곧바로 알려 주는 방법을 쓴다.
    - 구독을 여러 개 받는다. `subscribe(listener)`가 해제 함수를 돌려주고, 생성 인자 `onEvent`는 첫 구독자로 그대로 둔다(App 동작은 바뀌지 않는다).
    - 이전 모듈은 7단계 요청의 번호를 `uploadRequestId`(메모리)에 두고, `requestId >= uploadRequestId`인 사건만 판정에 쓴다. 7단계보다 먼저 시작한 회차는 번호가 작아서 걸러진다. 이어 가기가 상한(`MAX_CONTINUATIONS`)에 걸려 뒤의 평소 요청이 업로드를 마치는 경우도 번호가 크므로 판정에 들어간다.
    - **(B8 리뷰 반영)** 이어 가기 요청이 더 작은 번호의 대기 요청에 합쳐지면 대기 요청의 번호를 둘 중 큰 값으로 올린다. 이어 가기가 아닌 새 요청이 합쳐질 때는 올리지 않는다. 대기 요청이 그 사이에 들어온 7단계 요청보다 먼저 실행될 수 있어서, 올리면 아직 올리지 않은 업로드를 끝난 것으로 오인하기 때문이다.
    - **(B8 리뷰 반영)** 러너는 회차 시작 전 키가 맞지 않거나 회차 도중 다른 가족으로 바뀌어 D1 요청을 끝맺지 못하면 `dropped` 사건을 낸다. 화면은 이 사건을 무시한다. 이전 모듈은 `failed`, `dropped`, `migrationPending`, `detached`, `disconnected`를 "7단계가 끝맺지 못함"으로 보고, 업로드 번호는 지우지 않은 채 표시만 남긴다. 그러면 뒤의 평소 요청이 장부에 `full`이 없는 상태로 성공할 때 완료가 적히고, 다음 `ensure`는 이 표시가 있을 때만 7단계를 다시 넣는다. 새로 병합하면 이전 업로드 번호를 먼저 무효로 해, 병합 전 업로드의 완료가 병합 뒤 업로드의 완료를 가리지 않게 한다.
- **러너 관문 `migrationGate` (3판):** 러너는 평소 요청을 실행하기 전에 `deps.migrationGate(syncKey)`를 부른다. 이 함수는 저장소의 이전 상태와 이전 모듈의 메모리 값(`d1Status`)만 읽는다. 아래 규칙을 위에서부터 차례로 적용한다.
  1. **연결 회차(`connecting: true`)는 관문을 거치지 않는다** (2차 검토 M1). 합류와 가족 만들기는 저장된 키가 없거나 다른 키일 때 시작하므로, 관문이 막으면 이전 모듈도 시작할 수 없다. 연결 회차의 결과 처리는 2.9가 정한다.
  2. 이전이 끝났으면 `'proceed'`다.
  3. `d1Status`가 `deleted`이면 `'proceed'`다. 러너의 410 처리가 연결을 끊어야 하기 때문이다.
  4. 근거(2.2)가 없으면 `'proceed'`다. 1.8.0 가족이 여기에 해당한다.
  5. 근거가 있고 `d1Status`가 `exists`이면 `'proceed'`다. `mergeSource`가 아직 없어도 상대가 이미 D1로 옮긴 가족이므로 평소 동기화는 돈다.
  6. 그 밖(근거가 있고 `d1Status`가 `missing`이거나 모름)은 `'paused'`다. 러너는 D1에 요청하지 않고 `{ success: false, migrationPending: true }`를 돌려준다. 화면은 "이전 준비 중"을 보여 주고 오류로 표시하지 않는다.
  - 이어받기(2.4-6)가 성공하면 이전 모듈이 `d1Status`를 `exists`로 바꾸고, 그 뒤에 7단계 요청을 넣는다. 그래서 7단계 요청이 관문에 막히지 않는다.
  - **`deleted`일 때의 410 회차 (4판, 3차 검토 경미 4):** 이전 모듈이 `d1Status`를 `deleted`로 정하면 러너에 평소 요청 하나를 넣는다. 그 회차가 410을 받아 러너가 연결을 끊는다. 이 요청이 없으면 폴링이 멈춘 상태라 사용자가 무언가 하기 전까지 "이전 준비 중"에 머문다.
  - **합류 성공 (4판):** 연결 회차가 성공하면 `joinFamily`(2.9)가 곧바로 `d1Status`를 `exists`로 적는다.
- **관문은 기다리지 않는다 (4판, 3차 검토 경미 1):** 관문은 러너 대기열 안에서 돈다. 관문이 이전 모듈의 Promise를 기다리고 그 Promise가 7단계 러너 회차를 기다리면 서로 기다리게 된다. 그래서 아래 두 규칙을 지킨다.
  - 관문은 `ensure`를 부르기만 하고 결과를 기다리지 않는다. 관문 자체는 저장소 읽기와 메모리 값만으로 곧바로 답한다.
  - `ensure`의 Promise는 7단계 요청을 러너에 넣는 데서 끝난다. 업로드 완료는 사건 구독(`d1UploadedAt` 판정)으로 본다.
- **멈춤에서 빠져나오는 계기 (2차 검토 M3):** 관문이 `'paused'`를 돌려줄 때마다 `migrator.ensure(syncKey)`를 부른다(이미 돌고 있으면 같은 Promise). 2.4의 1~2단계는 D1 요청뿐이라 Firestore 실패 간격에 걸리지 않으므로, 오프라인으로 시작했어도 다음 저장, 앱 복귀, 당겨서 새로고침 때 `d1Status`가 정해진다. `nextFirestoreAttemptAt`이 있으면 그 시각에 `ensure`를 부르는 타이머를 둔다(앱이 떠 있는 동안만).
- **앱 시작 순서:** App의 첫 동기화(`App.tsx:224`)와 폴링 시작(`App.tsx:247` 이하) 전에 `migrator.ensure(syncKey)`를 시작한다. 관문이 근거 있는 키를 `'paused'`로 두므로 첫 동기화가 404 오류를 보이지 않는다. 폴링은 관문이 `'proceed'`일 때만 시작하고, 이전 모듈이 `d1Status`를 `exists`로 바꾸거나 이전을 마치면 App에 알려 폴링을 시작한다.
- **`migrationPending`의 화면 처리:** 당겨서 새로고침은 실패하면 경고창을 띄운다(`App.tsx:463-468`). `migrationPending`은 실패로 보지 않고 경고창을 띄우지 않는다. 동기화 상태 표시도 오류가 아니라 "이전 준비 중"이다.
- **설정 화면 (2차 검토 경미 5):** 설정 화면의 삭제 상태 확인(`Profile.tsx:119-186`)은 D1을 직접 부른다. 관문이 `'paused'`인 키에서는 이 확인을 하지 않고, 삭제 영역에 "이전 준비 중"을 보여 준다.
- **화면 판정의 순수 함수 (4판, 3차 검토 M2):** 위 세 가지 화면 판정은 React와 무관한 새 모듈 `src/database/migrationDecision.ts`에 순수 함수로 둔다. App과 Profile은 이 함수의 결과만 따른다. 하네스 단위 검사가 이 함수를 직접 검사한다.
  - `shouldAlertOnRefresh(result)`: 당겨서 새로고침의 경고창 여부. `migrationPending`이면 거짓이다.
  - `shouldStartPolling(gate)`: 폴링 시작 여부. 관문이 `'proceed'`일 때만 참이다.
  - `shouldCheckDeletionStatus(gate)`: 설정 화면의 D1 삭제 상태 확인 여부. 관문이 `'paused'`이면 거짓이다.
  - 관문 판정(위 규칙 1~6) 자체도 `decideMigrationGate(input)` 순수 함수로 두고, 러너에 넘기는 `migrationGate`는 저장소 값을 읽어 이 함수를 부른다.
- **실패 간격:** Firestore를 읽어 비용이 드는 실패에만 적용한다. D1 네트워크 실패는 위 계기로 다시 시도한다.
  - 가벼운 실패: `logs` 읽기 전의 실패(로그인, 회원 확인, 가족 문서, 거부, 삭제 예약)다. 30분, 1시간, 2시간 순서로 늘리고 최대 6시간이다.
  - 무거운 실패: `logs` 읽기를 시작한 뒤의 실패다. 1시간부터 두 배씩, 최대 12시간이다. 저장된 위치부터 이어 읽으므로 한 번에 버리는 읽기는 최대 한 페이지다.
  - **진척이 있으면 (2차 검토 경미 8):** 이번 시도에서 한 페이지 이상 합쳐 저장했으면 실패 횟수를 0으로 되돌리고 간격을 5분으로 둔다. 페이지 상한(15초)에 걸린 실패는 다음 시도의 페이지 크기를 절반으로 줄인다(하한 50건). 느린 망에서도 매번 진척하며 이어 읽는다.
  - 할당량 소진(`resource-exhausted`): 태평양 시간 자정 뒤로 미룬다.
  - 당겨서 새로고침도 이 간격을 지킨다.
- **화면 반영:** 이전 단계가 기기에 합친 결과를 저장하면 App은 저장소에서 기록과 프로필을 다시 읽어 화면에 반영한다.

#### 2.3.1 Firestore 읽기 모듈
- 새 모듈 `src/database/firestoreImport.ts`가 1.7.9 코드(`7d4753b` `sync.ts`)에서 회원 가입과 읽기 경로만 옮겨 온다. 지우는 함수는 옮기지 않는다.
- Firestore 해시는 1.7.9와 같이 키를 대소문자 그대로 해시한다(`babycheck:family:v2:<key>`, `babycheck:invite:v2:<key>`). D1 해시는 소문자 키 기준이므로 두 해시를 각자 기준대로 만든다.
- 모든 읽기는 캐시가 아니라 서버에서 읽는다(`getDocFromServer`, `getDocsFromServer`). 캐시 값으로 판정하면 예약 상태와 커서가 틀린다.
- `firebase.ts`는 지금 모듈을 불러올 때 `db`를 만든다. 이를 `getFirestoreDb()`와 `resetFirestoreDb()`로 바꿔 처음 쓸 때 만들고, `terminate` 뒤에는 새로 만든다. `terminate` 뒤 **기본 앱**으로 `initializeFirestore`를 다시 부를 수 있는지 구현 첫 커밋에서 확인한다.
  - 이름을 붙인 새 앱 인스턴스는 쓰지 않는다 (2차 검토 경미 2). 인증 저장 키가 앱 이름별로 달라서 1.7.9의 익명 uid를 잃고, uid가 바뀌면 `inviteHash` 없는 예전 문서에서 영구 거부가 난다.
  - 기본 앱으로 다시 만들 수 없으면 `terminate`를 쓰지 않는다. 대신 상한에 걸린 호출의 결과를 버리고, 직렬화 잠금(2.3)으로 다음 작업이 겹치지 않게 하며, 상한이 두 번 이어지면 그 실행에서는 Firestore를 더 부르지 않는다.
- **payload 검증 (2차 검토 경미 7):** Firestore 기록을 합치기 전에 문서 id와 `payload.id`가 같은지, `type`이 문자열인지, `timestamp`가 유한한 수인지 확인한다. 어긋난 문서는 건너뛰고 개수만 `lastError`에 남긴다. 형식이 깨진 기록 하나가 기기 저장소 전체를 못 쓰게 만드는 일(`storage.ts:106-118`의 `readLogsUnsafe`)을 막는다.
- `firestoreImport.ts`와 `firebase.ts`는 동적 `import()`로만 불러온다. 혼자 쓰는 기기와 1.8.0 신규 가족은 이 모듈을 불러오지 않는다.

### 2.4 이전 단계 순서
이전이 끝난 키는 아무것도 하지 않는다. 그렇지 않으면 아래 순서를 밟는다.

1. **이전 직전 백업:** `@baby_pre_cloudflare_backup_v1`에 현재 기록과 프로필을 저장한다. 이미 있으면 덮어쓰지 않는다. 저장이 실패하면(용량 부족 포함) 이전을 멈추고 "기기 저장 공간이 부족해 업데이트 전 백업을 만들지 못했습니다"를 보여 준다. 사용자가 "백업 없이 계속"을 고르면 진행한다. 이전 단계는 합치기만 하므로 백업이 없어도 기록은 줄지 않는다.
   - **작은 표지 (4판, 3차 검토 경미 12):** 관문이 멈출 때마다 `ensure`가 불리므로, "백업이 이미 있음"을 수 MB인 백업 값으로 확인하지 않는다. 백업을 저장한 뒤 `@baby_pre_cloudflare_backup_meta_v1`에 `{ savedAt, logCount }`를 적고, 이 표지만 읽어 판단한다. 표지가 없는데 백업 값이 있으면(표지 쓰기 직전 종료) 백업 값을 한 번 읽어 표지를 채운다.
   - **"백업 없이 계속"은 한 번만 묻는다:** 사용자의 선택을 같은 표지에 `{ skippedAt }`으로 적는다. 이 값이 있으면 백업을 다시 시도하지 않고 묻지도 않는다. 선택 전에는 이전을 멈춘 채 두고, 저장할 때마다 다시 묻지 않는다(앱을 다시 열 때 한 번 묻는다).
2. **D1 가족 확인:** `connectFamily(allowCreate=false)`를 부르고, 결과를 `d1Status`에 둔다.
   - 200이면 `exists`, 404면 `missing`, 410이면 `deleted`다.
   - `deleted`이면 이전을 멈추고 러너에 평소 요청 하나를 넣는다(2.3 "`deleted`일 때의 410 회차"). 러너의 410 처리가 연결을 끊는다.
   - 401(키 형식이 서버 정규식에 맞지 않음)이면 이전을 멈추고 "가족 연결 키 형식을 새 서버가 받지 못합니다"를 오류로 보인다. 6장 점검이 이 경우를 미리 막는다.
   - 네트워크 오류와 5xx는 실패로 끝내고 Firestore 실패 간격은 적용하지 않는다.
3. **Firestore를 읽을지 판단 (`mergeSource`가 없을 때만):**
   - D1이 `exists`이고 근거(2.2: 표식 또는 `legacyJoinedAt`)가 없으면 읽지 않는다. `mergeSource: 'skipped'`, `mergedAt`을 적고 7번으로 간다.
   - D1이 `missing`이면 근거와 상관없이 읽는다.
   - `nextFirestoreAttemptAt`이 지나지 않았으면 읽지 않는다. D1이 `exists`이면 7번으로 가고, `missing`이면 실패로 끝낸다.
4. **Firestore 읽기:**
   1. 익명 로그인 후 `families/<familyId>/members/<uid>`를 읽는다. 없으면 1.7.9와 같이 초대 해시로 회원 문서를 한 번 만든다. 생성이 `permission-denied`이면 결과는 `firestore_denied`다(2.5).
   2. 가족 문서를 읽는다. 문서가 없으면 `firestore_absent`다. 이 결과는 이미 회원 문서가 있는 기기에서만 나온다. 회원이 아닌 기기는 1단계의 회원 생성 규칙이 가족 문서의 `inviteHash`를 읽다 실패하므로 `firestore_denied`를 받는다(2차 검토 경미 1, `firestore.rules:52-54`). `pendingDeletionAt`이 timestamp이면(미래든 과거든) 결과는 `firestore_pending_deletion`이다. `null`이거나 필드가 없으면 다음으로 간다. 처음 읽는 시도라면 이 문서의 `lastChangedAt`(없으면 0)을 `baselineChangedAt`에 적는다.
   3. `logs`를 문서 id 순서로 500건씩 읽는다. 페이지마다 15초 상한을 두고, 받은 페이지를 곧바로 기기에 합쳐 저장한 뒤 `firestoreReadAfter`를 적는다. `deleted: true` 문서는 삭제 표식으로, 나머지는 `payload`를 기록으로 합친다.
   4. 모든 페이지를 읽으면 `profile/shared`를 읽어 프로필 LWW 규칙으로 합친다. 결과는 `firestore_ok`다.
   5. 할당량 소진, 상한 초과, 그 밖의 오류는 `firestore_error`다.
5. **병합 완료:** `firestore_ok`이면 `mergeSource: 'ok'`, `mergedAt`을 적고 2.6의 전환기 상태를 만든다. 이때 `d1UploadedAt`이 있으면 지운다(2.2 "병합 전 업로드").
6. **D1 가족 결정:**

   | D1 | Firestore 또는 병합 상태 | 처리 |
   |---|---|---|
   | deleted | 무엇이든 | 이전을 멈춘다 |
   | exists | 읽지 않음(근거 없음) | 7번 |
   | exists | ok | 7번 |
   | exists | denied, absent, error | 병합 없이 7번. 실패 간격 뒤 Firestore 읽기만 다시 시도한다(2.5의 종료 조건). 평소 동기화는 계속한다 |
   | exists | pending_deletion | 위와 같이 7번으로 가되, 예약 값이 `promptedPendingDeletionAt`과 다르면 2.6.3과 같은 선택 화면을 한 번 보여 준다(2차 검토 경미 6). 1.7.9에서 직접 삭제를 요청한 사용자에게 그 요청이 실행되지 않았음을 알리기 위해서다. 이 화면의 "삭제에 따르기"도 2.6.3의 보내기 전 재확인을 거친다(4판, 3차 검토 M1). 화면을 보이면 `legacyDeletionNoticeAt`과 `promptedPendingDeletionAt`을 적는다 |

7. **D1 전체 업로드:** `d1Status`를 `exists`로 바꾼 뒤 러너에 `forceFullRead: true` 요청을 넣는다(2.3). 단계 A의 전체 모드가 서버의 모든 행을 당겨 받고, 장부와 다른 항목만 나눠 올린다. `d1UploadedAt`이 이미 있고 이번 시도에서 새로 병합하지 않았으면 이 단계를 건너뛴다(2.2 "병합 전 업로드").

#### 2.4.1 1.7.9에서 삭제를 예약한 가족 (`missing` + `pending_deletion`)
1.7.9의 영구 삭제는 규칙 때문에 끝날 수 없었으므로, 이 가족의 Firestore 데이터는 그대로 남아 있다(부분 삭제 상태는 없다). 사용자에게 고르게 한다.

- 화면 안내: "이전 버전에서 가족 서버 데이터 삭제를 요청한 기록이 있습니다." 선택지는 셋이다.
  - **요청 취소하고 계속 쓰기:** Firestore 가족 문서에 `pendingDeletionAt: null`을 쓰고 곧바로 2.4를 다시 실행한다. 이어받기까지 끝난다.
  - **삭제에 따르기 (3판, 2차 검토 M4):**
    1. 보내기 직전에 가족 문서를 서버에서 다시 읽는다. `pendingDeletionAt`이 더 이상 timestamp가 아니면(상대가 취소함) 보내지 않고 "다른 기기에서 삭제 요청을 취소했습니다"를 보여 준 뒤 2.4를 다시 실행한다. 읽기가 실패하면 보내지 않는다.
    2. 서버에 `POST /api/family/delete`를 `legacyDeletion: true`와 함께 보낸다(2.7-1). 서버는 D1에 가족이 없을 때만 한 문장으로 `deleted_families`에 기록한다.
    3. 응답이 `{ ok: true }`이거나 410일 때만 이 기기의 연결을 해제한다. 409(그 사이 D1 가족이 생김)이면 해제하지 않고 2.4를 다시 실행한다(이제 D1이 `exists`이므로 평소 동기화로 이어진다). 그 밖의 오류는 해제하지 않고 오류만 보인다.
    - **409 뒤의 반복 방지 (4판, 3차 검토 경미 6):** 409를 받으면 "다른 기기가 이미 새 서버로 옮겼습니다"만 보이고, 2.4를 다시 실행하기 전에 `legacyDeletionNoticeAt`과 `promptedPendingDeletionAt`(이 화면의 예약 값)을 적는다. 그래서 다시 실행한 2.4가 `exists` + `pending_deletion` 행에서 같은 선택 화면을 곧바로 다시 띄우지 않는다.
  - 2.4.1 화면을 보이면 `promptedPendingDeletionAt`에 예약 값을 적는다. "나중에"를 고른 경우는 예외로, 이 값을 적지 않아 앱을 다시 열 때 다시 묻는다.
    4. 기기 기록은 지우지 않는다. Firestore 사본은 운영자 정리(2.8)로 지운다고 안내한다.
    - 이 선택은 예약 시각과 상관없이 고를 수 있다. 사용자의 삭제 요청은 이미 있었고, D1에는 지울 데이터가 없으며, 결과는 이 가족의 이어받기를 막는 것뿐이기 때문이다.
  - **나중에:** 연결을 유지하고 아무것도 하지 않는다. 앱을 다시 열 때 다시 묻는다(가벼운 실패 간격 적용).
- **합류 도중의 화면 (4판, 3차 검토 경미 5):** 이 화면이 1.7.9 가족 합류(2.9) 도중에 나오면, 아직 키가 저장되지 않았고 이 기기는 가족 회원도 아니다. 이 기기가 "삭제에 따르기"로 D1에 삭제 기록을 남기면 묻지 않은 두 기기가 410으로 끊긴다. 그래서 합류 중에는 선택지를 둘만 둔다.
  - **요청 취소하고 합류:** 취소를 쓰고 합류를 이어 간다. 취소 쓰기는 회원만 할 수 있으므로, `legacyJoin` 1단계에서 회원 문서를 만든 뒤에 쓴다.
  - **합류 취소:** 합류를 끝내고 키를 저장하지 않는다.
- 상대 기기(1.7.9)는 Firestore로 계속 동기화한다. 상대가 나중에 1.8.0으로 업데이트하면 "삭제에 따르기"를 고른 경우 410을 받아 연결이 해제되고, 상대 기기의 기록은 남는다.

### 2.5 거부와 예약이 이어질 때 (결함 F)
`firestore_denied`는 근거(2.1)로 나눈다.

- 근거가 있으면 이 기기는 Firestore에서 이 가족과 연결돼 있었다. `denied`는 uid 변경이나 예전 문서 형식 때문일 수 있으므로 `firestore_error`로 낮춘다. 연결은 유지하고 가벼운 실패 간격 뒤 다시 시도한다.
- 근거가 없으면 초대 키가 잘못됐거나 가족이 없는 것이다. 동기화 오류로 "가족 연결을 확인할 수 없습니다. 초대 링크를 다시 받아 주세요."를 보여 준다. 앱이 스스로 연결을 끊지는 않는다.
- `blockedSince`를 적고, 7일 넘게 이어지면 안내를 "가족 연결을 다시 확인해 주세요. 기록은 이 기기에 그대로 있습니다."로 바꾼다.
- **재시도 종료:** D1이 `exists`인 가족에서 `denied`, `pending_deletion`, `absent`가 14일 넘게 이어지면 Firestore 읽기를 멈추고 `mergeSource: 'skipped'`, `mergedAt`을 적는다. 상대가 이미 D1로 옮긴 가족이라 평소 동기화가 돌고, 상대 기기의 기록은 상대가 D1에 올린다. 화면에는 "이전 서버의 기록을 가져오지 못했습니다"를 한 번 보여 준다. D1이 `missing`인 가족은 멈추지 않는다(멈추면 이어받을 길이 없다). 대신 간격의 최대값 6시간을 지킨다.

### 2.6 전환기 (결함 G)
- 전환기는 `mergeSource: 'ok'`인 기기에만 있다. 시작은 `mergedAt`이다.
- 전환기 상태는 `@baby_cf_transition_v1:<syncKey>`에 따로 둔다. 가져오기와 백업 복원은 이 값을 지우지 않는다.

  ```ts
  type TransitionState = {
    seenFamilyChangedAt: number;       // 마지막으로 처리한 가족 문서 lastChangedAt
    partnerSeenAt?: number;            // otherMembers ≥ 1을 처음 관측한 시각
  };
  ```

  4판에서 `promptedPendingDeletionAt`은 이전 상태(2.2)로 옮겼다.

- **끝내는 조건 (1차 검토 경미 반영):** 변경 토큰 응답의 `otherMembers`(2.7)가 1 이상이면 `partnerSeenAt`을 적고, 그때부터 24시간 동안은 30분 간격으로 읽은 뒤 끝낸다. 상대가 업데이트 직전에 1.7.9로 쓴 기록까지 받으려는 여유다. 시작부터 30일이 지나면 무조건 끝낸다. 14일이 지나면 간격을 30분으로 늘린다. `otherMembers`가 시험 기기나 세 번째 기기 때문에 일찍 1이 되더라도 24시간 여유와 30분 간격 덕분에 상대의 남은 쓰기를 받을 기회가 남는다.

#### 2.6.1 커서
- 전환기 읽기의 커서는 `seenFamilyChangedAt` 하나다. 처음 값은 2.4-4.2의 `baselineChangedAt`, 곧 **첫 읽기 시도에서 읽은 가족 문서 `lastChangedAt`**이다.
- 이 값이 맞는 이유: 1.7.9는 기록 쓰기와 `lastChangedAt` 갱신을 같은 트랜잭션에서 한다(`7d4753b` `sync.ts:266-326`, 프로필은 `:613-635`). 그래서 `baselineChangedAt` 이후에 바뀐 문서의 `updatedAt`은 모두 `baselineChangedAt` 이상이다. 페이지 나눠 읽기 도중에 이미 읽은 페이지의 문서가 바뀌어도 첫 전환기 읽기에 들어온다.

#### 2.6.2 읽기 순서
- 평소 동기화가 끝난 뒤, 5분(14일 뒤와 `partnerSeenAt` 뒤에는 30분)에 한 번 이하로 가족 문서 하나를 서버에서 읽는다. `lastChangedAt`이 `seenFamilyChangedAt`보다 새로우면 아래를 읽는다.
  - `logs`에서 `updatedAt >= seenFamilyChangedAt`인 문서(삭제 표식 포함). 경계 문서는 다시 받지만 합치기가 중복을 처리한다.
  - `profile/shared` 문서 하나.
- 합친 결과를 저장한 뒤에만 `seenFamilyChangedAt`을 이번에 읽은 가족 문서의 `lastChangedAt`으로 바꾼다.
- `lastChangedAt`이 그대로면 가족 문서 1회만 읽는다.
- 받은 기록은 기기에 합치고, 다음 평소 동기화가 D1에 올린다. Firestore 쪽 오류는 평소 동기화 결과에 섞지 않는다. 회원 확인이 거부되면 재가입을 한 번 시도하고, 그래도 거부되면 가벼운 실패 간격을 적용한다.
- 첫 이전이 끝나면 한 번 안내한다: "새 버전부터 동기화 서버가 바뀌었습니다. 가족 모두 1.8.0으로 업데이트해야 서로의 새 기록이 보입니다."

#### 2.6.3 1.7.9 상대의 삭제 예약
1.7.9의 삭제 예약은 `pendingDeletionAt`만 쓰고 `lastChangedAt`은 바꾸지 않는다(`7d4753b` `sync.ts:704`). 실제 삭제는 규칙 때문에 끝날 수 없다. 그래서 전환기의 가족 문서 읽기(추가 비용 없음)에서 예약만 본다.

- `pendingDeletionAt`이 timestamp이고 그 값이 `promptedPendingDeletionAt`과 다르면 "상대 기기(이전 버전)에서 가족 서버 데이터 삭제를 요청했습니다"를 보여 준다. 선택지는 셋이다.
  - **요청 취소:** Firestore에 `pendingDeletionAt: null`을 쓴다.
  - **삭제에 따르기 (4판, 3차 검토 M1):** 1.8.0의 영구 삭제 절차(2.8, D1 예약과 냉각 뒤 삭제)를 이 기기에서 시작한다. 1.8.0의 예약된 삭제는 설정 화면을 열거나 앱으로 돌아올 때 자동으로 실행되고(`Profile.tsx:144-150`), 1.7.9 상대는 D1 예약을 보지도 취소하지도 못한다. 그래서 2.4.1 1단계와 같은 규칙으로 보내기 전에 다시 확인한다.
    1. D1 삭제 예약을 보내기 직전에 가족 문서를 서버에서 다시 읽는다.
    2. `pendingDeletionAt`이 timestamp가 아니거나 화면에 보인 값과 다르면 보내지 않는다. 취소된 경우에는 "다른 기기에서 삭제 요청을 취소했습니다"를, 값이 바뀐 경우에는 새 값으로 선택 화면을 다시 보여 준다.
    3. 다시 읽기가 실패하면(거부, 가족 문서 없음, 오류, 상한 초과) 보내지 않고 "이전 서버에서 삭제 요청을 확인하지 못했습니다. 잠시 뒤 다시 시도해 주세요."를 보인다.
    - 이 규칙은 2.4-6의 `exists` + `pending_deletion` 안내 화면에도 똑같이 적용한다.
  - **나중에:** 아무것도 하지 않는다.
- 어느 쪽이든 그 값을 `promptedPendingDeletionAt`(2.2)에 적어 같은 예약으로 다시 묻지 않는다. 값이 `null`로 돌아오면 지운다. 2.4-6의 `exists` + `pending_deletion` 안내에서 보인 경우도 `legacyDeletionNoticeAt`과 함께 이 값을 적으므로, 전환기에서 같은 예약을 다시 묻지 않는다.
- 2판에서는 앱이 Firestore에 예약을 쓰지 않으므로, 1판의 "내 예약을 상대 예약으로 오인" 문제는 생기지 않는다.
- 회원 확인 거부나 가족 문서 없음은 삭제 완료의 근거로 쓰지 않는다(1.7.9 삭제는 끝날 수 없다). 2.6.2의 실패 처리를 따른다.
- 어느 경우에도 앱이 스스로 D1을 지우거나 연결을 끊지 않는다.

### 2.7 서버 변경 (단계 A에 더하는 것)
D1 데이터베이스는 아직 만들지 않았다(배포 전). 2판은 열을 더하지 않는다.

1. **1.7.9 삭제 따르기 (3판, 2차 검토 M4):** `POST /api/family/delete`에 `legacyDeletion: true`가 있으면 가족 행을 미리 읽지 않고 한 문장으로 판정한다.

   ```sql
   INSERT OR IGNORE INTO deleted_families (id, deleted_at)
   SELECT ?1, ?2
   WHERE NOT EXISTS (SELECT 1 FROM families WHERE id = ?1)
   ```

   - 1행을 썼으면 `{ ok: true }`다.
   - 0행이면 이유를 읽는다. `deleted_families`에 이미 있으면 410, 가족 행이 있으면 409 `family_exists`다. 가족이 있는데 삭제 기록을 붙이는 경쟁(가족 없음을 읽은 뒤 그 사이 이어받기가 가족을 만듦)은 이 한 문장 안에서 생길 수 없다. 그래서 살아 있는 가족에 삭제 기록이 붙어 이후 정상적인 영구 삭제가 막히는 일이 없다.
   - `legacyDeletion`이 없으면 지금 경로 그대로다. 클라이언트에서 이 값을 싣는 곳은 2.4.1의 "삭제에 따르기" 한 곳뿐이다.
2. **변경 토큰의 `otherMembers`:** `GET /api/family/token?members=1`이면 `members`에서 요청한 클라이언트가 아닌 행의 수를 응답에 싣는다. 쿼리 한 번이 더해지므로, 전환기가 있는 기기만 이 값을 요청한다.
3. **키 형식:** 6장 점검에서 실사용자 키가 서버 정규식을 통과하는지 확인한다. 벗어나면 서버 정규식과 클라이언트 `parseFamilySyncId`를 그 키가 통과하도록 넓힌다. 합류 진입점 두 곳(`App.tsx:343`의 초대 링크, `Profile.tsx:385`의 키 입력)도 32자 16진수만 받으므로 함께 넓힌다(4판, 3차 검토 경미 9). 확인 전에는 바꾸지 않는다.

### 2.8 영구 삭제와 Firestore 사본 (2판)
- 1.8.0의 영구 삭제는 단계 A 그대로 D1만 지운다. 앱은 Firestore에 요청하지 않는다.
- 삭제 확인 화면에 한 줄을 더한다: "이전 서버(Firebase)에 남은 예전 사본은 운영자가 따로 삭제합니다." 이 문장은 이 기기에 `mergeSource: 'ok'` 이전 상태가 있을 때만 보인다.
- **운영자 정리 (앱 밖, 승인 전, 3판에서 기준 보강):** 성기님이 Firebase 콘솔에서 `families` 컬렉션을 하위 컬렉션(`members`, `logs`, `profile`)까지 지운다. 영구 삭제 요청을 받은 가족의 사본도 이 정리로 지워진다. 정리는 아래 조건을 모두 통과할 때만 한다 (2차 검토 M5).
  1. 실사용 가족의 모든 기기가 1.8.0으로 옮겼다. **성기님이 두 가족에게 직접 확인한 것이 주된 기준이다 (4판, 3차 검토 경미 8-d).** D1 `members`의 기기 수와 Firestore 회원 수 비교는 참고로만 쓴다. Firestore 회원 문서는 uid가 바뀔 때마다 쌓이므로 정확하지 않다.
  2. **기록 단위 비교:** 정리 전 점검 스크립트(읽기 전용)로, 가족마다 "Firestore의 살아 있는 기록 문서 id 집합 ⊆ D1의 (살아 있는 행 ∪ 삭제 표식) id 집합"을 확인한다. Firestore의 삭제 표식 문서는 D1에도 삭제 표식이 있어야 한다. 차이가 하나라도 있으면 정리하지 않고, 그 기록을 D1로 옮길 방법을 먼저 정한다. 4판에서 아래를 더한다(3차 검토 경미 8).
     - (a) **삭제된 가족:** D1 `deleted_families`에 있는 가족(1.8.0 영구 삭제, 삭제에 따르기)은 D1 행이 없으므로 비교하지 않고 "삭제됨"으로 따로 보고한다. 정리 대상에 넣을지는 성기님이 정한다.
     - (b) **가족 짝 찾기:** Firestore 가족 id는 원래 키의 해시이고 D1 가족 id는 소문자 키의 해시라서, id만으로는 짝을 찾을 수 없다. 스크립트는 키를 입력받아 두 해시를 각자 기준(2.3.1)으로 만든다. 키가 없어 짝을 찾지 못한 Firestore 가족(시험 가족, 떠난 가족)은 "짝 없음"으로 보고하고 가족별로 성기님이 판단한다.
     - (c) **수정본 비교:** id만 비교하면 떠난 기기가 Firestore에만 남긴 수정본을 놓친다. 살아 있는 기록은 "D1 행의 `client_updated_at` ≥ Firestore `payload.updatedAt`"까지 확인한다. D1 행이 삭제 표식이면 통과로 본다(삭제가 이긴다).
  3. 정리 뒤에는 1.7.9 기기가 거부를 받아 스스로 연결을 끊는다(`7d4753b` `App.tsx:254`). 그래서 1번 확인이 끝나기 전에는 정리하지 않는다.
  - 점검 스크립트의 실행 방법과 이 작업은 배포 순서(18장)의 마지막에 승인 전 항목으로 둔다.
- Firestore 사본이 남아 있는 동안에도 부활은 없다. 이어받기는 D1의 410에서 멈추고(2.4-2), 1.7.9 기기의 평소 동기화는 가족 문서를 새로 만들지 않는다(`7d4753b` `App.tsx:150`의 `allowFamilyCreation=false`).

### 2.9 새로 만드는 가족과 합류 (결함 M 반영)
- **새 가족 만들기**(`allowFamilyCreation=true`)는 Firestore에 있을 수 없으므로 `mergeSource: 'skipped'`, `mergedAt`, `d1UploadedAt`을 바로 적는다. 첫 업로드는 단계 A의 연결 회차가 한다.
- **합류 회차가 성공했을 때 (3판, 2차 검토 M1·M2):** 러너의 연결 회차(관문을 거치지 않음, 2.3)가 성공하면(D1 `exists`) 근거(2.2)로 나눈다.
  - 근거가 없으면 1.8.0 가족 합류다. Firestore를 읽지 않고 이전 상태를 `mergeSource: 'skipped'`, `mergedAt`, `d1UploadedAt`으로 바로 적는다. 연결 회차가 이미 전체 모드로 돌았으므로 7단계를 다시 하지 않고 직전 백업도 만들지 않는다.
  - 근거가 있으면(1.7.9 시절 이 가족에 연결돼 있었거나, 이 키로 `legacyJoin`을 시작한 적이 있음) 이전 상태를 완료로 적지 않고 2.4를 시작한다. 1.7.9가 스스로 연결을 끊은 뒤 다시 합류하는 기기, 사용자가 해제했다가 다시 연결한 기기, `legacyJoin`이 중간에 끊긴 뒤 다시 합류한 기기가 여기에 해당한다. 그래서 상대(1.7.9)의 Firestore 기록을 읽고 전환기가 생긴다.
- **합류 회차가 404로 끝났을 때 (1.7.9 가족 합류, 결함 M):** 근거와 상관없이 이전 모듈의 `legacyJoin(key)`를 부른다. 이 함수는 러너 상한 밖에서 돌고, 화면은 "이전 서버에서 가족 정보를 확인하는 중"을 보여 준다.
  1. Firestore 회원 확인과 가입, 가족 문서 읽기만 한다(2.4-4의 1~2).
  2. 가족 문서가 있고 예약 중이 아니면, **D1 가족을 만들기 전에** 이 키의 이전 상태에 `legacyJoinedAt`과 `baselineChangedAt`(1단계에서 읽은 `lastChangedAt`)을 적는다. 합류가 실패해 이 값이 남아도, 다음 합류가 Firestore를 한 번 더 읽는 비용만 생긴다.
  3. `connectFamily(allowCreate=true)`로 D1 가족을 만든다. 410이면 합류를 실패로 끝내고 "이 가족은 삭제되었습니다"를 보인다. 키는 저장하지 않는다(4판, 3차 검토 경미 5).
  4. 러너에 연결 회차(`connecting: true`, `allowFamilyCreation: false`)를 다시 넣는다. 키 저장은 단계 A의 연결 회차 규칙(첫 저장, 기대 키, `06` 2.6.3)을 그대로 따른다. 이 회차가 성공하면 위 "합류 회차가 성공했을 때"의 근거 있음 경로로 2.4가 시작된다.
  - 예약 중이면 2.4.1의 합류용 화면("요청 취소하고 합류", "합류 취소" 두 가지, 2.4.1 끝)을 보여 준다. 거부(가족 문서가 없는 경우 포함, 2.4-4.2)면 `JOIN_NOT_FOUND`로 끝낸다.
  - 기기 기록은 D1 가족이 생기고 키가 저장된 뒤에야 2.4가 합치므로, 합류가 실패하면 그 가족의 기록이 이 기기에 섞이지 않는다.
- **합류 진입점 (2차 검토 경미 9):** 합류는 초대 링크(`App.tsx:336-369`)와 키 입력(`Profile.tsx:316`) 두 곳에서 시작한다. 지금 `handleSync`(`App.tsx:456`)는 반환값에서 `familyNotFound`를 버리므로, 이 값과 `migrationPending`을 함께 돌려주게 고친다.
- **`joinFamily` (4판, 3차 검토 M2):** 3판은 합류 분기를 `App.tsx`의 함수에 두었는데, 하네스는 `src/database/*`만 불러오므로(`tools/sync-harness/device-real.mjs:32-37`) 분기를 판정하지 못한다. 그래서 합류 흐름 전체를 이전 모듈의 `joinFamily(key, { allowFamilyCreation })`로 옮긴다. 이 함수는 React와 무관하고, App과 Profile은 이 함수만 부른다.
  1. 러너에 연결 회차(`connecting: true`)를 넣는다.
  2. 성공하면 `d1Status`를 `exists`로 적고, 위 "합류 회차가 성공했을 때"의 근거 분기를 한다. 새 가족 만들기(`allowFamilyCreation: true`)면 첫 항목대로 이전 상태를 완료로 적는다.
  3. 결과가 `familyNotFound`이면 `legacyJoin(key)`로 넘긴다.
  4. 그 밖의 실패는 연결 회차의 결과를 그대로 돌려준다.
  - 돌려주는 값은 `{ outcome: 'joined' | 'not_found' | 'deleted' | 'pending_deletion_choice' | 'cancelled' | 'failed', message? }`처럼 화면이 문구와 다음 동작을 고를 수 있는 형태다. 선택 화면이 필요한 경우는 화면 쪽 콜백(`deps.askLegacyDeletionChoice`)으로 묻고, 하네스는 이 콜백에 정해 둔 답을 넣는다.
  - 하네스 기기 명령에 `join`을 더해 이 함수를 그대로 실행한다(5.1). 남는 화면 동작(경고창 문구, 버튼 배치)은 5.4의 코드 검사로 확인한다.

### 2.10 이전 직전 백업 복원 (결함 L)
- 설정 화면의 백업 목록에 `@baby_pre_cloudflare_backup_v1`을 "1.8.0 업데이트 직전 기록"으로 보여 준다.
- `restoreFromLocalBackup`(통째로 바꿈)과 `importDataWithoutLoss`(지운 기록을 새 id로 되살리고 프로필을 덮어쓰며 장부를 지움)는 쓰지 않는다.
- 전용 함수 `restorePreMigrationBackup()`을 만든다.
  - 백업 기록 가운데 id가 지금 기기 기록에도 없고 지금 프로필의 `deletedLogIds`에도 없는 기록만 추가한다. 새 id를 만들지 않고, `updatedAt`은 백업 값 그대로 둔다.
  - 프로필과 삭제 표식은 바꾸지 않는다.
  - 장부, 이전 상태, 근거 표식, 전환기 상태는 지우지 않는다. 그래서 Firestore를 다시 읽지 않는다.
  - 저장은 저장 큐 안의 합치기 저장으로 한다.
- 추가한 기록은 장부에 없으므로 다음 증분 동기화가 D1에 올린다. 서버에 같은 id가 더 새 버전이나 삭제로 있으면 서버 쪽이 이긴다(삭제된 행은 다시 쓰지 않는다, `index.ts`의 `WHERE logs.deleted_at IS NULL`).
- 백업은 기록 사본이 하나 더 생기는 것이므로, 6장에서 실제 크기를 재고 AsyncStorage 여유(약 6MB)를 확인한다.

### 2.11 혼자 쓰기
- `syncKey`가 없으면 이전 단계, 전환기 읽기를 실행하지 않고 `firebase.ts`도 불러오지 않는다. 예외는 사용자가 직접 시작한 합류뿐이다(불변 조건 5, 4판). 합류가 404를 받아 `legacyJoin`으로 갈 때만 `firebase.ts`를 불러온다.
- 근거 표식(2.1)은 혼자 쓰는 기기에도 적지만 저장소에 쓰는 일이라 네트워크 요청이 없다.

## 3. 바꾸지 않는 것
- `firestore.rules`는 바꾸지 않는다. Firestore에는 불변 조건 2의 쓰기 외에는 쓰지 않고, 앱은 Firestore 문서를 지우지 않는다.
- 이전 안내, 삭제 예약 선택 화면, 오류 문구, 백업 목록 항목, 삭제 확인 화면의 한 줄 외에 화면은 바꾸지 않는다.
- 단계 A의 동기화 프로토콜(`06`)은 바꾸지 않는다. 2.7의 서버 변경은 새 필드와 새 분기만 더한다.
- 실사용자에게 앱 삭제나 재설치를 안내하지 않는다. "1.7.9로 되돌리기"는 지원 경로로 두지 않는다.

## 4. 예산

### 4.1 Firestore
하루 읽기 5만, 쓰기 2만은 프로젝트 전체가 함께 쓴다. 보안 규칙의 `exists()`, `get()` 평가도 읽기로 과금된다. 회원만 읽을 수 있는 문서(가족 문서, 기록, 프로필)는 요청마다 `isMember`의 `exists()` 1회가 더해진다.

**1.7.9 기기의 평소 사용량 (1차 검토 M4):** 1.7.9는 6시간마다 전체 대조를 한다(`7d4753b` `sync.ts:39`, `:431-441`). 앱을 쓰는 1.7.9 기기 하나는 하루 최대 약 4N회를 읽는다. 업데이트 전에도 있던 사용량이지만, 전환기에는 1.8.0 쪽 비용과 겹치므로 함께 센다.

| 항목 | 읽기 | 쓰기 | 조건 |
|---|---|---|---|
| 1.7.9 기기 평소 | 약 4N + 증분 | 기록 수 | 업데이트 전까지, 기기당 |
| 1.7.9 자동 삭제 시도 | 회당 약 N + 3 | 0 | 예약 시각이 지난 가족의 1.7.9 기기가 설정 화면을 열거나 앱에 돌아올 때마다(`7d4753b` `Profile.tsx:144-150`). 기록을 모두 읽은 뒤 회원 목록 거부로 실패한다(2차 검토 경미 4) |
| 첫 이전 | N + 페이지 수 + 6 | 1 (회원 문서) | 기기당 1회 |
| 가벼운 실패 재시도 | 회당 6 | 회당 최대 1 | 30분부터, 최대 6시간. 첫날 최대 7회 |
| 무거운 실패 재시도 | 회당 버리는 읽기 최대 500 + 6 | 회당 최대 1 | 1시간부터, 최대 12시간. 첫날 최대 5회 |
| 전환기 가족 문서 | 576 | 0 | 기기당, 5분 간격, 문서 1 + 규칙 평가 1 |
| 전환기 증분 | 상대가 바꾼 문서 수 + 4 | 0 | `lastChangedAt`이 바뀐 때만 |
| 1.8.0 신규 가족 | 0 | 0 | 불변 조건 6 |

- 업데이트한 날의 최악을 두 가족 모두 "한 기기는 1.8.0, 한 기기는 1.7.9"로 잡는다(N=3,000).
  - 1.7.9 두 대: 2 × 12,000 = 24,000
  - 1.8.0 두 대(무거운 실패 다섯 번, 가벼운 실패 일곱 번, 전환기): 2 × (3,012 + 5 × 506 + 7 × 6 + 576) ≈ 12,300
  - 합계 약 3만 6천 회로, 한도의 72%다.
- 정상 경로(실패 없음)는 24,000 + 2 × (3,012 + 576) ≈ 3만 1천 회다. 1.7.9 사용량이 대부분이고, 1.8.0으로 옮기면 그 몫이 사라진다.
- 1.7.9 자동 삭제 시도는 예약 시각이 지난 가족에만 있다. 이런 가족이 있으면 하루 몇 번만 설정 화면을 열어도 수 N회가 더해지므로, 6장에서 예약 상태를 확인하고, 있으면 그 가족의 1.8.0 업데이트와 2.4.1 선택을 먼저 안내한다.
- 6장에서 Firebase 콘솔의 실제 일일 사용량과 N을 확인한 뒤 이 표를 고친다. 최악이 한도의 80%를 넘으면 무거운 실패 간격의 시작값을 2시간으로, 전환기 간격을 10분으로 늘린다.

## 5. 검증 계획

### 5.1 하네스
- 이전 모듈(2.3)은 의존성을 주입받으므로 실제 서버 모드(`06` 2.10)의 기기 프로세스에서 그대로 돈다. 기기 명령에 `runMigration`, `join`(4판, `joinFamily`를 그대로 실행), `legacyJoin`, `migrationState`, `transitionTick`, `setLegacyMarker`, `clearLegacyMarker`(개발 메뉴의 비우기와 같은 함수), `restorePreMigrationBackup`, `setChoiceAnswers`(화면 콜백의 답)를 더한다. 기기 저장소의 초기값은 1.7.9 기기처럼 스키마 2로 둘 수 있게 한다.
- **합류 시나리오의 실행 (4판):** 시나리오 4, 21, 22, 33은 기기 명령 `join`으로 `joinFamily`를 실행한다. 하네스가 합류 분기를 따로 흉내 내지 않는다. `migrationDecision.ts`의 순수 함수는 단위 검사로 확인한다.
- **가짜 Firestore (`stubs/fake-firestore.mjs`):** 지금 `loader.mjs`는 `firebase/firestore`를 가짜 Worker로 바꿔치기한다. 이를 `firestoreImport.ts`와 `firebase.ts`에서 온 import만 가짜 Firestore로 보내도록 고친다. 가짜 Firestore의 상태는 실제 서버 프로세스가 갖고 제어 엔드포인트로 공유한다. 두 기기가 같은 Firestore를 봐야 하기 때문이다. 흉내 낼 것:

  - 앱이 Firestore에 쓴 모든 쓰기의 목록(경로와 필드). 불변 조건 2의 허용 목록(회원 문서 생성, `pendingDeletionAt: null`) 밖의 쓰기가 0건인지 판정한다
  - 시계 주입. 14일, 30일, 태평양 시간 자정 판정은 기기 시계와 가짜 Firestore 시계를 함께 옮겨 확인한다
- 기기 프로세스는 `firestoreImport.ts`와 `firebase.ts`가 언제 불러와졌는지 기록한다(동적 import 판정, 불변 조건 5·6).
  - `pendingDeletionAt`의 timestamp, `null`, 필드 없음
  - 같은 트랜잭션의 기록 쓰기와 `lastChangedAt` 갱신(1.7.9 기기 흉내 `legacy179Write`, `legacy179Schedule`, `legacy179Cancel`)
  - 끝나지 않는 호출, `resource-exhausted`
  - 문서 읽기 수와 규칙 평가 읽기 수 집계(요청마다 규칙 평가 1회)
  - `terminate`와 그 뒤 재생성
  - 페이지 읽기 사이에 다른 기기의 쓰기를 끼워 넣는 걸쇠
  - 앱이 Firestore에 쓴 문서와 지운 문서의 목록(불변 조건 2 판정용)
- **규칙 가정 확인 (1차 검토 S1):** 가짜 Firestore가 흉내 내는 규칙 동작이 실제와 같은지, Firebase 에뮬레이터와 실제 `firestore.rules`로 따로 확인한다(`@firebase/rules-unit-testing`, `verify.sh rules`). 확인할 가정은 아래와 같다.
  - 초대 해시가 맞으면 회원 문서를 만들 수 있다.
  - 예전 문서처럼 `inviteHash`가 없으면 회원 생성이 거부된다.
  - 비회원은 가족 문서와 기록을 읽을 수 없고, 자기 회원 문서는 읽을 수 있다.
  - 회원은 `pendingDeletionAt: null`을 쓸 수 있다.
  - 회원 목록 쿼리는 회원이어도 거부된다.
  - 가족 문서가 없으면 회원 생성이 거부된다(2.4-4.2의 `absent`와 `denied` 구분 근거).
  - (4판) 회원은 `logs` 목록 쿼리(`orderBy(documentId())`, `startAfter`, `limit`)를 할 수 있다. 2.4-4.3의 페이지 읽기 근거다.
  - (4판) 회원은 `setDoc(..., { merge: true })`로 `pendingDeletionAt: null`을 쓸 수 있다. 1.7.9 취소와 같은 쓰기 형태다.
  그래서 확인할 가정은 모두 여덟 가지다.
  에뮬레이터는 Java 17(`/opt/homebrew/opt/openjdk@17`)이 필요하다. 이 검사는 로컬 에뮬레이터만 쓰고 Firebase 프로젝트에 접속하지 않는다.
- 1.7.9 기기는 실제 1.7.9 코드가 아니라 가짜 Firestore 위의 쓰기 흉내로 대신한다. 흉내가 지켜야 할 성질(같은 트랜잭션, 서버 시각, 삭제 표식의 `updatedAt`, 예약이 `lastChangedAt`을 바꾸지 않음)은 `7d4753b` 코드와 맞춘다.

### 5.2 시나리오
1. **두 기기 차례 업데이트:** Firestore 가족(기록 3,000건, 삭제 표식 300건)에서 A가 먼저 업데이트하면 이어받기로 D1 가족이 생기고 기록이 모두 올라간다. B가 나중에 업데이트하면 Firestore를 다시 읽고 D1 쪽과 합쳐진다. 어느 쪽도 연결이 끊기지 않고 세 곳의 기록 집합이 같다. A의 첫 동기화는 이전 전에 404 오류를 보이지 않는다(관문). (결함 A)
2. **부활 금지:** 1.8.0에서 영구 삭제한 가족에 다른 기기가 이전을 시도하면 410을 받고 D1에 가족이 생기지 않는다. `legacyDeletion` 없는 delete는 가족이 없으면 404이고 `deleted_families`가 그대로다. (불변 조건 4)
3. **1.7.9 삭제 예약 가족:** `pendingDeletionAt`이 미래나 과거 timestamp이면 이어받지 않고 연결도 끊지 않는다. `null`이나 필드 없음이면 이어받는다. "요청 취소하고 계속 쓰기"는 이어받기까지 끝난다. "삭제에 따르기"는 D1이 410을 돌려주고 이 기기는 연결이 해제되며 기록은 남는다. 어느 경우에도 앱이 지운 Firestore 문서는 0건이다. (2.4.1, 불변 조건 2)
4. **1.7.9 가족 합류:** 상대는 1.7.9 흉내, D1에 가족이 없다. 새 1.8.0 기기가 초대 링크로 합류하면 D1 가족이 생기고, 키가 저장되며, Firestore 기록이 합쳐지고 전환기가 생긴다. 가족 문서가 없거나 거부되면 합류가 실패하고 그 가족의 기록이 기기에 섞이지 않는다. (결함 M)
5. **동시 이어받기:** 두 기기가 같은 키로 동시에 이어받아도 가족 행은 하나이고, 다음 회차 안에 서로의 기록을 받는다.
6. **uid 변경과 예전 문서:** 근거가 있는 기기의 회원 생성이 거부되면 연결을 유지하고 간격 뒤 다시 시도한다. 근거가 없으면 오류만 보인다. D1이 `exists`이고 거부가 14일 넘게 이어지면 Firestore 읽기를 멈춘다. `missing`이면 멈추지 않는다. (2.5)
7. **강제 종료 시점:** 백업 직후, Firestore 페이지 읽기 중간(다음 시도는 저장된 위치부터 읽고 읽은 페이지를 다시 읽지 않는다), 병합 저장 직후, 이어받기 직후, D1 업로드 묶음 중간에 끝내고 다시 띄워도 기록이 줄지 않고 결국 이전이 끝난다.
8. **병합 완료 + D1 missing:** `mergeSource: 'ok'` 뒤 이어받기 전에 종료하고 다시 띄우면 가족 문서를 다시 확인한 뒤 이어받는다. `mergeSource: 'skipped'`인 키에서 D1 가족이 사라지면 오류만 보이고 이어받지 않는다.
9. **이전 중 가족 전환:** 이전이 도는 동안 다른 키로 바꾸면 앞 가족의 병합 결과가 새 가족에 섞이지 않는다. (4판) 키를 바꾼 뒤 저장이 거부된 페이지는 `firestoreReadAfter`를 올리지 않고, 원래 키 K로 돌아오면 그 페이지부터 모두 읽어 K의 기록이 빠짐없이 합쳐진다.
10. **직전 백업 복원:** 이전 뒤 이 기기에서 기록 하나 추가와 백업에 있던 기록 하나 삭제, 상대 기기에서 백업에 있던 기록 하나 수정, 백업에 있던 다른 기록 하나 삭제(이 기기는 아직 그 삭제 표식을 받지 않음), 아기 정보 수정을 한 뒤 복원한다. 두 기기가 동기화를 마치면 추가와 상대의 수정이 남고, 이 기기와 상대가 지운 기록이 어떤 id로도 되살아나지 않으며(상대가 지운 기록은 서버의 `remoteDeletedIds`가 되돌린다), 아기 정보는 상대 값이다. Firestore를 다시 읽지 않는다. (결함 L)
11. **전환기 중 복원과 가져오기:** 전환기 상태가 유지되고 다음 전환기 읽기가 전체 읽기로 바뀌지 않는다.
12. **A→B 전달과 커서:** A만 업데이트한 상태에서 B(1.7.9 흉내)가 쓴 기록, 삭제, 프로필 변경이 A에 들어오고 A가 D1에 올린다. A의 페이지 읽기 도중 **이미 읽은 페이지의 문서**를 B가 고쳐도 첫 전환기 읽기에서 받는다. B가 프로필만 고친 뒤 가족 문서 외의 읽기가 반복되지 않는다. (결함 G)
13. **전환기 종료:** 상대가 1.8.0으로 옮겨 D1에 연결하면(아무것도 쓰지 않아도) `otherMembers`로 `partnerSeenAt`이 적히고, 상대가 업데이트 직전에 1.7.9로 쓴 기록을 받은 뒤 24시간 안에 전환기가 끝난다. 30일이 지나도 끝난다.
14. **1.7.9 상대의 예약:** B(1.7.9 흉내)가 삭제를 예약하면 A에 선택 화면이 한 번 뜬다. 같은 예약으로 다시 뜨지 않고, 취소 뒤 새 예약에는 다시 뜬다. "요청 취소"는 Firestore 값을 `null`로 만들고, "삭제에 따르기"는 D1 예약을 만든다. 거부와 가족 문서 없음은 삭제로 판정하지 않는다. (4판, 3차 검토 M1) A가 선택 화면을 띄운 사이 B가 예약을 취소하거나 새 값으로 다시 예약한 뒤 A가 "삭제에 따르기"를 누르면 D1 예약이 생기지 않는다. 다시 읽기가 거부되거나 상한에 걸려도 D1 예약이 생기지 않는다. 2.4-6의 `exists` + `pending_deletion` 화면에서도 같다. (2.6.3)
15. **하루 읽기 총량:** 기록 3,000건 가족에서 아래를 흉내 냈을 때 가짜 Firestore 집계(규칙 평가 포함)가 4.1 표의 상한 이하다. 이 판정은 가짜의 과금 모델을 스스로 확인하는 면이 있으므로, 6장 실측으로 보강한다.
    - 정상 이전 1회와 하루 동안 저장 100회, 90초 주기 동기화, 5분 주기 전환기 읽기
    - Firestore가 하루 종일 실패하는 경우
    - 1.8.0 신규 가족과 그 가족에 합류한 기기. 혼자 쓰던 기기가 처음 실행 뒤 합류하는 경우와 새로 설치한 기기가 합류하는 경우. 재시작을 여러 번 해도 0회다.
16. **상한과 직렬화:** Firestore 호출이 끝나지 않으면 15초 뒤 `terminate`가 불리고 다음 시도는 새 인스턴스로 동작한다. 그 사이 평소 동기화는 계속 돈다. 이전 단계와 전환기 읽기가 겹쳐 요청돼도 한 번에 하나만 돈다.
17. **Firestore 오류와 D1 없음:** 연결을 유지하고 러너는 `migrationPending`을 돌려주며 D1 요청을 보내지 않는다. 다음 시도에 Firestore가 살아나면 이어받는다. D1 네트워크 실패에는 Firestore 실패 간격을 적용하지 않는다. 이어받은 직후의 7단계 요청은 관문에 막히지 않는다.
18. **직전 백업 보존:** 두 번째 이전 시도가 백업을 덮어쓰지 않는다. 백업 저장이 실패하면 사용자가 고르기 전까지 이전을 시작하지 않는다.
19. **혼자 쓰기와 근거 표식:** 스키마 2인 1.7.9 저장소로 처음 실행하면 근거 표식이 적힌다. `syncKey` 없이 기록을 추가, 수정, 삭제하고 앱을 다시 열어도 Cloudflare와 Firestore 요청이 0회다.
20. **업로드 완료 판정:** 기록 2,400건 가족의 이전에서 7단계가 이어 가기 회차 여러 개에 걸치면, 마지막 이어 가기 회차가 끝난 뒤에만 `d1UploadedAt`이 적힌다. 7단계 요청을 넣기 전에 시작한 회차의 사건으로는 적지 않는다.
21. **근거 있는 키로 다시 합류 (3판, 2차 검토 M1):** 1.7.9가 스스로 연결을 끊은 기기(프로필 키 없음, 옛 장부의 `familyKey`만 K)를 1.8.0으로 처음 실행하면 표식에 K가 적힌다. K 초대 링크로 다시 합류하면 관문에 막히지 않는다. D1이 `missing`이면 `legacyJoin`으로, `exists`이면 2.4로 가서 Firestore 기록을 읽고 전환기가 생긴다. 사용자가 해제했다가 다시 연결하는 경우도 같다.
22. **`legacyJoin` 끊김 (3판, 2차 검토 M2):** `legacyJoin`의 D1 생성 직후 연결 회차가 네트워크 실패로 끝난 뒤 다시 합류하는 경우와, 키 저장 직후 강제 종료한 뒤 다시 띄우는 경우 모두 Firestore 기록을 읽어 합치고 전환기가 생긴다. `mergeSource: 'skipped'`로 적히지 않는다.
23. **오프라인 시작 뒤 재개 (3판, 2차 검토 M3):** 근거가 있고 병합까지 끝난 기기를 오프라인으로 시작하면 관문이 `paused`를 돌려주고 D1 요청은 0회다. 네트워크가 돌아온 뒤 다음 저장이나 당겨서 새로고침에서 재시작 없이 `d1Status`가 정해지고 이전이 이어진다. 당겨서 새로고침은 `migrationPending`에 경고창을 띄우지 않는다.
24. **삭제에 따르기의 경쟁과 오래된 선택 (3판, 2차 검토 M4):** A가 `missing` + `pending_deletion` 선택 화면을 띄운 사이 (a) B(1.7.9 흉내)가 예약을 취소하거나 (b) 다른 기기가 이어받아 D1 가족을 만든 뒤 A가 "삭제에 따르기"를 누른다. (a)는 서버에 보내지 않고 2.4로 돌아간다. (b)는 서버가 409를 돌려주고, A는 연결을 해제하지 않으며, `deleted_families`가 비어 있다. (4판) (b) 뒤 다시 실행한 2.4가 `exists` + `pending_deletion` 행에 가도 같은 선택 화면이 다시 뜨지 않는다. 서버 단위 검사로, 가족 생성과 `legacyDeletion` 판정이 겹쳐도 살아 있는 가족에 삭제 기록이 붙지 않는지 확인한다.
25. **불변 조건 2의 쓰기 목록:** 시나리오 1~24와 29~34를 모두 돈 뒤, 가짜 Firestore의 쓰기 목록이 회원 문서 생성과 `pendingDeletionAt: null`뿐이다.
26. **대문자 섞인 키:** 대문자가 섞인 키(서버 정규식 통과)로 1.7.9 가족을 이전하면, Firestore는 원래 키의 해시로, D1은 소문자 키의 해시로 찾고 기록이 모두 옮겨진다.
27. **형식이 깨진 Firestore 기록:** `payload.id`가 문서 id와 다르거나 `timestamp`가 없는 문서가 섞여 있어도 나머지 기록이 합쳐지고, 기기 저장소가 정상으로 읽힌다.
28. **운영자 정리 전 점검 스크립트:** 가짜 Firestore와 D1에서 Firestore에만 있는 기록 하나를 만들면 점검이 실패하고, 그 기록이 D1에 오른 뒤에는 통과한다(2.8). (4판) Firestore에만 더 새 수정본이 있는 기록(`payload.updatedAt` > D1 `client_updated_at`)도 실패한다. `deleted_families`에 있는 가족은 "삭제됨"으로, 키를 주지 않은 Firestore 가족은 "짝 없음"으로 따로 보고하고 실패로 세지 않는다.
29. **회원 문서만 남은 가족 (4판, 3차 검토 경미 11):** 이 기기의 회원 문서는 있고 가족 문서가 없는 상태에서 D1이 `missing`이면, "가족 정보를 찾지 못했습니다"만 보이고 연결이 유지되며 이어받지 않는다. 실패 간격 뒤 다시 시도한다. 병합이 끝난 뒤(`mergeSource: 'ok'`) 다시 읽기에서 가족 문서가 없거나 거부되는 경우도 각각 `absent` 행과 2.5로 간다.
30. **병합 전 업로드 (4판, 3차 검토 경미 3):** D1 `exists`이고 Firestore가 실패해 병합 없이 7단계가 끝나면 `d1UploadedAt`만 적힌다. 앱을 다시 열어도 Firestore가 계속 실패하면 7단계(`forceFullRead`)가 반복되지 않는다. 뒤에 Firestore가 살아나 병합하면 `d1UploadedAt`이 지워지고 7단계가 한 번 더 돌아, 병합한 기록이 D1에 오른 뒤에만 이전이 완료된다.
31. **`deleted` 뒤 연결 해제 (4판, 3차 검토 경미 4):** 근거가 있는 기기를 시작했는데 D1이 410이면, 사용자가 아무것도 하지 않아도 이전 모듈이 넣은 평소 요청 하나로 연결이 해제된다. 기기 기록은 남는다.
32. **관문 교착 없음 (4판, 3차 검토 경미 1):** 7단계 요청이 러너 대기열에 있는 동안 저장과 당겨서 새로고침이 이어져 관문과 `ensure`가 여러 번 불려도, 모든 요청이 상한 안에 끝나고 `d1UploadedAt`이 적힌다.
33. **합류 중 예약과 410 (4판, 3차 검토 경미 5):** 합류 중 예약이 있으면 선택지가 두 개뿐이고 어느 쪽도 `deleted_families`를 쓰지 않는다. "합류 취소"는 키를 저장하지 않는다. `legacyJoin` 3단계에서 410이면 "이 가족은 삭제되었습니다"로 끝나고 키를 저장하지 않는다.
34. **백업 표지 (4판, 3차 검토 경미 12):** 백업이 있으면 관문이 여러 번 멈춰도 백업 값(수 MB)을 다시 읽지 않는다(저장소 읽기 기록으로 확인). "백업 없이 계속"을 고른 뒤에는 다시 묻지 않는다. 개발 메뉴의 표식 비우기 뒤 다시 실행하면 표식이 다시 계산되지 않고 `keys`가 빈 배열이다.

## 6. 배포 전 실데이터 점검 (읽기 전용, 승인 전)
배포 전에 실사용자 가족을 읽기만 해서 아래를 확인하고 이 문서에 적는다. Firestore에는 쓰지 않는다. 실행 전에 성기님 승인을 받는다.

- 가족 키 길이와 문자 종류(서버 정규식 통과 여부), 대문자 포함 여부
- 가족 문서의 `inviteHash`, `pendingDeletionAt`(값의 종류), `lastChangedAt` 유무
- `logs` 문서 수와 삭제 표식 수, 회원 문서 수, 기기의 기록 저장 크기(2.10 백업 여유)
- Firebase 콘솔의 최근 일일 읽기·쓰기 사용량(4.1 표의 1.7.9 기준치)
- 배포된 Firestore 규칙이 저장소 `firestore.rules`와 같은지(콘솔의 규칙 화면과 비교)
- 가족 문서의 `pendingDeletionAt`이 지난 timestamp인 가족이 있는지(4.1의 1.7.9 자동 삭제 시도 비용)
- 키와 해시는 화면에 그대로 출력하지 않고 길이와 앞 4자만 보여 준다.
- 점검 방법은 구현 단계에서 정한다. 후보는 성기님 기기에서 개발 메뉴로 읽기 전용 점검을 돌리는 방법이다. 익명 로그인으로는 회원이 아닌 가족을 읽을 수 없으므로(규칙), jjukkom 가족은 그 가족의 기기가 있어야 읽을 수 있다. 점검 범위를 성기님 가족과 콘솔 사용량으로 줄일지 함께 정한다.

### 6.1 점검 결과 (2026-10-31, 성기님 승인, 읽기 전용)
- 방법: 성기님 지시로 Firebase 콘솔에서 서비스 계정 키를 새로 만들어 저장소 밖(`~/.config/babycheck/admin-key.json`, 권한 600)에 두고, `firebase-admin`의 `listDocuments`, `get`, `count`, 규칙 조회만 쓰는 스크립트로 읽었다. 기록 본문은 읽지 않고 개수만 셌다. 스크립트에는 쓰기·삭제 API가 없다(grep 확인).
- 가족 문서 27개. 실사용 가족은 `b373…` 하나로 보인다(기록 2,426건, 삭제 표식 74건, 회원 2명). 나머지 26개는 기록 1~33건의 시험용 가족이다.
- 실사용 가족: `inviteHash` 문자열, `lastChangedAt` timestamp, `pendingDeletionAt` 없음, `profile/shared.birthWeight` 문자열. 이전 경로(2.4)에 걸리는 값이 없다. 1차 읽기는 500건 페이지 5번이다.
- 삭제 예약(`pendingDeletionAt`)이 걸린 가족은 0개다. 그래서 4.1의 1.7.9 자동 삭제 시도 비용은 없다.
- `lastChangedAt`이 없는 가족은 3개(시험용)다. 코드는 없으면 0으로 본다(2.4.1).
- id가 64자 해시가 아닌 가족 문서 `rule…`(24자)이 하나 있다. 어떤 키도 이 id로 해시되지 않으므로 이전에 영향이 없다. 운영자 정리 때 함께 지운다.
- 배포된 Firestore 규칙은 저장소 `firestore.rules`와 같다(배포본 2026-09-24).
- 콘솔 사용량(최근 24시간): 읽기 약 2.5만(무료 한도 5만의 절반), 쓰기 109, 삭제 1. 이전 1회에 기기당 약 2,500 읽기가 더해지므로 두 기기가 같은 날 옮겨도 한도 안이다. 삭제 1건은 앱이 아닌 출처(1.7.9 또는 콘솔)로 보이며 이전과 무관하다.

## 7. 남은 판단
- 전환기 간격(5분, 30분), 30일 상한, 24시간 여유, 실패 간격은 추정값이다. 6장 점검과 배포 뒤 확인에서 고친다.

- 1.7.9 시절 예전 키값 서버(`legacySync.ts`)에만 있고 Firestore로 합쳐지지 않은 기록이 있을 수 있는지는 6장의 키 형식으로 판단한다. 키가 32자 16진수이면 1.7.9도 그 서버를 읽지 않았으므로 해당이 없다.
- 운영자 정리(2.8)의 시점과 범위는 두 가족이 옮긴 뒤 성기님이 정한다.
