## 0. 불변 조건
아래 조건은 모든 단계가 지켜야 하고, 검증 시나리오도 이 조건으로 판정한다. 1·3·4·5는 단계 A가 D1 쪽에서 이미 지키고 있으며, 이 문서는 Firestore 쪽과 이전 단계에서 같은 조건을 지킨다.

1. **기록 보존:** 기기의 기록은 합치기만 하고 줄이지 않는다. 이전 단계, 전환기 읽기, 직전 백업 복원도 기록을 지우지 않는다.
2. **Firestore 쓰기 제한:** Firestore에 쓰는 일은 아래 세 가지뿐이다.
   - 이전 단계와 전환기의 회원 문서 생성 (1.7.9와 같은 동작)
   - 사용자가 확인 절차를 거쳐 요청한 영구 삭제 흐름의 예약 쓰기, 예약 취소 쓰기, 실제 삭제 (2.8)
   - 사용자가 고른 삭제 예약 취소와 1.7.9 삭제 마무리 (2.4.1, 2.6.3)
3. **자동 연결 해제 제한:** 앱이 스스로 가족 연결을 끊는 근거는 D1의 410뿐이다(단계 A `06` 2.7). Firestore 거부와 D1 404는 근거가 되지 않는다.
4. **부활 금지:** 영구 삭제한 가족은 어떤 경로로도 D1에 다시 생기지 않는다. 단계 A의 `deleted_families`와 이 문서 2.4의 이어받기 판정이 함께 지킨다.
5. **혼자 쓰기 무요청:** `syncKey`가 없으면 Cloudflare와 Firestore 요청이 모두 0회다. 예외는 2.8의 정리 대기 항목뿐이다.
6. **Firestore 무요청 기본값 (8.4 경미 반영):** 아래 두 경우가 아니면 Firestore에 요청하지 않는다.
   - 이 기기에 1.7.9 연결 근거(2.1)가 있는 키
   - D1에 가족이 없는(`missing`) 키. 상대가 아직 1.7.9인 가족의 초대 링크로 합류하는 경우다.
   따라서 1.8.0에서 새로 만든 가족과, 그 가족에 합류한 기기의 Firestore 요청은 0회다. `05`의 불변 조건 6은 두 번째 경우를 빠뜨려 2.4-3과 어긋났다.

### 1.2 남은 결함
- **결함 A (연결 끊김):** 단계 A 뒤에는 404로 연결이 끊기지 않는다. 그러나 D1에 가족이 없으므로 업데이트한 기기는 동기화 오류만 보이고, 기존 기록은 D1에 오르지 않는다. 이어받기(2.4)가 필요하다.
- **결함 C (Firestore 부활):** D1 쪽 부활은 단계 A가 막았다. 남은 것은 Firestore에 남은 사본이다. 1.8.0에서 영구 삭제해도 Firestore 사본이 남고, 1.7.9의 삭제 예약과 부분 삭제 상태도 이어받기 판정에 반영해야 한다(2.4, 2.8).
- **결함 D (상한과 재시도):** 이전 단계를 20초 동기화 상한 안에서 돌리면 병합이 버려지고 Firestore 할당량이 반복 소모된다(2.3).
- **결함 F (연결 해제 오판):** Firestore 회원 생성의 `permission-denied`는 uid 변경이나 `inviteHash` 없는 예전 문서에서도 나온다(2.5).
- **결함 G (한 기기만 업데이트):** 1.8.0 기기가 D1에 쓴 기록은 1.7.9 기기에 가지 않고, 그 반대도 따로 읽지 않으면 오지 않는다(2.6).
- **결함 I (키 형식):** 서버는 16~64자 키만 받고 소문자로 바꿔 해시한다. 1.7.9는 32자 16진수가 아닌 키에 예전 키값 서버를 함께 읽었으므로(`7d4753b` `sync.ts:450`), 실사용자 키가 다른 형식일 수 있다(2.7, 6장).
- **결함 L (백업 복원이 기록을 줄임):** 이전 직전 백업을 기존 복원 경로로 되돌리면 기록이 줄어든다(2.10).

## 2. 대책

### 2.1 1.7.9 연결 근거 표식
- 1.8.0을 처음 실행할 때 `syncKey` 유무와 상관없이 `@baby_cf_legacy_key_v1`에 아래 값을 **항상** 한 번 적는다. 값이 이미 있으면 다시 계산하지도 덮어쓰지도 않는다.

  ```ts
  type LegacyKeyMarker = {
    checkedAt: number;
    keys: string[]; // 첫 실행 시점의 프로필 syncKey와 옛 장부(@baby_sync_ledger_v1)의 familyKey. 없으면 빈 배열
  };
  ```

- 이 표식이 "1.7.9 시절 이 기기가 이 가족에 연결돼 있었다"를 판단하는 유일한 값이다. 첫 실행 뒤의 프로필 키나 옛 장부는 근거로 쓰지 않는다. 그래서 혼자 쓰던 기기나 새로 설치한 기기가 1.8.0에서 합류한 키는 근거가 되지 않는다.
- 표식은 `migrateStoredData`(앱 시작 때 한 번 도는 저장소 정리, `storage.ts:77`)에서 적는다. 동기화보다 먼저 돌기 때문이다.
- 출시 전 1.8.0 시험 빌드를 쓴 기기(성기님 시험 기기)는 근거가 잘못 잡힐 수 있다. 시험 빌드는 새 장부 키를 쓰므로 옛 장부가 1.7.9 시절 값으로 남아 있어 실제로는 영향이 없을 것으로 보지만, 출시 빌드를 깔기 전에 개발 메뉴에서 표식을 비우는 방법을 둔다. 실사용자 기기는 시험 빌드를 쓴 적이 없다.

### 2.2 이전 상태
가족 키마다 `@baby_cf_migration_v1:<syncKey>`에 아래 값을 둔다.

```ts
type MigrationState = {
  // 기기에 Firestore 기록을 합친 결과. 'ok'는 실제로 읽어 합침, 'skipped'는 읽을 필요가 없다고 판정함 (8.4 중간 3)
  mergeSource?: 'ok' | 'skipped';
  mergedAt?: number;
  d1UploadedAt?: number;            // 합친 기록을 D1에 전체 모드로 모두 올린 시각
  firestoreReadAfter?: string;      // 페이지 나눠 읽기에서 마지막으로 합친 문서 id
  baselineChangedAt?: number;       // 첫 읽기 시도에서 읽은 가족 문서 lastChangedAt (8.4 중간 1)
  nextFirestoreAttemptAt?: number;  // Firestore를 다시 읽어도 되는 시각
  failureCount?: number;            // 실패 간격 계산용
  deniedSince?: number;             // denied가 처음 관측된 시각 (2.5)
  lastError?: string;               // 화면 안내용
};
```

- **이전 완료**는 `mergedAt`과 `d1UploadedAt`이 모두 있는 상태다. 병합은 끝났는데 업로드가 실패하면 Firestore를 다시 읽지 않고 업로드만 다시 한다.
- 이 값은 데이터 가져오기, 백업 복원, 영구 삭제, 연결 해제에서 지우지 않는다. 그래서 삭제한 가족을 다시 이전하거나 되살리는 일이 없다.
- 모든 값은 수백 바이트라서 AsyncStorage 용량(약 6MB)에 영향이 없다.

### 2.3 실행 방식
- **모듈:** 새 모듈 `src/database/familyMigration.ts`에 `createFamilyMigrator(deps)`를 둔다. 러너(`06` 2.11)처럼 `react`, `react-native`, `expo-*`를 불러오지 않고, 저장소 함수, Firestore 읽기 함수(2.3.1), D1 함수, 시계를 인자로 받는다. 그래서 하네스가 실제 코드를 그대로 실행한다.
- **기기당 하나:** 같은 키의 이전이 이미 돌고 있으면 같은 Promise를 돌려준다. 다른 키로 바뀌면 앞 작업은 결과를 저장하지 않는다. 저장 직전에 현재 프로필의 `syncKey`를 다시 확인하고, 다르면 버린다.
- **상한 밖:** 이전 단계의 Firestore 부분(2.4의 1~6)은 러너의 20초 상한 밖에서 돈다. 전체 예산은 90초이고, Firestore 호출 하나마다 15초 상한을 둔다. 상한에 걸리면 `terminate(db)`로 인스턴스를 닫고, 다음 호출은 새 인스턴스를 만든다.
- **D1 업로드는 러너로:** 2.4의 7단계(D1 전체 업로드)는 러너에 `forceFullRead: true` 요청으로 넣는다(8.4 중간 2). 평소 동기화와 같은 대기열에서 돌므로 장부를 서로 덮어쓰지 않는다. 러너가 결과를 `succeeded`로 알리고 장부에 `full`이 남아 있지 않을 때 `d1UploadedAt`을 적는다. 큰 가족은 러너의 이어 가기(`06` 2.11)로 여러 회차에 걸쳐 올라가며, 그 동안 `d1UploadedAt`은 비어 있다.
- **러너와의 관계:** 러너는 요청을 실행하기 전에 `deps.migrationGate(syncKey)`를 부른다. 이 함수는 이전 상태만 읽는다(네트워크 요청 없음).
  - D1에 가족이 없다고 확인된 키(2.4-2의 결과를 이전 상태와 함께 메모리에 둔다)이고 이전이 끝나지 않았으면 `'paused'`를 돌려준다. 러너는 D1에 요청하지 않고 `{ success: false, migrationPending: true }`를 돌려준다. 화면은 "이전 준비 중"을 보여 주고 오류로 표시하지 않는다.
  - 그 밖에는 `'proceed'`다. 이전이 끝나지 않은 키라도 D1에 가족이 있으면 평소 동기화는 돈다.
- **변경 토큰 폴링:** `'paused'`인 키는 폴링을 시작하지 않는다. 이전이 끝나면 App이 폴링을 시작한다.
- **Firestore 사용 직렬화 (8.4 경미):** 이전 단계, 전환기 읽기(2.6), 영구 삭제 정리(2.8)는 모두 같은 Firestore 인스턴스와 익명 로그인을 쓴다. 모듈 수준의 잠금 하나로 한 번에 하나만 돌게 한다. 한 작업의 `terminate`가 다른 작업의 호출을 끊는 일을 막기 위해서다.
- **실패 간격:** Firestore를 읽어 비용이 드는 실패에만 적용한다. D1 네트워크 실패는 평소 동기화 주기대로 다시 시도한다.
  - 가벼운 실패: `logs` 읽기를 시작하기 전의 실패(로그인, 회원 확인, 가족 문서 읽기, 거부, 삭제 예약)다. 30분, 1시간, 2시간 순서로 늘리고 최대 6시간이다.
  - 무거운 실패: `logs` 읽기를 시작한 뒤의 실패다. 1시간부터 두 배씩, 최대 12시간이다. 저장된 위치부터 이어 읽으므로 한 번에 버리는 읽기는 최대 한 페이지다.
  - 할당량 소진(`resource-exhausted`): 태평양 시간 자정 뒤로 미룬다.
  - 당겨서 새로고침도 이 간격을 지킨다.
- **화면 반영:** 이전 단계가 기기에 합친 결과를 저장하면 App은 저장소에서 기록과 프로필을 다시 읽어 화면에 반영한다.

#### 2.3.1 Firestore 읽기 모듈
- 새 모듈 `src/database/firestoreImport.ts`가 1.7.9 코드(`7d4753b` `sync.ts`)에서 읽기와 회원 가입 경로만 옮겨 온다. Firestore 해시는 1.7.9와 같이 키를 대소문자 그대로 해시한다(`babycheck:family:v2:<key>`, `babycheck:invite:v2:<key>`). D1 해시는 소문자 키 기준이므로(`server/src/index.ts`의 `getAuthContext`), 두 해시를 각자 기준대로 만든다.
- 지금 `firebase.ts`는 모듈을 불러올 때 `db`를 만든다. 이를 `getFirestoreDb()`와 `resetFirestoreDb()`로 바꿔 처음 쓸 때 만들고, `terminate` 뒤에는 새로 만든다. `terminate` 뒤 같은 앱으로 `initializeFirestore`를 다시 부를 수 있는지 구현 첫 커밋에서 확인하고, 안 되면 이름을 붙인 새 앱 인스턴스를 만든다.
- `firestoreImport.ts`와 `firebase.ts`는 이전 단계, 전환기 읽기, 영구 삭제 정리에서만 동적 `import()`로 불러온다. 혼자 쓰는 기기와 1.8.0 신규 가족은 이 모듈을 불러오지 않는다.
- 호출이 쓰지 않는 예전 모듈 `legacySync.ts`(Firestore 이전의 키값 서버)는 그대로 둔다. 1.7.9가 이 경로로 읽던 예전 기록은 1.7.9 시절에 이미 Firestore로 합쳐졌다고 보고, 6장 점검에서 키 형식으로 확인한다.

### 2.4 이전 단계 순서
이전이 끝난 키는 아무것도 하지 않는다. 그렇지 않으면 아래 순서를 밟는다.

1. **이전 직전 백업:** `@baby_pre_cloudflare_backup_v1`에 현재 기록과 프로필을 저장한다. 이미 있으면 덮어쓰지 않는다. 저장이 실패하면(용량 부족 포함) 이전을 멈추고 "기기 저장 공간이 부족해 업데이트 전 백업을 만들지 못했습니다"를 보여 준다. 사용자가 "백업 없이 계속"을 고르면 진행한다. 이전 단계는 합치기만 하므로 백업이 없어도 기록은 줄지 않는다.
2. **D1 가족 확인:** `connectFamily(allowCreate=false)`를 부른다. 결과는 `exists`, `missing`(404), `deleted`(410) 중 하나다. 네트워크 오류면 실패로 끝내고 Firestore 실패 간격은 적용하지 않는다.
   - `deleted`이면 이전을 멈춘다. 연결 해제는 러너의 410 처리(`06` 2.7)가 한다.
3. **Firestore를 읽을지 판단 (`mergeSource`가 없을 때만):**
   - D1이 `exists`이고 근거(2.1)가 없으면 Firestore를 읽지 않는다. `mergeSource: 'skipped'`, `mergedAt`을 적고 7번으로 간다. 1.8.0에서 만든 가족에 1.8.0 기기가 합류하는 경우다.
   - D1이 `missing`이면 근거와 상관없이 Firestore를 읽는다(불변 조건 6의 두 번째 경우).
   - `nextFirestoreAttemptAt`이 지나지 않았으면 읽지 않는다. D1이 `exists`이면 7번으로 가고, `missing`이면 실패로 끝낸다.
4. **Firestore 읽기:**
   1. 익명 로그인 후 `families/<familyId>/members/<uid>`를 읽는다. 없으면 1.7.9와 같이 초대 해시로 회원 문서를 한 번 만든다. 생성이 `permission-denied`이면 결과는 `firestore_denied`다(2.5).
   2. 가족 문서를 읽는다. `pendingDeletionAt`이 timestamp이면(미래든 과거든) 결과는 `firestore_pending_deletion`이다. `null`이거나 없으면 다음으로 간다. 처음 읽는 시도라면 이 문서의 `lastChangedAt`(없으면 0)을 `baselineChangedAt`에 적는다. 이어 읽는 시도는 이 값을 바꾸지 않는다.
   3. `logs`를 문서 id 순서로 500건씩 읽는다. 페이지마다 15초 상한을 두고, 받은 페이지를 곧바로 기기에 합쳐 저장한 뒤 `firestoreReadAfter`를 적는다. `deleted: true` 문서는 삭제 표식으로, 나머지는 `payload`를 기록으로 합친다. 중간에 실패하면 다음 시도는 그 위치부터 읽는다.
   4. 모든 페이지를 읽으면 `profile/shared`를 읽어 프로필 LWW 규칙으로 합친다. 결과는 `firestore_ok`다.
   5. 할당량 소진, 상한 초과, 그 밖의 오류는 `firestore_error`다.
5. **병합 완료:** `firestore_ok`이면 `mergeSource: 'ok'`, `mergedAt`을 적는다. 기기 저장은 `saveSyncedDataWithoutLoss`로 하며, 이 함수는 저장 큐 안에서 기존 기록과 합친다. 이때 2.6의 전환기 상태를 함께 만든다.
6. **D1 가족 결정 (8.4 중간 3 반영):**

   | D1 | Firestore 또는 병합 상태 | 처리 |
   |---|---|---|
   | deleted | 무엇이든 | 이전을 멈춘다. 러너의 410 처리가 연결을 끊는다 |
   | exists | 읽지 않음(근거 없음) | 7번 |
   | exists | ok | 7번 |
   | exists | denied, pending_deletion, error | 병합 없이 7번. `mergeSource`는 적지 않고 실패 간격 뒤 Firestore 읽기만 다시 시도한다. 상대가 이미 D1로 옮겼으므로 평소 동기화는 계속한다 |
   | missing | ok (이번 시도에서 읽음) | `connectFamily(allowCreate=true, fromFirestore=true)`로 이어받고 7번 |
   | missing | 병합 완료 `mergeSource: 'ok'` (이전 시도에서 읽음) | 가족 문서 하나를 다시 읽어 `pendingDeletionAt`이 timestamp가 아니고 문서가 있으면 이어받고 7번. 문서가 없거나 예약 중이면 2.4.1 또는 2.6.3으로 간다 |
   | missing | 병합 완료 `mergeSource: 'skipped'` | 이 키는 D1에 있던 가족이었는데 지금 없다. 서버 이상(404 보존, `06` 2.7)으로 보고 오류만 보인다. 이어받지 않는다 |
   | missing | pending_deletion | 2.4.1 |
   | missing | denied | 2.5 |
   | missing | error | 실패로 끝내고 연결은 유지한다. 실패 간격 뒤 다시 시도한다 |

7. **D1 전체 업로드:** 러너에 `forceFullRead: true` 요청을 넣는다(2.3). 단계 A의 전체 모드가 서버의 모든 행을 당겨 받고, 장부와 다른 항목만 나눠 올린다. 장부의 `full`이 사라지고 결과가 성공이면 `d1UploadedAt`을 적는다.

#### 2.4.1 삭제 예약 중인 가족 (`missing` + `pending_deletion`)
1.7.9에서 삭제를 예약했거나 삭제가 도중에 멈춘 가족이다. 1.8.0의 예약, 취소, 삭제 버튼은 D1만 부르므로, 그대로 두면 아무도 이 상태를 풀 수 없다. 그래서 사용자에게 고르게 한다.

- 화면 안내: "다른 기기에서 가족 서버 데이터 삭제가 예약되어 있습니다." 선택지는 셋이다.
  - **예약 취소하고 계속 쓰기:** Firestore 가족 문서에 `pendingDeletionAt: null`을 쓰고(1.7.9 취소와 같은 쓰기) 곧바로 2.4를 다시 실행한다. 부분 삭제가 진행된 가족이면 남은 기록만 이어받고, 두 기기가 가진 기록은 D1로 모인다.
  - **삭제 마치기:** 예약 시각이 지났을 때만 고를 수 있다. 예약 시각 전이면 남은 시간을 보여 주고 그때 다시 묻는다. 순서는 아래와 같다 (8.4 경미 "삭제 마치기의 확인 근거와 의도 저장").
    1. 의도를 먼저 `@baby_cf_finish_delete_v1:<syncKey>`에 저장한다. 도중에 앱이 끝나도 다음 실행에서 이어 간다.
    2. 1.7.9의 `deleteFamilyCloudData` 순서(다른 회원, 기록, 프로필, 내 회원, 가족 문서)로 Firestore를 지운다.
    3. 확인 근거는 "가족 문서 삭제를 담은 마지막 배치의 커밋 성공"이다. 삭제 뒤에는 회원이 아니어서 가족 문서를 읽을 수 없으므로(규칙의 `isMember`), 읽기로는 확인하지 않는다. 이어 가는 실행에서 회원 문서 읽기가 "없음"이고 가족 문서 읽기가 거부되면, 앞 실행이 마지막 배치까지 커밋한 것으로 본다.
    4. 확인한 뒤에만 서버에 `POST /api/family/delete`를 `legacyFinished: true`와 함께 보낸다(2.7). 서버는 D1에 가족이 없을 때 `deleted_families`에 기록한다.
    5. 상대가 그 사이 예약을 취소해 Firestore 삭제가 규칙에 막히면 D1에는 아무것도 보내지 않고, 의도를 지운 뒤 "다른 기기에서 삭제 예약을 취소했습니다"를 보여 준다.
    6. 끝나면 연결을 해제한다. 기기 기록은 지우지 않는다.
  - **나중에:** 연결을 유지하고 아무것도 하지 않는다. 앱을 다시 열 때 다시 묻는다(가벼운 실패 간격 적용).

### 2.5 연결 해제 오판 방지 (결함 F)
`firestore_denied`는 근거(2.1)로 나눈다.

- 근거가 있으면 이 기기는 Firestore에서 이 가족과 실제로 연결돼 있었다. `denied`는 uid 변경이나 예전 문서 형식 때문일 수 있으므로 `firestore_error`로 낮춘다. 연결은 유지하고 가벼운 실패 간격 뒤 다시 시도한다.
- 근거가 없으면 초대 키가 잘못됐거나 가족이 이미 삭제된 것이다. 동기화 오류로 "가족 연결을 확인할 수 없습니다. 초대 링크를 다시 받아 주세요."를 보여 준다. 앱이 스스로 연결을 끊지는 않는다.
- `deniedSince`를 적고, 7일 넘게 이어지면 안내를 "가족 연결을 다시 확인해 주세요. 기록은 이 기기에 그대로 있습니다."로 바꾼다.
- **재시도 종료 (8.4 경미 "`exists`+`denied` 재시도 종료 조건"):** D1이 `exists`인 가족에서 `denied`가 14일 넘게 이어지면 Firestore 읽기를 멈추고 `mergeSource: 'skipped'`로 적는다. 상대가 이미 D1로 옮긴 가족이라 평소 동기화가 돌고 있고, 상대 기기의 기록은 상대가 D1에 올린다. 화면에는 "이전 서버의 기록을 가져오지 못했습니다"를 한 번 보여 준다. `missing`인 가족은 멈추지 않는다(멈추면 이어받을 길이 없다). 대신 간격의 최대값 6시간을 지킨다.

### 2.6 전환기 (결함 G)
- 전환기는 `mergeSource: 'ok'`인 기기에만 있다. 시작은 `mergedAt`이고 끝은 14일 뒤다.
- **상대 이전 감지로 일찍 끝내기 (8.4 경미 "전환기 종료를 D1 `members`로 판정"):** 변경 토큰 응답에 이 기기가 아닌 회원 수 `otherMembers`를 싣는다(2.7). 이 값이 1 이상이면 상대도 1.8.0으로 옮긴 것이므로 전환기를 끝낸다. `05`의 `last_client_id` 판정은 상대가 아무것도 쓰지 않으면 끝나지 않았다.
- 전환기 상태는 `@baby_cf_transition_v1:<syncKey>`에 따로 둔다. 가져오기와 백업 복원은 이 값을 지우지 않는다.

  ```ts
  type TransitionState = {
    endsAt: number;
    seenFamilyChangedAt: number;      // 마지막으로 처리한 가족 문서 lastChangedAt
    observedPendingDeletion?: number; // 상대(1.7.9)의 삭제 예약을 관측한 시각 (2.6.3)
  };
  ```

#### 2.6.1 커서 (8.4 중간 1 반영)
- 전환기 읽기의 커서는 `seenFamilyChangedAt` 하나다. 처음 값은 2.4-4.2의 `baselineChangedAt`, 곧 **첫 읽기 시도에서 읽은 가족 문서 `lastChangedAt`**이다.
- 이 값이 맞는 이유: 1.7.9는 기록 쓰기와 `lastChangedAt` 갱신을 같은 트랜잭션에서 한다(`7d4753b` `sync.ts:266-323`, 프로필은 `:613-631`). 그래서 `baselineChangedAt` 이후에 바뀐 기록 문서의 `updatedAt`은 모두 `baselineChangedAt`보다 크거나 같다. 페이지 나눠 읽기 도중에 이미 읽은 페이지의 문서가 바뀌어도, 그 변경은 `updatedAt >= baselineChangedAt`이라서 첫 전환기 읽기에 들어온다.
- `05`는 읽은 문서 `updatedAt`의 최댓값을 커서로 썼다. 읽는 도중 앞 페이지 문서가 바뀌면 최댓값이 그 변경보다 앞서 지나가 놓칠 수 있었다.

#### 2.6.2 읽기 순서
- 평소 동기화가 끝난 뒤, 5분에 한 번 이하로 가족 문서 하나를 읽는다. `lastChangedAt`이 `seenFamilyChangedAt`보다 새로우면 아래를 읽는다.
  - `logs`에서 `updatedAt >= seenFamilyChangedAt`인 문서(삭제 표식 포함). 경계 문서는 다시 받지만 합치기가 중복을 처리한다.
  - `profile/shared` 문서 하나. 프로필 LWW 규칙으로 합친다.
- 합친 결과를 저장한 뒤에만 `seenFamilyChangedAt`을 이번에 읽은 가족 문서의 `lastChangedAt`으로 바꾼다. 그 사이에 생긴 변경은 다음 읽기에서 `>=` 경계로 다시 들어온다.
- `lastChangedAt`이 그대로면 가족 문서 1회만 읽는다.
- 받은 기록은 기기에 합치고, 다음 평소 동기화가 D1에 올린다. Firestore 쪽 오류는 평소 동기화 결과에 섞지 않고, 실패하면 가벼운 실패 간격을 적용한다.
- 첫 이전이 끝나면 한 번 안내한다: "새 버전부터 동기화 서버가 바뀌었습니다. 가족 모두 1.8.0으로 업데이트해야 서로의 새 기록이 보입니다."

#### 2.6.3 1.7.9 기기의 삭제 감지 (8.4 중간 4, 경미 "내 예약을 상대 예약으로 오인" 반영)
1.7.9의 삭제 예약은 `pendingDeletionAt`만 쓰고 `lastChangedAt`은 바꾸지 않는다(`7d4753b` `sync.ts:704`). 실제 삭제는 문서를 표식 없이 지운다. 그래서 전환기의 가족 문서 읽기(추가 비용 없음)에서 아래를 본다.

- **예약 관측:** `pendingDeletionAt`이 timestamp이면 먼저 D1 삭제 상태(`deletion-status`)를 확인한다.
  - D1에도 예약이 있으면 1.8.0 쪽(이 기기나 1.8.0 상대)이 2.8로 낸 예약이다. 아무것도 묻지 않는다.
  - D1에 예약이 없으면 1.7.9 상대의 예약이다. `observedPendingDeletion`을 적고 "상대 기기(이전 버전)에서 가족 서버 데이터 삭제를 예약했습니다"를 보여 준다. 선택지는 **예약 취소**(Firestore에 `pendingDeletionAt: null`), **삭제에 따르기**(2.8의 1.8.0 영구 삭제 절차를 이 기기에서 시작), **나중에**다.
- **삭제 완료 판정:** 가족 문서 읽기가 거부되거나 문서가 없을 때는 바로 판정하지 않는다.
  1. 회원 문서를 읽고, 없으면 초대 해시로 다시 가입한다(uid 변경과 예전 문서 형식을 먼저 걸러 낸다).
  2. 재가입이 성공하면 가족은 살아 있다. 평소 읽기로 돌아간다.
  3. 재가입도 거부되고, **그 전에 `observedPendingDeletion`이 적혀 있을 때만** 상대가 1.7.9에서 삭제를 마친 것으로 본다. 1.7.9 규칙은 예약 시각이 지난 뒤에만 삭제를 허용하므로, 예약을 관측하지 못한 거부는 삭제의 근거가 되지 않는다.
  4. 삭제를 마친 것으로 보면 "상대 기기(이전 버전)에서 가족 서버 데이터를 삭제했습니다. 새 서버의 사본도 삭제할까요?"를 보여 준다. **삭제**를 고르면 2.8 절차를 시작하고, **유지**를 고르면 전환기를 끝낸다.
  5. 예약을 관측하지 못한 거부가 이어지면 2.5와 같이 처리한다(근거가 있으므로 오류로 낮추고 간격 뒤 재시도). 전환기가 끝나면 읽기를 멈춘다.
- 어느 경우에도 앱이 스스로 D1을 지우거나 연결을 끊지 않는다.

### 2.7 서버 변경 (단계 A에 더하는 것)
D1 데이터베이스는 아직 만들지 않았으므로(배포 전) 열 추가는 `ALTER TABLE` 없이 `schema.sql`의 `CREATE TABLE`에 넣는다(8.4 경미 "`firestore_origin`의 `ALTER TABLE`").

1. **`families.firestore_origin INTEGER NOT NULL DEFAULT 0`:** 이어받기로 만든 가족만 1이다. connect 요청의 `fromFirestore: true`가 새 가족을 만들 때 적힌다. 이미 있는 가족에 `fromFirestore: true`로 연결하면 0에서 1로만 바꾼다. connect 응답과 `deletion-status` 응답에 `firestoreOrigin`을 싣는다.
2. **가족이 없을 때의 delete (8.4 경미 "가족 없을 때 delete 호출 경로 제한"):** `POST /api/family/delete`에 `legacyFinished: true`가 있고 D1에 가족이 없으며 `deleted_families`에도 없으면, `deleted_families`에 기록하고 `{ ok: true }`를 돌려준다. `legacyFinished`가 없으면 지금처럼 404다. 클라이언트에서 이 값을 싣는 곳은 2.4.1의 "삭제 마치기" 한 곳뿐이다. 키를 아는 가족 구성원만 부를 수 있고, 결과는 그 가족의 D1 이어받기를 막는 것뿐이라서(Firestore와 기기 기록은 그대로) 잘못 불려도 기록은 줄지 않는다.
3. **변경 토큰의 `otherMembers`:** `GET /api/family/token` 응답에 `members`에서 요청한 클라이언트가 아닌 행의 수를 싣는다. 쿼리 한 번이 더해지므로, 전환기가 있는 기기만 `?members=1`로 요청할 때 계산한다.
4. **키 형식:** 6장 점검에서 실사용자 키가 16~64자의 `[A-Za-z0-9_-]`인지 확인한다. 벗어나면 서버 정규식을 그 키가 통과하도록 넓히고, 클라이언트 `parseFamilySyncId`도 함께 확인한다. 확인 전에는 바꾸지 않는다.

### 2.8 영구 삭제 (결함 C)
- 1.8.0의 영구 삭제는 `firestore_origin`이 1인 가족에서 D1과 Firestore를 모두 지운다. 사용자는 "가족 서버 데이터 영구 삭제"를 요청했으므로 Firestore 사본이 남으면 그 요청을 지키지 못한다. `firestore_origin`이 0인 가족은 Firestore에 요청하지 않는다.
- 1.8.0에서 합류한 기기(근거 없음)도 가족 키를 알므로 초대 해시로 회원 문서를 만들어 Firestore를 정리할 수 있다.
- **예약:** D1 예약을 먼저 한다. 성공하면 Firestore 가족 문서에 `pendingDeletionAt`을 D1과 같은 시각(지금부터 60분 뒤)으로 쓴다. 규칙은 50분 뒤보다 늦은 시각만 받는다. Firestore 쓰기가 실패해도 D1 예약은 두고, 정리 대기에 `schedule`을 남긴다.
- **취소 (8.4 경미 "취소 쓰기 실패 시 `cancel` 유지"):** D1 취소와 함께 Firestore에 `pendingDeletionAt: null`을 쓴다. 정리 대기의 항목이 `schedule`이면 지운다(예약이 반영되지 않았으므로). Firestore 쓰기가 실패했고 예약이 반영돼 있었거나 반영 여부를 모르면 `cancel`로 남긴다. `cancel` 재시도가 또 실패해도 `cancel`을 유지한다.
- **삭제 (8.4 중간 5 반영):**
  1. `firestore_origin`이 1이면 D1 삭제 직전에 Firestore 가족 문서를 읽는다. `pendingDeletionAt`이 `null`이거나 없으면, 1.7.9 상대가 Firestore에서 예약을 취소한 것이다. D1 예약도 취소하고 "다른 기기에서 삭제 예약을 취소했습니다"를 보여 준 뒤 멈춘다. 읽기가 실패하면 삭제하지 않고 오류를 보인다.
  2. D1을 먼저 지운다. D1 배치가 `deleted_families`를 남기므로, 이후 Firestore 삭제가 실패해도 가족은 되살아나지 않는다.
  3. D1 삭제가 성공한 뒤에만 1.7.9 순서로 Firestore를 지운다. 실패하면 정리 대기에 `delete`를 남긴다.
- **정리 대기:** `@baby_cf_firestore_cleanup_v1`에 가족 키마다 항목 하나만 둔다. 같은 키의 새 작업은 앞 작업을 대신한다.

  ```ts
  type CleanupEntry = {
    syncKey: string;   // inviteHash를 다시 만들려면 키가 필요하다 (키는 이미 프로필에 평문으로 있다)
    action: 'schedule' | 'cancel' | 'delete';
    nextAttemptAt: number;
    attempts: number;
  };
  ```

  - 연결을 해제해도 항목은 남긴다. 재시도는 30분부터 두 배씩, 최대 24시간 간격이다.
  - **모든 재시도는 D1 상태를 먼저 확인한다.** `deletion-status`를 부르고, 결과가 작업과 맞지 않으면 Firestore에 요청하지 않고 항목을 지운다.
    - `schedule`: D1에 예약이 있을 때만 진행한다. 취소됐으면 항목을 지운다. 410이면 `delete`로 바꾼다. 진행할 때는 `max(D1 예약 시각, 지금부터 60분 뒤)`로 쓴다.
    - `cancel`: D1에 예약이 없을 때만 진행한다. 다시 예약돼 있으면 `schedule`로 바꾼다.
    - `delete`: D1이 410일 때만 진행한다. 410이 아니면 Firestore를 지우지 않고 항목을 지운 뒤 오류로 기록한다.
  - `delete` 진행은 가족 문서 1건만 먼저 읽는다. 문서가 없거나 회원 생성이 거부되면 끝난 것으로 보고 항목을 지운다. `pendingDeletionAt`이 timestamp가 아니면 60분 뒤로 예약을 쓰고 미룬다(D1 삭제가 확정됐으므로 사용자의 삭제 요청을 마치는 쓰기다). 예약 시각 전이면 그 시각 뒤로 미룬다. 지났을 때만 기록과 회원 목록을 읽고 지운다.
  - 화면에는 "서버의 예전 사본 정리가 남아 있습니다"를 보여 준다.

### 2.9 새로 만드는 가족과 합류
- 새 가족 만들기(`allowFamilyCreation=true`)는 Firestore에 있을 수 없으므로 `mergeSource: 'skipped'`, `mergedAt`, `d1UploadedAt`을 바로 적는다. 첫 업로드는 단계 A의 연결 회차가 한다.
- 초대 링크로 합류하는 기기는 2.4를 밟는다. D1에 가족이 있고 근거가 없으면 Firestore를 읽지 않는다.

### 2.10 이전 직전 백업 복원 (결함 L)
- 설정 화면의 백업 목록에 `@baby_pre_cloudflare_backup_v1`을 "1.8.0 업데이트 직전 기록"으로 보여 준다.
- `restoreFromLocalBackup`(통째로 바꿈)과 `importDataWithoutLoss`(지운 기록을 새 id로 되살리고 프로필을 덮어쓰며 장부를 지움)는 쓰지 않는다.
- 전용 함수 `restorePreMigrationBackup()`을 만든다.
  - 백업 기록 가운데 id가 지금 기기 기록에도 없고 지금 프로필의 `deletedLogIds`에도 없는 기록만 추가한다. 새 id를 만들지 않고, `updatedAt`은 백업 값 그대로 둔다.
  - 프로필과 삭제 표식은 바꾸지 않는다.
  - 장부, 이전 상태, 근거 표식, 전환기 상태는 지우지 않는다. 그래서 Firestore를 다시 읽지 않는다.
  - 저장은 저장 큐 안의 합치기 저장으로 한다.
- 추가한 기록은 장부에 없으므로 다음 증분 동기화가 D1에 올린다. 서버에 같은 id가 더 새 버전으로 있으면 서버 쪽이 이긴다.

### 2.11 혼자 쓰기
- `syncKey`가 없으면 이전 단계, 전환기 읽기를 실행하지 않고 `firebase.ts`도 불러오지 않는다. 예외는 2.8의 정리 대기 항목뿐이다.
- 근거 표식(2.1)은 혼자 쓰는 기기에도 적지만, 저장소에 쓰는 일이라 네트워크 요청이 없다.

## 3. 바꾸지 않는 것
- Firestore에는 불변 조건 2의 쓰기 외에는 쓰지 않는다. `firestore.rules`는 바꾸지 않는다.
- 이전 안내, 삭제 예약 선택 화면, 오류 문구, 백업 목록 항목 외에 화면은 바꾸지 않는다.
- 단계 A의 동기화 프로토콜(`06`)은 바꾸지 않는다. 2.7의 서버 변경은 새 필드와 새 분기만 더한다.
- 실사용자에게 앱 삭제나 재설치를 안내하지 않는다. "1.7.9로 되돌리기"는 지원 경로로 두지 않는다.

## 4. 예산

### 4.1 Firestore
하루 읽기 5만, 쓰기 2만은 1.7.9 사용자를 포함한 프로젝트 전체가 함께 쓴다. Firestore 보안 규칙의 `exists()`, `get()` 평가도 읽기로 과금된다(8.4 경미). 회원만 읽을 수 있는 문서(가족 문서, 기록, 프로필)는 읽을 때마다 `isMember`의 `exists()` 1회가 더해진다. 기록 N건인 가족 하나의 하루 최대치는 아래와 같다.

| 항목 | 읽기 | 쓰기 | 조건 |
|---|---|---|---|
| 첫 이전 | N + 페이지 수 + 6 | 1 (회원 문서) | 기기당 1회. 규칙 평가는 쿼리 한 번에 1회로 잡는다(6장에서 실측) |
| 가벼운 실패 재시도 | 회당 6 | 회당 최대 1 | 30분부터, 최대 6시간. 첫날 최대 7회 |
| 무거운 실패 재시도 | 회당 버리는 읽기 최대 500 + 6 | 회당 최대 1 | 1시간부터, 최대 12시간. 첫날 최대 5회 |
| 전환기 가족 문서 | 576 | 0 | 기기당, 5분 간격, 문서 1 + 규칙 평가 1 |
| 전환기 증분 | 상대가 바꾼 문서 수 + 2 | 0 | `lastChangedAt`이 바뀐 때만 |
| 영구 삭제 정리 | 2 (대기) / N + 회원 수 + 규칙 평가 (실행) | N + 회원 수 + 2 | 사용자가 삭제를 요청한 경우만 |
| 1.8.0 신규 가족 | 0 | 0 | 불변 조건 6 |

- 실사용자 가족 둘, N을 각각 3,000, 기기 네 대로 잡는다. 정상 경로는 4 × (3,000 + 6 + 6 + 576) ≈ 1만 4천 회다. 최악(모든 기기가 무거운 실패 다섯 번과 가벼운 실패 일곱 번)은 4 × (3,012 + 5 × 506 + 7 × 6 + 576) ≈ 2만 5천 회로 하루 한도의 절반 정도다.
- 6장 점검에서 실제 N을 확인한 뒤 이 표를 고친다. 최악 합계가 한도의 60%를 넘으면 전환기 간격을 10분으로 늘린다.

### 4.2 D1
단계 A의 `06` 4장을 그대로 따른다. 이전 업로드는 가족당 한 번의 전체 모드이고, 두 번째 기기는 장부와 다른 항목만 올린다. 2.7-3의 `otherMembers`는 전환기가 있는 기기의 토큰 요청에만 행 읽기를 더한다(회원 수만큼, 90초마다).

## 5. 검증 계획

### 5.1 하네스
- 이전 모듈(2.3)은 의존성을 주입받으므로 실제 서버 모드(`06` 2.10)의 기기 프로세스에서 그대로 돈다. 기기 명령에 `runMigration`, `migrationState`, `transitionTick`, `setLegacyMarker`, `restorePreMigrationBackup`을 더한다.
- **가짜 Firestore (`stubs/fake-firestore.mjs`):** 지금 `loader.mjs`는 `firebase/firestore`를 가짜 Worker로 바꿔치기한다. 이를 `firestoreImport.ts`와 `firebase.ts`에서 온 import만 가짜 Firestore로 보내도록 고친다. 가짜 Firestore는 실제 서버 모드에서 별도 프로세스가 아니라 서버 프로세스의 제어 엔드포인트로 상태를 공유한다. 두 기기가 같은 Firestore를 봐야 하기 때문이다. 흉내 낼 것:
  - `firestore.rules`의 회원 생성(`inviteHash` 일치, 예전 문서의 `inviteHash` 없음), 회원이 아닐 때의 읽기 거부, 삭제 규칙과 50분 예약 조건
  - `pendingDeletionAt`의 timestamp, `null`, 부분 삭제 상태
  - 같은 트랜잭션의 기록 쓰기와 `lastChangedAt` 갱신(1.7.9 기기 흉내 `legacy179Write`)
  - 끝나지 않는 호출, `resource-exhausted`
  - 문서 읽기·쓰기 수와 규칙 평가 읽기 수의 집계
  - `terminate`와 그 뒤 재생성
  - 페이지 읽기 사이에 다른 기기의 쓰기를 끼워 넣는 걸쇠
- 1.7.9 기기는 실제 1.7.9 코드가 아니라 가짜 Firestore 위의 쓰기 흉내로 대신한다. 1.7.9 쓰기 경로는 바뀌지 않으므로, 흉내가 지켜야 할 성질(같은 트랜잭션, 서버 시각, 삭제 표식의 `updatedAt`)만 `7d4753b` 코드와 맞춘다.

### 5.2 시나리오
1. **두 기기 차례 업데이트:** Firestore 가족(기록 3,000건, 삭제 표식 300건)에서 A가 먼저 업데이트하면 이어받기로 D1 가족이 생기고 기록이 모두 올라간다. B가 나중에 업데이트하면 Firestore를 다시 읽고 D1 쪽과 합쳐진다. 어느 쪽도 연결이 끊기지 않고, 세 곳의 기록 집합이 같다. (결함 A)
2. **부활 금지:** 1.8.0에서 영구 삭제한 가족에 다른 기기가 이전을 시도하면 410을 받고 D1에 가족이 생기지 않는다. (불변 조건 4)
3. **삭제 예약 중인 가족:** `pendingDeletionAt`이 미래나 과거 timestamp이면 이어받지 않고 연결도 끊지 않는다. `null`이면 이어받는다. "예약 취소하고 계속 쓰기"는 이어받기까지 끝난다. "삭제 마치기"는 Firestore에서 가족이 사라진 뒤 D1이 410을 돌려준다. 상대가 그 사이 취소하면 D1에 아무것도 보내지 않는다. (2.4.1)
4. **삭제 마치기 중 종료:** 마지막 배치 커밋 직후에 기기를 `SIGKILL`로 끝내고 다시 띄우면, 의도 표식으로 이어 가서 D1에 `legacyFinished`를 보낸다. 첫 배치 전에 끝내면 Firestore를 처음부터 지운다. (2.4.1)
5. **동시 이어받기:** 두 기기가 같은 키로 동시에 이어받아도 가족 행은 하나이고, 다음 회차 안에 서로의 기록을 받는다. (`06` 2.2 위에서)
6. **uid 변경과 예전 문서:** 근거가 있는 기기의 회원 생성이 거부되면 연결을 유지하고 간격 뒤 다시 시도한다. 근거가 없으면 오류만 보인다. D1이 `exists`이고 거부가 14일 넘게 이어지면 Firestore 읽기를 멈춘다. (2.5)
7. **강제 종료 시점:** 백업 직후, Firestore 페이지 읽기 중간(다음 시도는 저장된 위치부터 읽고 읽은 페이지를 다시 읽지 않는다), 병합 저장 직후, 이어받기 직후, D1 업로드 묶음 중간에 끝내고 다시 띄워도 기록이 줄지 않고, 결국 이전이 끝난다.
8. **병합 완료 + D1 missing:** `mergeSource: 'ok'` 뒤 이어받기 전에 종료하고 다시 띄우면 가족 문서를 다시 확인한 뒤 이어받는다. `mergeSource: 'skipped'`인 키에서 D1 가족이 사라지면 오류만 보이고 이어받지 않는다. (8.4 중간 3)
9. **이전 중 가족 전환:** 이전이 도는 동안 다른 키로 바꾸면 앞 가족의 병합 결과가 새 가족에 섞이지 않는다.
10. **직전 백업 복원:** 이전 뒤 이 기기에서 기록 하나 추가와 백업에 있던 기록 하나 삭제, 상대 기기에서 백업에 있던 기록 하나 수정과 아기 정보 수정을 한 뒤 복원한다. 두 기기가 동기화를 마치면 추가와 상대의 수정이 남고, 지운 기록이 어떤 id로도 되살아나지 않으며, 아기 정보는 상대 값이다. Firestore를 다시 읽지 않는다. (결함 L)
11. **전환기 중 복원과 가져오기:** 전환기 상태가 유지되고 다음 전환기 읽기가 전체 읽기로 바뀌지 않는다.
12. **A→B 전달과 커서:** A만 업데이트한 상태에서 B(1.7.9 흉내)가 쓴 기록, 삭제, 프로필 변경이 A에 들어오고 A가 D1에 올린다. A의 페이지 읽기 도중 **이미 읽은 페이지의 문서**를 B가 고쳐도 첫 전환기 읽기에서 받는다(8.4 중간 1). B가 프로필만 고친 뒤 가족 문서 외의 읽기가 반복되지 않는다. (결함 G)
13. **전환기 종료:** 상대가 1.8.0으로 옮겨 D1에 연결하면(아무것도 쓰지 않아도) 다음 토큰 응답의 `otherMembers`로 전환기가 끝난다. 14일이 지나도 끝난다.
14. **1.7.9 삭제 감지:** B(1.7.9)가 삭제를 예약하면 A에 선택 화면이 뜨고, A가 2.8로 낸 예약에는 뜨지 않는다. B가 삭제를 마치면 A에 "새 서버 사본도 삭제할까요?"가 뜬다. 예약을 관측하지 않은 거부(uid 변경 흉내)에는 뜨지 않는다. A가 고르기 전까지 D1은 그대로다. (8.4 중간 4)
15. **1.7.9 상대의 취소 존중:** A가 2.8로 예약하고 B(1.7.9)가 Firestore에서 취소한 뒤 A가 삭제를 누르면, D1 삭제 없이 D1 예약도 취소된다. (8.4 중간 5)
16. **정리 대기:** D1 삭제 뒤 Firestore 삭제가 실패하면 정리 대기가 다시 예약하고, 예약 시각 전 재시도는 가족 문서 1건만 읽으며, 시각 뒤 정리가 끝난다. 예약 → Firestore 예약 실패 → 취소 → 간격이 여러 번 지나도 Firestore 가족이 그대로이고 상대(1.7.9) 동기화가 계속된다. 취소 쓰기가 두 번 실패해도 `cancel`이 남는다. (2.8)
17. **하루 읽기 총량:** 기록 3,000건 가족에서 아래를 흉내 냈을 때 가짜 Firestore 집계(규칙 평가 포함)가 4.1 표의 상한 이하다.
    - 정상 이전 1회와 하루 동안 저장 100회, 90초 주기 동기화, 5분 주기 전환기 읽기
    - Firestore가 하루 종일 실패하는 경우
    - 1.8.0 신규 가족과 그 가족에 합류한 기기. 혼자 쓰던 기기가 처음 실행 뒤 합류하는 경우와 새로 설치한 기기가 합류하는 경우. 재시작을 여러 번 해도 0회다.
18. **상한:** Firestore 호출이 끝나지 않으면 15초 뒤 `terminate`가 불리고, 다음 시도는 새 인스턴스로 동작한다. 그 사이 평소 동기화는 계속 돈다. 이전 단계와 전환기 읽기가 겹쳐 요청돼도 한 번에 하나만 돈다(2.3 직렬화).
19. **Firestore 오류와 D1 없음:** 연결을 유지하고 러너는 `migrationPending`을 돌려주며 D1 요청을 보내지 않는다. 다음 시도에 Firestore가 살아나면 이어받는다. D1 네트워크 실패에는 Firestore 실패 간격을 적용하지 않는다.
20. **직전 백업 보존:** 두 번째 이전 시도가 백업을 덮어쓰지 않는다. 백업 저장이 실패하면 사용자가 고르기 전까지 이전을 시작하지 않는다.
21. **혼자 쓰기:** `syncKey` 없이 기록을 추가, 수정, 삭제하고 앱을 다시 열어도 Cloudflare와 Firestore 요청이 0회이고, 근거 표식은 적혀 있다.

## 6. 배포 전 실데이터 점검 (읽기 전용, 승인 전)
배포 전에 실사용자 두 가족을 읽기만 해서 아래를 확인하고 이 문서에 적는다. Firestore에는 쓰지 않는다. 실행 전에 성기님 승인을 받는다.

- 가족 키 길이와 문자 종류(서버 정규식 16~64자 `[A-Za-z0-9_-]` 통과 여부), 대문자 포함 여부
- 가족 문서의 `inviteHash`, `pendingDeletionAt`(값의 종류), `lastChangedAt` 유무
- `logs` 문서 수와 삭제 표식 수(4.1 예산을 실측값으로 고친다), 회원 문서 수
- 키와 해시는 화면에 그대로 출력하지 않고 길이와 앞 4자만 보여 준다.
- 점검 방법은 구현 단계에서 정한다. 후보는 성기님 기기에서 개발 메뉴로 읽기 전용 점검을 돌리는 방법이다. 익명 로그인으로는 회원이 아닌 가족을 읽을 수 없으므로(규칙), 서비스 계정을 쓰는 방법은 쓰지 않는다. jjukkom 가족은 그 가족의 기기가 있어야 읽을 수 있으므로, 점검 범위를 성기님 가족으로 줄일지 함께 정한다.
