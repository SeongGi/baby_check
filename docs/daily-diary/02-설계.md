# 02. 설계: 한줄 육아일기와 댓글

요구사항은 `01-요구사항.md`를 따른다. 이 문서는 데이터 모양, 저장 경로, 화면, 검증 방법을 정한다.

## 1. 핵심 결정 요약
1. 일기와 댓글은 **기존 기록 목록(`logs`)에 새 종류로 넣는다.** 동기화, 백업, 삭제 표식을 그대로 물려받으므로 서버와 동기화 코드를 고치지 않는다.
2. 작성자는 **프로필의 "내 역할"(아빠/엄마)** 로 정한다. 이 값은 휴대폰마다 따로 두는 값이며, 가족 공유 항목 4개(`SHARED_PROFILE_FIELDS`)에 넣지 않는다.
3. "사람마다 하루 한 줄"은 **화면과 저장 함수의 고르기 규칙**으로 지킨다. id는 매번 새로 만든다. 같은 날짜·역할의 줄이 이미 있으면 새로 만들지 않고 그 줄을 고친다. 두 휴대폰이 동시에 써서 줄이 둘 이상 생기면 가장 최근 줄 하나만 보이고, 나머지는 지우지 않고 남긴다(검토 1회차 1·2번 반영).
4. 본문은 기존 `notes` 칸에 담는다. 그래서 이미 설치된 1.8.0 앱에서도 "📝 본문"으로 보이고 멈추지 않는다.

## 2. 데이터 모양 (`src/types.ts`)

```ts
export type DiaryRole = 'dad' | 'mom';

export interface DiaryLog extends BaseLog {
  type: 'diary';
  diaryDate: string;      // 'YYYY-MM-DD', 기기 현지 날짜. 일기가 속한 날의 기준
  authorRole: DiaryRole;
  notes: string;          // 본문, 1~200자(코드 포인트 기준)
}

export interface DiaryCommentLog extends BaseLog {
  type: 'diaryComment';
  parentId: string;       // 댓글을 단 일기 줄의 id
  diaryDate: string;      // 부모 일기의 날짜. 부모를 못 찾아도 날짜로 묶을 수 있게 복사해 둔다
  authorRole: DiaryRole;
  notes: string;          // 본문, 1~100자
}
```

- `LogType`과 `BabyLogEntry`에 두 종류를 더한다.
- `BabyProfile`에 `diaryRole?: DiaryRole`을 더한다. `normalizeProfile`은 `'dad'`나 `'mom'`이 아니면 값을 지운다(undefined).
- `timestamp`: 일기는 처음 저장한 시각을 쓴다. 단 지난 날짜에 쓰면 그날 21:00(현지)으로 둔다. 이 값은 1.8.0 타임라인에서 카드가 놓일 자리와 정렬에만 쓰이며, 새 앱은 날짜를 `diaryDate`로만 판단한다. 댓글은 쓴 시각이다.
- `updatedAt`: 기존 `updateLog`, `addLog`와 같게 저장할 때마다 `Date.now()`를 넣는다. 동기화의 "나중 수정 우선" 규칙이 이 값을 본다.

### 2.1 일기 id
- id: `diary_<YYYYMMDD>_<role>_<무작위>` (예: `diary_20261101_mom_k3j9x2`). 무작위 부분은 `addLog`와 같은 방식으로 만든다. 날짜와 역할은 사람이 읽기 쉽게 붙일 뿐이며, 코드는 id에서 날짜나 역할을 읽지 않는다.
- 날짜로 고정한 id를 버린 이유: 서버는 삭제 표식이 있는 id를 다시 살리지 않는다(`server/src/index.ts` 451~458행의 `deleted_at IS NULL` 조건). 이 기기가 그 표식을 아직 모르는 상태(새 휴대폰, 가족 연결 직후, 예전 백업 복원 뒤)에서 같은 id로 다시 쓰면, 다음 동기화가 방금 쓴 글을 오류 없이 지운다. 또 부모 둘이 같은 역할을 고르면 한 사람의 글이 덮인다. 무작위 id는 두 문제가 모두 없다.
- 새 id가 현재 목록의 id나 `deletedLogIds`와 겹치면 다시 만든다.

### 2.2 한 줄 고르기 규칙
- 같은 `diaryDate`와 `authorRole`을 가진 일기를 한 묶음으로 본다. 묶음 안에서 `updatedAt`(없으면 `timestamp`)이 가장 큰 줄을 고른다. 같으면 id를 코드 포인트 순서로 비교해 큰 쪽을 고른다. 그래서 모든 기기가 같은 줄을 고른다.
- **저장할 때**(`saveDiaryLine`)는 본문이 빈 줄도 묶음에 넣어 고른다. 1.8.0에서 메모를 지운 줄이 있으면 새 줄을 만들지 않고 그 줄을 고친다(검토 1회차 3번).
- **화면에 보여 줄 때**는 고른 줄의 본문이 비어 있으면 그 묶음을 "아직 안 씀"으로 보여 준다.
- 나머지 줄은 지우지 않는다. 묶음에 줄이 둘 이상이면 보이는 줄 아래에 작은 글씨로 "다른 휴대폰에서 같은 역할로 쓴 줄 N개가 더 있어요"를 보여 준다. 누르면 숨은 줄의 본문을 펼쳐 볼 수 있다.
- 숨은 줄 수에는 본문이 빈 줄을 넣지 않는다. 안내 문구는 출처를 단정하지 않게 "같은 역할로 쓴 다른 줄 N개"로 쓴다(검토 2회차 6번).
- 순수 함수 `pickDiaryLine(logs, date, role, { includeEmpty })`와 `groupDiaryByDate(logs)`를 새 파일 `src/utils/diary.ts`에 둔다. 저장 함수와 화면이 같은 함수를 쓴다.
- **형식 검사:** 같은 파일에 `isDiaryLog`, `isDiaryComment`를 둔다. `diaryDate`가 `YYYY-MM-DD` 문자열, `authorRole`이 `'dad'`나 `'mom'`, `notes`가 문자열이거나 없음, 댓글은 `parentId`가 문자열인지 본다. 고르기·묶기·글자 수 세기는 검사를 통과한 기록만 다루고, 통과하지 못한 기록은 지우지 않고 무시한다. 동기화로 깨진 값이 내려와도 새 화면이 멈추지 않게 하기 위해서다(검토 2회차 3번). `notes`가 없는 줄은 본문이 빈 줄로 본다.

### 2.3 댓글 id와 소속
- 댓글은 기존 `addLog`로 만든다(무작위 id).
- 화면은 `parentId`가 보이는 일기 줄의 id와 같은 댓글만 그 줄 아래에 보여 준다. 부모가 지워졌거나 보이지 않는 줄의 댓글은 화면에 나오지 않는다. 데이터는 지우지 않는다.
- 고르기 규칙 때문에 숨은 중복 줄에 달린 댓글이 보이지 않는 일을 막으려고, 같은 날짜·역할 그룹의 모든 줄 id에 달린 댓글을 보이는 줄 아래에 함께 모은다.

## 3. 저장 경로 (`src/database/storage.ts`)
새 함수 두 개(`saveDiaryLine`, `deleteDiaryGroup`)를 더한다. 기존 쓰기 함수는 고치지 않는다.

```ts
export const saveDiaryLine = async (input: {
  diaryDate: string; role: DiaryRole; text: string;
  targetId: string | null;   // 입력 창을 열 때 고른 줄의 id. 처음 쓰면 null
  now?: number;
}): Promise<DiaryLog | null>
```
- `runStorageWrite` 대기열 안에서 `readLogsUnsafe`와 `readProfileUnsafe`로 읽는다. 읽기가 실패하면 쓰지 않고 `null`을 돌려준다(손상 판정된 목록을 빈 배열로 덮어쓰지 않기 위해서다).
- 고칠 줄은 **입력 창을 열 때 고른 줄(`targetId`)** 로 정한다. 저장 순간에 다시 고르지 않는다. 고치는 사이 동기화로 같은 역할의 다른 줄이 내려와도 그 줄을 덮지 않기 위해서다(검토 2회차 1번).
  - `targetId`의 줄이 목록에 있고 `isDiaryLog`를 통과하며 `diaryDate`와 `authorRole`이 입력값과 같으면 그 줄의 `notes`, `updatedAt`만 바꾼다. 하나라도 다르면(입력 창을 연 채 역할을 바꾼 경우 등) 새 줄을 만든다.
  - `targetId`가 null이거나 그 사이에 지워졌으면 2.1 규칙으로 새 줄을 만든다. 묶음에 이미 줄이 있어도 새로 만들며, 두 줄 모두 남고 2.2 규칙으로 하나만 보인다.
- 화면은 입력 창을 열 때 `pickDiaryLine(logs, date, role, { includeEmpty: true })`로 `targetId`를 정한다. 그래서 1.8.0에서 메모를 지운 빈 줄도 고치기 대상이 된다.
- 저장은 `AsyncStorage.setItem(LOGS_STORAGE_KEY, …)` 한 번이고, 다른 기록은 원래 배열 그대로 둔다. 목록 길이는 같거나 1만 늘어난다.
- 글자 수는 이 함수에서도 검사한다(앞뒤 공백 제거 후 1~200 코드 포인트). 넘으면 `null`.

- 이미 200자를 넘는 줄(1.8.0에서 고친 줄)은 자르지 않는다. 입력 창이 원문을 그대로 보여 주고, 저장 버튼을 누르면 "200자 이내로 줄여 주세요"라고 안내한다.

```ts
export const deleteDiaryGroup = async (input: {
  diaryDate: string; role: DiaryRole;
}): Promise<boolean>
```
- 내 줄을 지울 때 쓴다. 대기열 안에서 한 번에, 같은 날짜·역할 묶음의 일기를 모두 목록에서 빼고 그 id들을 `deletedLogIds`에 더한다. 프로필은 `deleteLog`(`storage.ts` 250~271행)와 같이 `normalizeProfile({ ...profile, deletedLogIds, updatedAt: Date.now() })`로 만들고, 기록과 프로필을 `multiSet` 한 번으로 저장한다. 공유 항목 판정을 타는 프로필 저장 함수는 거치지 않는다(검토 2회차 5번). 한 번에 저장하므로 중간에 실패해도 숨은 줄만 다시 보이는 일이 없다(검토 1회차 7번). 숨은 줄까지 지우는 까닭은, 남기면 지운 뒤 옛 줄이 다시 보이기 때문이다. 모두 내 역할의 줄이므로 "본인만 삭제" 규칙 안이다.
- `type === 'diary'`이고 날짜·역할이 같은 줄만 지운다. 조건을 함수 안에서 검사하고, 시험에서 다른 기록이 그대로인지 확인한다.

댓글 추가는 기존 `addLog`, 댓글 삭제는 기존 `deleteLog`를 쓴다. 댓글 삭제 버튼은 `type === 'diaryComment'`이고 내 역할의 댓글에만 보인다.

### 3.1 가져오기·복원에서 역할 보존
`importDataWithoutLoss`는 가져온 프로필을 현재 프로필 위에 덮는다. 백업 파일에는 `diaryRole`이 들어 있으므로, 엄마 휴대폰에서 아빠의 백업을 가져오면 역할이 바뀐다. `restoreFromLocalBackup`도 백업의 프로필을 그대로 쓴다. 그래서 두 함수에서 `diaryRole`만 현재 기기 값을 유지하도록 한 줄씩 더한다. 기록 병합 규칙은 건드리지 않는다. `restorePreMigrationBackup`은 프로필을 바꾸지 않으므로 고치지 않는다.

### 3.2 동기화 영향
- 프로필의 `diaryRole`은 서버에 올라가지 않는다. 서버는 공유 4항목만 저장한다(`server/src/index.ts` 400~420행). 병합(`mergeSyncedState`)은 기기 값이 이기므로 다른 가족 휴대폰의 역할로 바뀌지 않는다.
- 일기와 댓글은 다른 기록과 똑같이 장부 기반으로 올라가고 내려온다. 동기화 코드 변경은 없다.
- 가족 연결이 없으면 `App.tsx`의 기존 처리처럼 `profile.syncKey`가 없어서 동기화를 부르지 않는다. 네트워크 요청은 0회다.

## 4. 기존 화면에서 일기를 빼는 곳
일기와 댓글은 "활동"이 아니므로, 새 앱에서는 아래 세 곳에서 거른다. 공통 도우미 `isDiaryType(type)`(일기와 댓글 모두 참)을 `src/types.ts`에 둔다.
1. `Dashboard.tsx` 활동 타임라인: 먼저 `activityLogs = logs.filter(log => !isDiaryType(log.type))`를 만든다. 자르기(`slice`), 날짜 묶기, 빈 화면 판정(`length === 0`), "더 보기" 건수를 모두 `activityLogs`로 계산한다(검토 1회차 5번).
2. `feedingReminder.ts`의 `mostRecent = logs[0]`: 일기와 댓글을 뺀 첫 기록을 쓴다. 빼지 않으면 마지막 기록이 일기일 때 위젯 상태 문구가 "잘 지내고 있어요"로 바뀐다.
3. `Statistics.tsx`: 화면 맨 앞에서 일기와 댓글을 뺀 목록을 만들어 모든 계산에 쓴다. "하루 평균"의 일수(103~106행)와 "총 N개의 활동 기록"(140행)이 종류를 가리지 않고 전체 기록을 보기 때문이다(검토 1회차 4번).

음성 명령은 종류를 지정해 찾으므로(`VoiceLogButton.tsx` 127행) 고치지 않는다.

## 5. 화면

### 5.1 프로필: "내 역할"
- `Profile.tsx`에 "일기 작성자" 칸을 더한다. 버튼 두 개(👨 아빠, 👩 엄마)이고, 누르면 `onSaveProfile({ diaryRole }, false)`로 바로 저장한다. 공유 항목이 아니므로 동기화를 부르지 않는다.
- 설명 문구: "한줄 일기에 이 이름으로 표시돼요. 이 휴대폰에만 저장됩니다."

### 5.2 홈: "오늘의 한 줄" 칸 (`Dashboard.tsx`, 요약 카드 아래·타임라인 위)
- 오늘 날짜(현지)의 줄을 역할별로 보여 준다: "👩 엄마: 오늘 처음 뒤집었다". 각 줄 옆에 댓글 수(💬 2)를 표시한다.
- 내 줄이 없으면 "오늘 어땠나요? 한 줄 남겨 보세요" 입력 버튼을 보여 준다. 내 줄이 있으면 그 줄을 눌러 고친다.
- 역할이 없으면 입력 대신 "프로필에서 아빠·엄마를 먼저 정해 주세요" 버튼을 보이고, 누르면 프로필 화면으로 간다.
- "모아보기 ›" 버튼은 일기 화면으로 간다.

### 5.3 일기 화면 (새 파일 `src/screens/Diary.tsx`)
- `App.tsx`의 `activeScreen`에 `'diary'`를 더한다. 하단 탭에는 넣지 않고, 홈의 "모아보기"로 들어가며 뒤로 가기는 홈으로 돌아간다(다른 기록 화면과 같은 방식).
- 날짜별 카드 목록을 최근 날짜부터 보여 준다. 오늘 카드는 항상 맨 위에 있다. 기록 화면이 수천 건을 한 번에 그리지 않도록 처음 30일치만 그리고 "이전 일기 더 보기"로 늘린다.
- 카드마다 역할별 줄, 그 아래 댓글(작성자, 본문, 내 댓글이면 지우기 버튼), "댓글 달기" 입력을 둔다.
- 내 줄에는 고치기·지우기 버튼이 있다. 지우기는 확인 창을 띄운다. 다른 가족의 줄에는 버튼이 없다.
- "다른 날짜에 쓰기": 앞·뒤 화살표로 날짜를 고르는 작은 선택기를 둔다(새 라이브러리를 더하지 않기 위해서다). 오늘보다 뒤 날짜와 아기 생일(`birthDate`)보다 앞 날짜는 고를 수 없다. `birthDate`가 형식에 맞지 않거나 오늘보다 뒤면 하한을 두지 않고, 오늘은 항상 고를 수 있다. 하한보다 앞 날짜에 이미 쓴 일기(다른 휴대폰에서 생일을 고친 경우)도 목록에는 그대로 보인다(검토 2회차 7번).

### 5.4 입력 창 (공통 컴포넌트 `src/components/DiaryEditor.tsx`)
- 저장 중에는 저장 버튼을 다시 누를 수 없다(`Dashboard.tsx`의 `editSavingRef`와 같은 방식). `targetId`가 null일 때 연달아 눌러 줄이 둘 생기는 것을 막는다.
- 일기: 여러 줄 입력, 200자 카운터("37/200"), 저장·취소. 댓글: 100자 카운터.
- 글자 수는 코드 포인트(`Array.from(text).length`)로 센다. 한글과 이모지가 한 글자로 세어진다. 입력 중에는 200자에서 더 입력되지 않게 자르고, 저장 시 `saveDiaryLine`이 한 번 더 검사한다.
- 키보드가 입력 칸을 가리지 않도록 기존 `KeyboardAwareScrollView` 또는 모달의 `KeyboardAvoidingView` 패턴(`Dashboard.tsx`의 다음 수유 모달)을 따른다.

### 5.5 `App.tsx` 연결
- `handleSaveDiaryLine(date, text, targetId)`: `saveDiaryLine` → `getLogs` → `setLogs` → `backupLocalData` → `profile.syncKey`가 있으면 `syncLatestData`. 기존 `handleAddLog`와 같은 순서다.
- `handleDeleteDiaryGroup(date)`: `deleteDiaryGroup` → `getLogs` → `setLogs` → `backupLocalData` → `profile.syncKey`가 있을 때만 `syncLatestData`. 기존 `handleDeleteLog`와 같은 순서다.
- 댓글 추가와 삭제는 기존 `handleAddLog`, `handleDeleteLog`를 그대로 넘긴다.
- 삭제 확인 창은 숨은 줄이 있으면 "같은 역할로 쓴 다른 줄 N개도 함께 지워져요"를 덧붙인다(검토 2회차 4번).

## 6. 1.8.0 앱과의 호환 (받아들이는 차이)
- 1.8.0 타임라인에 일기와 댓글이 제목 없는 카드("📝 본문")로 보인다.
- 1.8.0에서 그 카드를 고치면 `type`, `diaryDate`, `authorRole`은 유지되고 `notes`와 `timestamp`만 바뀐다. 새 앱은 날짜를 `diaryDate`로 보므로 줄이 다른 날로 옮겨지지 않는다.
- 1.8.0에서 지우면 삭제 표식이 생기고, 새 앱은 새 무작위 id로 다시 쓴다.
- 1.8.0 위젯의 "마지막 기록"이 일기나 댓글이면 상태 문구가 "잘 지내고 있어요"로 나온다(`feedingReminder.ts` 94~96행). 해는 없고 업데이트하면 사라진다.
- 내 줄을 지울 때 아직 이 기기에 내려오지 않은 같은 역할의 줄은 지우지 못한다. 그 줄은 다음 동기화 뒤에 보인다. 삭제 뒤에 새로 쓴 정당한 줄과 구별할 방법이 없으므로 막지 않는다(검토 2회차 4번).
- 다른 휴대폰에서 지운 줄을 삭제 표식이 오기 전에 이 기기에서 고치면, 고친 글은 다음 동기화에서 사라진다. 모든 기록에 적용되는 "삭제가 수정보다 이긴다" 규칙과 같다.
- 부모가 둘 다 같은 역할을 고르면 묶음 삭제가 다른 사람의 숨은 줄까지 지운다. 삭제 확인 창의 안내로 알린다.
- 1.8.0 통계의 "총 N개"와 평균 일수에 일기가 섞인다. 표시 차이이고 업데이트하면 사라진다.
- 부모가 둘 다 같은 역할을 고르면, 고치기도 그 날짜·역할 묶음에서 가장 최근 줄을 대상으로 잡는다. 그 줄이 다른 사람의 글이면 본문을 덮는다. 다른 활동 기록은 영향을 받지 않는다. 역할을 각자 고르게 안내하는 것으로 다룬다(구현 뒤 리뷰 A 5번).
- 1.8.0 기기가 새 앱의 백업을 가져오면 1.8.0은 프로필을 그대로 들이므로 `diaryRole`도 함께 들어온다. 그 기기를 새 앱으로 올리면 처음부터 백업한 사람의 역할로 잡혀 있을 수 있다. 1.8.0 코드는 고칠 수 없으므로, 프로필의 역할 선택 칸에서 확인하고 바꾸는 것으로 다룬다(리뷰 A 6번).
- 줄을 지운 뒤에도 그 줄에 달렸던 댓글은 지우지 않는다. 새 앱에서는 보이지 않고 계속 동기화되며, 1.8.0 타임라인에는 "📝" 카드로 남는다. 데이터를 지우지 않는다는 원칙을 따른 결과다(리뷰 A 8번).

## 7. 데이터 보전 확인 (기존 기록을 건드리는 경로가 없는지)
- 새 쓰기 경로는 `saveDiaryLine`과 `deleteDiaryGroup` 두 개다. `saveDiaryLine`은 일기 한 건만 추가하거나 바꾸고, `deleteDiaryGroup`은 같은 날짜·역할의 일기만 지운다. 시험에서 "실행 전 일기 아닌 기록 == 실행 후 일기 아닌 기록"을 id별 내용(`stableValue`)으로 대조한다. `readLogsUnsafe`가 정렬해서 다시 쓰므로 배열 순서는 비교하지 않는다.
- 기존 함수(`addLog`, `updateLog`, `deleteLog`, 병합, 동기화)는 고치지 않는다. 바뀌는 기존 함수는 `normalizeProfile`(역할 값 정리), `importDataWithoutLoss`와 `restoreFromLocalBackup`(역할 유지 한 줄씩)뿐이다.

## 8. 검증 방법
1. **단위 시험(새 파일 `tools/diary-tests/`, Node로 실행)**: AsyncStorage를 메모리로 바꿔 `saveDiaryLine`을 돌린다.
   - 새로 쓰기 → 같은 날 다시 쓰기: 줄 1개, 본문 교체.
   - 엄마·아빠가 같은 날: 줄 2개.
   - 삭제 후 다시 쓰기: 새 id가 지운 id와 다르고 화면 고르기에서 보인다.
   - 1.8.0에서 메모를 지운 줄(본문 없음)이 있을 때 저장하면 그 줄을 고치고 줄 수가 늘지 않는다.
   - 같은 날짜·역할의 줄 2개(동시 쓰기 흉내): 고르기가 최근 줄을 고르고, 동점이면 id 큰 쪽을 고른다. `deleteDiaryGroup`이 둘 다 지운다.
   - 일기 아닌 기록 2,439건을 넣고 쓰기·삭제를 반복한 뒤 그 기록들이 id별 내용으로 같다.
   - 201자 거부, 공백만 거부, 이모지 200개 허용.
   - 손상된 저장 값에서 `null`을 돌려주고 저장 값이 그대로다.
   - `normalizeProfile`이 잘못된 역할을 지우고, 가져오기와 로컬 백업 복원이 역할을 유지한다.
   - 통계·타임라인·위젯에 쓰는 거르기 함수가 일기와 댓글을 뺀다.
   - 고치는 도중 같은 역할 줄이 도착한 경우: `targetId`로 저장하면 도착한 줄의 본문이 그대로다. 처음 쓰는 도중 줄이 도착한 경우(`targetId` null): 두 줄 모두 남는다.
   - 깨진 일기(날짜 없음, 역할이 이상함, `notes`가 숫자) 한 건을 섞어도 고르기·묶기가 예외 없이 그 기록을 무시하고, 저장 후에도 그 기록이 그대로 남는다.
2. **두 기기 하네스(`tools/sync-harness`, `verify.sh offline`과 실제 서버 코드를 쓰는 `verify.sh real` 둘 다)**:
   - 엄마 기기가 쓴 줄과 아빠 기기의 댓글이 서로에게 작성자와 함께 보인다.
   - 같은 역할 두 기기가 같은 날 쓰면 두 줄 모두 남고, 두 기기 모두 같은 줄을 고른다.
   - 서버에만 삭제 표식이 있는 상태(새 기기가 첫 동기화 전에 씀)에서 쓴 줄이 동기화 뒤에도 남는다.
3. **네트워크 0회**: 가족 연결 없는 상태에서 저장 함수만 돌릴 때 가짜 `fetch` 호출 수가 0인지 센다. `App.tsx`의 `syncKey` 조건은 하네스가 거치지 않으므로 코드 검토 항목으로 따로 확인한다.
4. 기존 검사: `npx tsc --noEmit`, `npx tsc --noEmit --project server/tsconfig.json`, `npm run test:voice`, `tools/sync-harness/verify.sh offline`.
5. **변이 검증**: 아래를 하나씩 임시로 바꾸고 시험이 실패하는지 본 뒤 원복한다.
   ① 새 id를 날짜·역할 고정 id로 바꾸기, ② 고르기 규칙을 첫 번째 줄로 바꾸기, ③ 저장 고르기에서 빈 줄 빼기, ④ 가져오기·복원의 역할 유지 빼기, ⑤ `normalizeProfile`의 역할 검사 빼기, ⑥ 거르기 함수에서 댓글 빼기, ⑦ `deleteDiaryGroup`의 종류 조건 빼기, ⑧ `saveDiaryLine`이 `targetId`를 무시하고 다시 고르기, ⑨ 형식 검사 빼기.
6. 화면 확인: 에뮬레이터 빌드는 인수인계 문서의 `./gradlew` 방법만 쓰고, 빌드를 할지는 구현 뒤 성기님께 여쭌다.
